# Inbox 加载调用的完整合同

[组件入口](../README.md) · [V3 范围](../../../../docs/formal/03-protocol-inbox.md) ·
[依赖合同](../../../../docs/formal/dependencies.md) · [证明工作流](../../../../docs/proof-workflow.md)

本包固定 a9c 的生产源码，在隔离副本中将 `codec::load` 的库调用移到有状态接口，
保留实际 Rust 的检查、首错、短路及两次配置读取。它复用完整 Inbox 校验候选，
生产源码保持只读。`production-candidate.patch` 供工程审查；一般重构等价、
标准提供者连接和生产采用继续待证，原生对照测试不能代替这些义务。

`InboxLoad.FullLoadContract` 是正确版及四个真实 Rust 错误版共用的合同。
`full_load_contract` 对任意效果状态和接口字典，连接实际抽取的 `load_using`
与完整规格：表／格式／来源关系、内部表排斥、Maintenance 与 Capacity 校验、
长度和预留限制、解码错误映射、完整摘要值比较、完整重编码字节比较、精确预算、
完整 Inbox 校验及第二次配置中的 operation 限额。回调成功、业务错误、外层失败／
发散及返回的效果状态分别保留。两次配置读取不假定相等。

`Raw` 仅是复用原控制流证明的中间表示；九个等式将库比较规范化到同一完整值关系。
它没有另一份完整业务合同。最终组合复用原 `InboxValidation` 与 `ConfigBudget`
规格，不能将局部控制流对应或有限样例视为任意 Inbox 的完整校验。

正常见证给出完整合法 Inbox 和十五步加载轨迹。四个错误版均改动真实 Rust 后重新
编译、抽取，分别给出实际错误接受与同一完整合同的反例：

| 错误版 | 被遗漏的条件 | 合同中的拒绝位置 |
|---|---|---|
| `wrong-digest` | 相同长度的摘要值不同 | digest 后，编码前 |
| `wrong-canonical` | 相同长度的编码字节顺序不同 | 重编码后，完整校验前 |
| `wrong-validation` | 忽略真实完整校验的业务错误 | 第二次配置读取前 |
| `wrong-policy` | 以 session 数代替 operation 上限 | 第二次完整配置读取后 |

这些轨迹的字节／摘要由显式回调见证提供，不宣称它们是真实 JSON 或实际 SHA256
计算结果。合同允许每次读取返回不同状态，也没有补上原实现未检查的
`length(state_json) = bytes.len()` 条件；同一数据库快照的连贯性另由提供者建立。

加载成功的必要后置条件由同一 `FullLoadContract` 推出：`full_load_success_body`
保留读取、解码、摘要和重编码的效果状态，并证明返回的同一 Inbox 对应完整摘要值
和完整编码字节相等、精确预算及完整校验成功。`successful_load_requires_validation`
供调用方直接复用完整校验结论；正常见证沿用上述合法 Inbox。`BodyEvidence` 只记录
这些必要事实，不替换完整合同，也不增加 JSON、SHA、同快照读取或持久接受假设。

## 表示关系与提供者

本包使用依赖登记中已有的字符串、Vec、比较、算术和 Result 逐符号合同；独立抽取
已有 graphic 与 Result 原语，并复用已审查的字面量适配，不引入业务不透明函数。
`DecodedStringsRepresentable` 限定成功解码值中的配置字符串表示范围；
`FullGraphicContract` 连接实际字节分类。其余编码、SQL 和摘要行为保留为显式接口，
字段相等不能推出授权、耐久接受或资源存在。

V7 提供独立认证来源及受保护配置；V1/V2 提供当前意图和耐久发送；V4/V5 提供实际
本地接受、数据库读取、提交／未知提交和重启事实；V6 提供文件、VM 与材料事实。
真实 JSON 字节到值、标准编码及哈希接口的实现连接必须分别落实，不能将整个
Serde、HTTP handler 或收件事务列为可信。

## 开发与验收入口

`native.py --output ...` 在独立副本检查原版、候选、四个错误版和恢复版。共用原生
断言覆盖真实 SQLite 行、JSON、摘要及首拒绝；候选另核对回调顺序。错误版必须
新编译实际协议库和服务测试，并到达精确断言；编译失败或超时不算性质拒绝。

`formal.py --variant correct --development-native .../result.json --output ...` 重新
抽取真实加载及完整校验根，并检查整个视图的真实文件、内核、同服务诊断与依赖审计。
其余 `--variant` 使用上表名称。`inventory.json` 登记五个业务视图及独立原语的
完整函数清单、导入闭包、模板来源和必需审计；负例不导入被变异加载函数的正确证明。
准入回归拒绝漏根、改错调用目标、业务不透明、漏函数及削弱抽取选项。

执行者持有共享重锁，每次使用独立 `.lake/build`，保留失败与缓存。
`--prepare-only` 仅准备输入，不能报告证明通过。`--require-native` 消费 ning
对同一输入的正式功能和组件回执；开发回执不能代替它。

公共 Lake／检查入口、原生登记、冻结和覆盖记录交主控采纳候选改动并统一验收。
本包的局部证明不代表共享整套、E2E 或完整 V3 完成。持久收件、未知提交／重启、
网络外壳和完整系统结论继续单列；历史证据仍限定于各自精确输入。
