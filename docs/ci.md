# CI 运行环境

[文档目录](README.md) · [开发规则](../CONTRIBUTING.md) · [系统验收](testing-plan.md)

普通 CI 与产品沙箱的高权限系统验收分开。宿主为 Linux x86_64，需支持 QEMU、systemd 与 cgroup v2；可用内存和磁盘须满足实际任务预算及管理余量。普通 CI 来宾不暴露 KVM；产品实机验收另要求可访问的 `/dev/kvm`（API 12）及固定 Firecracker/jailer、来宾内核与镜像摘要。部署机器、SSH 配置、代理订阅及管理凭据由运维在仓库外配置，公共仓库只保留通用示例。

### 预打包晋升回归

受信运维一次性用[固定制备配方](../benchmarks/ci-fixture.Dockerfile)在原通用构建服务中准备两份干净模板：基础任务 OCI 使用明确摘要，额外预装固定评分 Python/依赖，不包含解答、测试文件或评分结果。制备导出显式核对原中心 UID 持有的 Ready 源盘，并在复制前后检查原文件身份；导出的独立只读副本、固定内核及最终私有清单仍按运维身份检查。镜像与私有清单保存在仓库外；清单绑定原任务文件、原 OCI、内核、磁盘、资源、启动设置及评分依赖摘要。[输入检查](../benchmarks/ci_fixtures.py)登记和使用前核对内容及文件身份，来宾启动后核对保留目录未泄漏。预装静态模板使用独立 `ci-` 编号，不冒充正式发布的 `tpl-` 模板；回执恢复显式选择该绑定，其他身份检查不变。原基础镜像不修改。

一次性制备复用[隔离实机入口](../tests/system/harbor_generic_chain.py)：在原来完整批准参数之外，选择 `--task polyglot-c-py --task db-wal-recovery --source-kind dockerfile --prepare-ci-fixtures <新私有目录> --ci-build-inputs <两题原 OCI 摘要 JSON> --ci-uv <已批准 uv>`。只有两份 Ready 模板和原构建的精确清理全部完成，才发布最终 `manifest.json`；报告明确为制备而不是题目通过。此阶段可使用现有批准出口，日常预装模式不带这些制备参数。

一次性制备使用独立的 `--ci-preparation-timeout` 构建预算，默认和上限均为 900 秒；它只调整制备构建期限、不增加资源容量，报告不声称原题构建期限通过，日常评分及原解答/评分时限不变，普通执行模式禁止指定此参数。

监督配置显式选择 `source_kind=prepared-ci`、`selection.profile=ci`、`ci_fixtures=<root 私有清单>` 和 `check_name=E2E / terminal-bench-ci`，把清单摘要纳入 `host_assets`，同时更新选择目录的 `selection_sha256`。每轮仍跑候选代码的真实 SDK/控制器/宿主启停与精确清理；不启动下载代理、不启用全局转发、不改变宿主 VPN/DNS。评分只在独立派生目录替换启动脚本，不改冻结源文件和断言；缺少材料失败，不临时联网安装。模板可重复用，工作盘及成绩不可重复用。平台安装程序或模板内容变化须重新制备与批准清单。该模式跳过本轮模板构建，相关构建变更仍用原通用构建定向验收；判据和上线切换看[验收清单](testing-plan.md)。

两题预装链运行中心、固定 Redis 和一个私有运行宿主，不派发构建 VM 或启动私有构建助手。中心登记已核对的全局模板描述，宿主从空缓存经原双向认证下载、封存并登记真实可用事实；不能在配置中伪造正空闲量、健康期限或缓存就绪。中心与 Redis 分别使用不同非 root 账号、0700 目录；宿主使用 root 私有目录。共同可遍历父目录只由 root 管理为 0711，私钥与配置不因此变为公共可读。宿主收件配置须满足原 Rust `InternalInboxConfig::required_bytes()` 的完整请求、回执、确认及退休窗口预留；不能沿用旧单宿主入口的单条 SQL 值上限。修正该单条上限不增加总 SQL、数据库、物理磁盘或验收期限预算。

固定两题档位使用原监督器的 `batch_size=1`，在同一候选、基线和验收身份下串行运行两个独立批次，逐批精确收尾后再运行下一题；两题仍必须全部通过。这样每批只保留一题的中心静态副本、宿主缓存与未完成下载、仓库预留，完整两倍磁盘余量仍不超过 200 GiB。不降低运行池、清理预留、单题磁盘形状或评分要求；若实际绑定后的完整预算超限，原激活检查仍拒绝启动。

配置显式给出 `prepared_ci_disk_budget_bytes`（示例为 200 GiB），它限制**包含两倍安全余量后的总空闲磁盘要求**，不是单台虚拟机磁盘上限。原运行/清理/元数据额度不截断；中心产物、宿主完整缓存、未完成下载、Redis/AOF、日志及文件系统余量均须计费，完整包络仍由原 Rust 物理准入核验。实际包络超过上限时在派发前拒绝，不按稀疏盘当前块数减免，也不跳过检查。原题资源、解答/评分时限和断言保持；通用构建与一次性制备使用两个独立 root 宿主配置/进程及原私有构建助手，属于同一生产入口的不同资源池，不是另一套架构。新配置只用于全新验收身份，旧失败和在途现场保留，不把旧成绩改为双服务成功。

### 普通 CI 自建执行环境

SDK 与 Harbor 的原锁定检查使用 `UV_OFFLINE=1`、`CARGO_NET_OFFLINE=true`，只读取受控黄金盘中已制备的固定依赖，避免缓存未命中后等待 GitHub/PyPI/crates.io 下载。缺材料立即失败，审核新锁后重新制备和验收黄金盘；不静默改锁、联网补料或跳过测试。GitHub 源码检出、任务领取及结果回传仍经原受限网络，依赖离线不表示整条 CI 无网络。

完整 Rust 入口用[阶段诊断工具](../tools/check_stages.py)记录单调时钟耗时、阶段类型与原退出码；构建、工具测试、工作区测试、文档测试和诊断特性分别报告。阶段时间包含该原命令的全部开销；构建细分直接使用 Cargo 原 `Finished … in …`、测试目标使用原 harness 的 `finished in …`，不为计时增加 `--no-run` 或重复编译。无默认特性、工作区及 `contention-diagnostics` 不相互替代，不改变测试参数或持久化要求。完整 Rust 作业预算为 30 分钟，普通四项任务期限不变；这是执行预算，不是安全性质或测试通过证据。工具不代理子进程输入输出、不管理进程清理、不重试命令。

完整基础入口显式加载[检查构建配置](../scripts/check-profiles.toml)，仅为控制核心、控制服务与捆绑 SQLite 引擎三个已测热点包的 dev/test 设置 `opt-level=1`，其余包保持 0；引擎只改变编译优化，不改版本、功能宏或同步配置。不对大型来宾等冷路径全局优化，避免编译成本抵消执行收益。入口统一采用有限调试信息 `debug=1`（保留回溯行号，不生成全部变量/类型信息），关闭一次性环境无跨轮复用价值的增量编译缓存；显式保持 `debug-assertions=true` 与 `overflow-checks=true`，不改为 release、不关闭调试故障点或整数溢出检查。工具回归核对原命令矩阵和环境覆盖，并用三个选中包与未选中包的独立无依赖 Rust 小程序核对 Cargo 实际 profile，实测调试断言与溢出确实 panic。原测试/特性参数不变，只有上述明确的构建配置。未改产品 Rust、Cargo 锁、测试次数、SQL 同步、特性矩阵或容量；普通部署构建与证明抽取不自动加载此配置，也不受该入口环境影响。耗时对比须绑定同提交、相同容量和外部并发情况，区分编译与执行，不能把宿主争用推断成断言失败。

窗口辅助程序的预构建、保留策略夹具和窗口桥接夹具使用同一检查构建配置；同进程夹具共用一次真实编译结果，Cargo 仍核对锁与产物，不靠文件存在便跳过构建。独立 Python 优化模式入口探测保留全部脚本与四种模式（当前 296 次），最多同时执行两次且最多提交两项；每项使用独立临时目录，原 10 秒期限、拒绝标志及无残留断言全部保留。异常和超时在主测试线程逐项记录，不以并行吞掉失败。不并行化共享持久化状态的测试，也不合并不同特性检查。

每轮使用独立有界事件文件（最多 128 KiB），已有文件或符号链接不得复用；本地未指定 `SANDPROOF_CHECK_EVENTS` 时创建私有临时目录，CI 放在本轮 `RUNNER_TEMP`。原检查子命令不继承外层事件文件路径，嵌套检查各自新建记录。正常失败记录首个失败阶段并保持原非零退出码，后续检查不执行；诊断写入失败也不能把检查变绿。工作流收尾尝试生成阶段摘要，但强制中断可能没有终局，最后一个 start 不代表成功或断言失败。摘要只是诊断，不是子进程停止、资源清理或测试通过证据；Actions 原结论保持权威，不能仅凭退出码 124 判断超时。

需要定位失败或比较热点时，把 `gh run view <运行编号> --log` 的输出保存在本地忽略的 `artifacts/`，再运行 `bash scripts/python-entry.sh tools/check_stages.py analyze-log --log artifacts/ci.log --conclusion failure`；`--conclusion` 必须取实际 Actions 结果（`success|failure|cancelled|timed_out`）。工具列出原 Rust harness 的慢测试目标与网络、依赖/材料、超时、断言、清理等**候选信号**；混合原因并列，无法识别保留未分类，不把关键字猜测作为确定归因或自动重跑依据。输出不附带原日志/命令参数，完整日志仍按私有证据保存。未增加 Go 对照、Rust PR 自动触发、KVM 或证明检查。

Actions 的任务期限可能以 `cancelled` 结算，不能擅自把原结论改成 `timed_out`。可另将原检查的 annotations JSON 私下保存，以 `--annotations artifacts/annotations.json` 提供原平台明确的最大执行时间注释；分析器分别保留原结论和期限证据。已通过的负向测试名称不作为故障信号，清理候选仍需原清理回执确认。

SDK 合同任务另运行 `scripts/check-distributed-contract.sh`：先由 `tools/ci_redis.py check` 校验黄金盘中受保护的固定 Redis 源/二进制摘要及可执行权限，再以离线 Cargo 运行选定协议、中心、HTTPS 和原 SQLite 收件组件。只在本轮隔离来宾启动私有回环 Redis；没有宿主凭据或产品 KVM。缺引擎、材料损坏或 Rust 依赖缺失立即失败，不下载 Redis、跳过或回退旧组件。该步骤启用前必须实测候选黄金盘的两次全新离线来宾及故意缺料失败，然后受控切换；源码有此步骤不等于宿主已完成安装，实际切换证据归关联 PR/issue。

中心/宿主的[双产物清单](../tools/ci_e2e_artifacts.py)复用唯一[离线准备入口](../tools/ci_e2e_prepare.py)：同一干净候选离线构建 `sandproof-center`、`sandproof-host`、原窗口工具及原迟到动作检查助手，实际执行两个服务的 `contract-versions` 并核对一致。准备不带 App 凭据，不运行 VM，缺固定材料立即失败。固定验收构建使用 `--release` 并明确开启 `CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=true`，让原受控故障点可实际触发；DK 和两题使用同一对真实产物，不另编译一套宿主。这是测试构建，不是普通部署 release 或证明证据。助手必须来自该候选构建目录，其摘要在准备完成后固化，DK 启动前和实际使用前再次核对。监督器源码已拒绝旧 `server` 配置、单服务报告和旧运行状态；工具自测不是已安装或已执行双服务的证据。真实运行、DK 故障组和两题报告仍须同候选组合验收，成功/故意失败/取消收尾完成后才可受控切换原 App 必需检查。不得用现役单服务成功满足新架构验收。

普通 PR 的 SDK、Harbor、标题和分支规则四项任务保持并行、独立检查名称和原测试命令，通过 `sandproof-ci-sdk/harbor/title/policy` 标签分别调度。`sandproof-ci-rust` 仅供 main/test 推送与手动基础检查，迁移中的旧任务仍按原身份收尾。每项任务使用一台全新 Ubuntu 24.04 QEMU 虚拟机和一次性 GitHub JIT 执行器；执行后注销执行器、停止该虚拟机并删除本轮 seed/工作盘，不把前一轮工作盘用于后续任务。模板为只读基线，Ubuntu、执行器、rustup 与 uv 下载指纹由[构建输入](../tools/ci_image_pins.json)记录，Rust 版本仍以 `rust-toolchain.toml` 为准。[uv 安装入口](../tools/ci_install_uv.sh)只从固定官方 PyPI 制品下载 uv 0.11.31，核对 SHA256 后以 root/0555 安装到 `/usr/local/bin/uv`；SDK/Harbor 工作流直接检查 `uv --version`，版本缺失或不符即失败。工具或执行器更新时重新准备基线并重新验收，不能静默沿用旧证据。

固定普通 CI 依赖由[可信预热入口](../tools/ci_dependencies.py)从管理员已审查的精确提交准备输入；输入只含 SDK/Harbor 项目的锁与清单、Cargo 锁与清单、固定 Redis 官方归档及必要的固定工具配方，不由 PR 提供任意预热命令。先运行 `python3 tools/ci_dependencies.py prepare-input --checkout <审核检出目录> --approved-commit <40位提交> --output <新私有输入JSON> --redis-archive <固定官方Redis归档>`，它核对输入文件与该提交的 Git blob 一致。旧运行 pins 缺少 uv 三个字段时，创建独立 root 私有制备 pins，保留当前 `cloud_sha256`、`golden_sha256` 及既有 `golden_image` 等基线身份，只从已核验的[构建输入](../tools/ci_image_pins.json)加入 `uv_version`、`uv_url`、`uv_sha256`，不提前覆盖运行 pins；通过受控宿主入口 `python3 tools/ci_vm.py --role preheat --pins <独立私有制备pins> --dependency-input <该输入JSON> --timeout <秒>` 从当前黄金盘派生独立来宾，安装同一固定 uv，并以 runner 身份按原锁预热 uv 和 Cargo。新增 [Redis 制备工具](../tools/ci_redis.py)只接受输入锁固定的官方归档，在同一隔离来宾以 runner 身份、固定参数编译；可信 root 配方确认 runner 工作结束后才封存 x86_64 程序和源/二进制摘要，缺失、损坏或不受保护材料拒绝。来宾不下载 Redis、不接受 PR 的构建命令，也不初始化生产账本。预热须在不同临时目录完成离线重建及 Git 安装来源核对，真实退出成功后才发布按磁盘摘要命名的新候选黄金盘及 `prepared-pins.json`，不会自动替换运行 pins。候选 pins 位于受下文 40 份／128 MiB 限制回收的诊断目录，开始验证前须保存 root 私有副本。入口实现不表示已安装或已验收；同固定材料的两次全新虚拟机离线验证、镜像与输入摘要和真实结果须记录在对应 issue/PR。

预热入口只在普通执行位置自然空闲、登记已清且没有已有维护标记时，自动认领本轮暂停与独占身份；他人的维护标记、未清普通占用或仍在运行的工作单元均使启动拒绝。管理员先等待普通任务自然完成再调用，不提前创建 `paused` 或 `exclusive-host`，也不停止在途任务。收尾确认本轮来宾与工作盘已停止、回收后，只按精确身份移除自己的标记并恢复准入；未知结果保留身份供核对。

候选盘验证通过后，更换黄金盘另行认领本次 `paused` 停止新准入，等待全部普通工作单元及未知占用排空，再核对候选盘、保存的 pins 与输入摘要并切换受控配置；保留旧基线用于恢复，完成后只移除本次认领的暂停标记。候选 pins 的 `golden_image` 为新的按摘要命名文件，切换前须先受控安装支持该身份的新 `ci_vm.py` 并完成静态核验，不能让旧入口忽略新文件名。旧黄金盘没有固定 uv 时，应先验证并切换含固定 uv 的候选盘，再启用直接调用预装 uv 的工作流；迁移中的旧工作流仍按原入口完成。每轮工作盘从只读黄金盘获得固定材料，uv/Cargo 的可写缓存仅存在当轮工作盘，任务结束后随盘回收，不回写黄金盘或与后续任务共享。SDK/Harbor 新锁缺失材料时须重新审核固定提交、受控制备并验证新基线；独立 Rust 检查仍按原受限网络配置运行。不把缓存命中等同于来源检查，也不取消原 `--locked` 安装与测试门槛。

宿主侧[单任务入口](../tools/ci_vm.py)必须由受控安装调用，不由 PR 调用；[基线准备](../tools/ci_vm_bootstrap.sh)和[启动前隔离探针](../tools/check_ci_isolation.py)在可信镜像中执行。宿主管理凭据不进入镜像、seed 或任务环境，只传单任务 JIT 配置。虚拟机中的 runner 用户无 sudo/docker/kvm 等管理权限，不挂宿主目录、不转发 SSH、不暴露宿主 KVM；限制网络仅能经过[出站网关](../tools/ci_proxy.conf)访问当前 CI 所需公开依赖域名，拒绝私有地址、管理端口和其他目标。owner 已同意仅将 Python/Rust 的既有公共依赖域名直连，GitHub/Actions 继续经现有宿主代理；两条路线仍使用相同白名单、端口及私有地址拒绝，不修改产品沙箱网络策略。[服务模板](../tools/ci_proxy.service)仅监听宿主回环。SDK/Harbor 任务使用[CI Git 入口](../tools/ci_git.py)只拉取各自 `uv.lock` 的已锁定提交，不重复下载父提交历史；保留原来源、提交与安装来源检查，普通 Git 操作和开发者本地入口不变，不共享前一任务的可写缓存。

普通 PR 四个档位各一台合计 6.5 GiB 来宾内存，另一个 Rust 档位为 4 GiB；每个档位最多两个独立执行位置，总上限十台，但**每次启动仍须通过宿主实际内存及磁盘准入**，不意味着任一宿主都能同时运行两整套检查。优先为有需求的各类任务提供第一个位置，再按余量补第二个；同类在途检查不再强制阻塞其他 PR，标签和保留的检查名称不变。任务之间不设串行依赖，任务内部限制编译并行，防止同时编译占满测试机。不可用、启动失败、测试失败、取消和清理未知均按真实结果报告；宿主报告只说明虚拟机生命周期，不能代替 GitHub 上的测试结论。私有诊断日志和源码树/镜像/执行器摘要留在宿主，公开 PR 只贴脱敏结果。

普通执行器的启动/领取阶段最多 300 秒；固定 runner 首次输出对应任务的开始行后，单独计入执行预算，等待不占用此预算。Rust 为 2100 秒（工作流 30 分钟及 5 分钟回传/退场余量），其他档位仍为 1800 秒且原 5/15 分钟工作流期限不变。重复、其他任务、stderr 或超长开始行不能重置计时；开始行只影响一次有限预算，不是授权、任务归属或检查通过证据。Python 监视器总时长 Rust 最多 2400 秒、其他最多 2100 秒；独立 systemd 单元分别为 2500/2200 秒，包含有界宿主收尾余量。制备/预热仍按原绝对期限执行。超时只终止本轮精确进程组并保留诊断，确认工作盘/JIT/执行器登记清理后才释放位置，不把退出报告当作测试成功。

自动补充由宿主受控安装的[补充服务](../tools/ci_runner_supervisor.py)和[服务单元](../tools/ci_runner_supervisor.service)负责。专用 GitHub App 只安装到本仓库，权限限定为 Actions 只读、Administration 写入和默认 Metadata 只读；它不需要 webhook 或入站公网端口。Administration 是仓库管理权限，不是只允许操作执行器的细粒度权限，所以 App 密钥仍是高敏感宿主管理凭据，不能复制个人登录凭据或向 PR 发放它。

部署前由管理员把 App 私钥放入 `/etc/sandproof-ci/app-key.pem`（目录 root/0700、文件 root/0600），以[鉴权工具](../tools/ci_github_app.py)核对安装范围，取得安装编号；将[配置示例](../tools/ci_runner_supervisor.example.json)填为本 App 的 Client ID、安装编号、普通工作流编号和宿主回环代理地址，安装到 `/etc/sandproof-ci/supervisor.json`（root/0600）。宿主 `/usr/bin/python3` 需要发行版提供的 PyJWT、cryptography；安装的工具、单元和配置均由 root 管理，不从 PR 下载执行。用 `systemd-analyze verify` 检查单元，再 `systemctl enable --now sandproof-ci-supervisor.service`。密钥通过 systemd 的独立凭据目录读取；工作执行单元只收到该任务的 JIT 配置，不继承 App 密钥或安装令牌。令牌限定本仓库和上述权限，并在到期前更新，不把管理凭据写入日志。

服务只轮询固定 `function-ci.yml` 和独立 `rust-ci.yml` 的排队任务，后者尚未登记时不阻塞普通 PR，登记后核对固定路径且只接受 push/manual 事件；它不运行高权限或证明任务。核对名称、完整标签集合及去重后的任务身份；标签是需求信号，GitHub 决定实际分配，不能声称某次注册绑定了某个 job。启动中或空闲的执行器已覆盖相应排队需求，不能因任务尚未分配便重复补充；确认忙碌且仍有排队需求时才补同类位置。每个执行位置一份持久占用登记和独立启动锁；第一个位置兼容旧登记及旧锁，第二个位置独立登记。先记身份再注册、先记启动意图再调用 systemd。管理服务重启不会停止独立工作单元，而是按精确单元身份接管；注册回执丢失时按精确名字查回，清理或观察结果未知时保留占用并退避，不重复启动。工作单元的整组进程停止后才删除工作盘和 JIT 文件、注销登记，再释放位置。宿主重启后清理上次遗留工作，不复用旧盘。缺失身份或不熟悉的执行器要求人工核对，不宽泛删除他人的资源。

启动前将当前虚拟机尚未实际占用的内存预算计入预留，保留 2 GiB 宿主余量；磁盘按每台 32 GiB 逻辑上限和额外 8 GiB 余量准入。QEMU 预分配来宾内存，工作单元有独立内存上限；资源不足时排队，不造绿色检查。控制台与 QEMU 错误日志分别最多 8 MiB，超限终止自己的任务；只回收已经停止、登记可辨识的诊断目录，保留最多 40 份且合计不超过 128 MiB。不递归清空目录，未知文件、旧 VM 用户所有的有限批次证据及仍运行的目录不自动删除。systemd 管理日志也限速；宿主全局日志容量仍由管理员的 journald 策略管理。

运维可在 root 私有 `/var/lib/sandproof-ci/supervisor/` 创建 `paused` 文件停止新准入（已有任务继续），删除它后恢复；后续高权限宿主验收使用 `exclusive-host` 标记之前，须先等待普通工作单元全部退出，不能仅靠标记便宣布独占。标记写明本次维护身份；验收结束、启动前被拒绝或调查转回本机时，确认本次宿主工作已停止后及时移除自己的标记并核对准入恢复，不能为尚未运行的验收长期阻塞日常 CI。更新调度服务须核对旧文件身份、保留恢复副本并兼容在途登记；只重启管理服务，不停止独立工作单元。日常检查 `systemctl status sandproof-ci-supervisor.service` 与脱敏 journal；不要输出私钥、凭据目录或 `.jit` 文件。未配置并实测可信服务时，仍只能称为有限批次验收。版本变动重跑真实成功/失败与干净恢复，不以此前单任务入口的验收替代补充服务验收。

这套普通执行环境不运行 KVM 系统验收、真实题目或 Lean 完整证明；普通绿灯和旧 2.0 报告不能代替高权限验收或 2.1 通过。自建执行器不绕过分支保护。

### 中心与宿主拆分的 CI 扩展

[#292](https://github.com/ningZhang-cs/sandproof/issues/292) 使用同仓库、两套独立服务产物。普通 PR 四项检查及 test/main 后的 Rust 检查节奏保持；此扩展不增设 root runner，也不要求每 PR 真题或完整 Lean 证明。

| 环境 | 待增加的工作 | 权限与通过依据 |
|---|---|---|
| 现有 SDK 合同隔离来宾 | 已实现 `scripts/check-distributed-contract.sh` 独立步骤；选定中心/协议/存储 Rust 组件、真实固定 Redis 与受控节点；安装和运行证据归 PR/issue | 回环专用账本、受控证书，无 KVM/生产凭据；缺固定材料报错，不用假库或 skip 代替 Redis 故障验收 |
| 可信 KVM 监督器 | 同候选中心＋Redis＋一个真实宿主，经双向认证 HTTPS；先 DK 故障组，再既有两题从中心入口运行 | 独立账号/目录/端口/身份，两端摘要绑定候选；故障组、评分、清理和报告均成功才发布原 App/检查名 |

固定 Redis、证书工具与依赖在[输入锁](../references/v1-baseline.json)登记；定向组件脚本、固定黄金盘预热配方及普通 SDK 工作流步骤已实现，实际受控安装与验收以关联 PR/issue 的精确证据为准，不能临时用 latest。组件运行前的制备入口见[存储基础检查](testing-plan.md#已实现的存储基础检查)。新增普通步骤只跑选定组件，不恢复每 PR 全 workspace Rust。真实 KVM 把中心和 Redis 计入原资源预算、准入与独占，不能省略内部鉴权、直连本地函数或取消他人任务。只读预装模板可按合同复用，每轮账本与工作盘独立。

按实现批次切换，不等整个 #292 完成才修改测试。未接入生产入口的组件先在开发环境执行基础/定向检查，现有普通与两题检查继续验收现役链路，不将旧链路绿灯记为双服务通过。真实 Redis 步骤启用前，先制备和实测固定依赖的隔离来宾，再接入普通 SDK 任务；缺材料仍失败，不以动态 skip 或探测到旧版本就回退来过渡。

公开入口切换批次须同时迁移 SDK 网关组合测试、模板构建/系统测试夹具、产物制备及 KVM 候选运行/报告合同，删除被替代的启动路径；不能先启用中心再让正式测试继续访问旧服务。唯一服务命令为 `initialize|serve|audit --config <受保护配置>`；宿主额外保留内部 `relay`，两个产物的 `contract-versions` 不读取配置。系统夹具显式区分中心故障、宿主故障和 Redis 故障，SDK 只连接中心。宿主离线审计明确停止该宿主后，从原收件记录得到全局→本地映射；中心离线审计先停止中心、持原写者租约并读取已校验业务信封，不绕锁读取原始 Redis/SQLite 值，也不从 SDK 编号后缀猜 VM 身份。丢失创建回执的诊断关联只比较原测试意图的元数据摘要，不导出用户元数据，也不把缺席记录当作已清理。

题目收尾的运行身份恢复循环，在每轮中心离线审计前先等待原服务的新认证健康回报，让上轮重启后的缓存恢复和终态确认继续推进；等待同时受原恢复绝对截止时间和原缓存下载期限限制。健康回报只允许继续审计，不能替代双方持久终态及物理清理证据，也不改变原题目失败结果。

固定双向证书按实际节点独立配置：仅运行宿主的两题档位使用一份宿主身份；通用构建档位的运行宿主与构建宿主使用不同叶证书及私钥，分别登记到原节点身份，不能让同一证书代表两个节点。每个宿主拥有独立、绑定原池命名空间的模板缓存及排他锁；中心模板副本、Redis/AOF、服务材料与日志在同一物理部署预算中显式登记独立根和所有者，不藏入文件系统开销，不与构建仓库重复计费。固定两题档位的总启动空闲要求仍不超过 200 GiB，并包含原两倍余量；通用构建使用其独立批准的完整包络，不套用两题上限，实际空闲和原 Rust 激活检查始终保留。`maxmemory` 不是 AOF 磁盘上限；本批两题必须记录真实峰值，生产长期重写与磁盘边界不能由这一轮短验收背书。

实现、测试脚本和对应工作流先在开发环境验证，再随同一批 PR 推送。macOS 可移植检查不代替 Linux 完整检查；真实双服务/KVM 手动验收使用批准的精确候选和隔离 Linux 主机，不能要求开发者笔记本完成所有测试。普通四项检查名称、权限与晋升门槛保持，中心、Redis 和节点的实际验收范围分别报告。

监督器安装是独立受控步骤，不能靠合入 YAML 自动更新宿主工具。新生产入口候选必须由理解其双服务产物/配置/报告合同的新监督链验收；未安装或合同不匹配时阻塞晋升，不让旧监督器仅跑原服务后回写成功。新版手动验收通过后按下面规则切换唯一监督链，随后再发起正常两级晋升；详细旧入口退出判据见[验收清单](testing-plan.md#53-旧公开入口退出验收)。

部署双服务监督链前，必须批准精确代码及配置，并实测同一候选的真实成功、故意失败、取消和精确恢复；源码合入不代替安装或实机验收，切换证据只记录在关联 PR/issue。旧门槛在此之前保持，不产生两个竞争监督器。自动晋升、原 App 身份/检查名/提交与目标基线约束，以及受控命令行手动入口保持。测试用例和单机/多机验收边界统一见[中心与宿主验收](testing-plan.md#5-中心与宿主验收组合验收待完成)，CI 附件保存结果，不回写动态文档。

### 可信 KVM 端到端监督与晋升门槛

Rust envd 的受控验收阶段（#311）：

同一[监督器](../tools/ci_e2e_supervisor.py)可显式配置 `rust_envd_acceptance`，在原 DK 组之后、原 Harbor 题集之前运行[来宾验收入口](../tests/system/envd_acceptance.py)。这不是普通 PR root runner，也不切换产品默认 Go 模板；旧配置不发布 Rust envd 成功结论。已运行任务仍使用原冻结配置，不在途中追加或移除该阶段。安装与实跑结果须绑定精确候选，源码合入不能代替宿主受控安装。

该私有对象的唯一字段由[验收策略](../tools/envd_acceptance.py)校验：`configuration`、`policy_template`、`oci_archive`、`go_rootfs`、`builder_rootfs`、`budget_profile` 是审核后登记在原 `host_assets` 的只读材料；`tls_material` 指向本阶段独立的中心、运行和构建节点证书/密钥目录，每个材料同样登记原摘要，不更换现役单节点两题的证书或复用同一节点叶子。另显式提供原 `registry_limits`、`build_limits`、`data_transfer`，不从题名推导或自动扩大预算。配置不含 App 密钥。阶段的 `budget_profile` 必须独立声明原服务 CPU/内存预算，不从现役 Go 组继承，不给 DK 或原题集增额；例如已有 Rust 构建配置需要 2 vCPU，而现役 Go 监督组只有 1 CPU，不能将两者混用。不同阶段沿原宿主租约串行执行，缺失、损坏或未批准的阶段预算立即拒绝。`toolchain_bin` 中的 rustc/cargo 必须是同一固定版本的实际原生文件，不能用 rustup 代理或符号链接替代来宾打包器要求的独立编译器指纹。制备沿用原离线 Rust 来宾工具，输出绑定同一源码的新清单，只将批准配置中的 worker 身份替换为真实新产物，保留原数值、路径及版本检查。固定 OCI 输入在原私有构建 VM 内转换并经原中心发布/实际启动验证，不在宿主运行容器构建或把旧镜像重标为新源码。

阶段复用原双端 SDK、stdin、PTY、命令/RPC/文件期限及文件权限用例；补充丢 Start 回执、服务重启/旧 PID、来宾文件系统写满、慢输出、登记回收及独立寿命清理。真实结果还核对实际中心/宿主执行清单、Rust 服务/worker/配置身份、每组原终态和物理残留、服务 cgroup 收尾。完整固定清单缺项、错误候选、非零退出、未知或清理失败均不能进入后续题集或发布绿灯；启动意图先持久化，丢派发回执不再启动一轮。原两题、评分、App 身份及分支保护保持，普通 CI 仍不持有宿主权限。

失败或取消仍保留失败结果与原始证据。只有同候选的 VM、服务目录和空服务 cgroup 都完成实际清理，且原执行清单、退出及回执全部核对后，监督器才停止本轮单元并释放本轮普通 CI 暂停；以已结束但未通过的状态终结，允许后续新候选正常验收。恢复不会重跑同一失败身份或启动其后续 Harbor。任何身份、退出或清理未知仍保持阻塞，等待精确审计，不因普通作业排队而强制忘掉资源。

受控安装必须先在同一候选实测成功、真实失败和取消/精确恢复，再启用该宿主配置。默认 Go envd 切换属于验收通过后的独立交付，不能借该阶段提前更换模板。采样与有限压力是工程证据，不表示任意负载内存证明或整个 E01–E10 自动完成。

[监督器](../tools/ci_e2e_supervisor.py)、[准备工具](../tools/ci_e2e_prepare.py)、[服务单元](../tools/ci_e2e_supervisor.service)与[私有配置示例](../tools/ci_e2e_supervisor.example.json)已实现；宿主安装与真实结果回传须以对应 issue/PR 的实测证据为准。当前通过[2.0 兼容题集](../benchmarks/terminal-bench-2.0-suites.json)回归，[2.1 原题配置](../benchmarks/terminal-bench-2.1-suites.json)保留为发布前待办；判据以[验收清单](testing-plan.md)为准，支持完整题集不等于已通过。

管理服务使用 root 受控且满足仓库 Python 版本要求的解释器；独立候选准备单元复用同一解释器，忽略 Python 环境变量和用户包。可以安装在独立虚拟环境，不要求替换宿主系统 Python；候选源码和离线构建依赖仍分别按原配置核验。

不新增 root GitHub runner，不执行外部 PR 宿主代码或 `pull_request_target`。监督程序、配置、任务来源和工具均由 root 受控安装；自动晋升模式须显式启用，只从固定仓库读取受保护 integration/test/main 的精确引用，接受 integration→test、test→main 及既有 main→test 同步，不接受任务分支、fork 或 PR 自带命令。候选必须包含当前目标基线；已经进入目标的源版本不重复执行。目标独有变更需要先通过正常同步 PR 合入源分支，不能只测源版本而忽略最终组合。未满足历史／普通检查的方向保持阻塞，但不阻止另一个合法且已就绪的方向；服务不主动创建或合并同步 PR。最终合并依赖严格保护防止目标更新竞态。配置和编译产物绑定原运行，重启不能改用新配置或重跑未知工作。

普通补充服务与 KVM 服务使用同一准入锁；自动晋升先等待精确候选的四项普通检查完成，核对宿主配置 `ordinary_check_app_id` 对应的最新真实结果，不接受旧成功覆盖新排队／失败或其他 App 的同名检查。没有就绪候选时不占用验收身份、不暂停普通 CI，GitHub 必需 E2E 检查仍待返回。普通检查成功后才发布 E2E 检查并再次核对，KVM 创建自己的暂停标记，等待全部普通任务及未知占用退出，再独占。准备/批次由独立 systemd 单元执行，管理服务重启不停止它们；准备完成后固定实际中心、宿主、窗口工具摘要与协议/业务信封/宿主格式。执行清单另外绑定全部角色目录身份、配置摘要、实际 PID/启动时钟、固定 Redis、证书及完整预算；通用双池和助手不能缺项。恢复汇总时复核候选/格式/服务边界，不能混入旧或不同候选的已回收成绩。按配置大小分批串行，精确收尾确认和脱敏结果持久化后才按原目录设备/inode 回收临时盘，不能宽泛删除他人资源。清理或单元身份未知时保留占用，恢复按原资源核对，不盲目新建。

预装题目在 Create 结果未知、来宾预检与评分均未运行时，报告须保留 `create_unknown` 和明确的 `not_run`，不能伪造预检/评分来源，也不能仅因未运行便抹去已核对的原清理。只有原候选、执行清单、存储、物理清理及服务移除回执全部通过，才按失败结束并释放自身租约；任何清理或身份未知仍阻塞。失败批次的原私有根、报告和日志保留，重启按原设备/inode和回执摘要核对，不重放创建。汇总同时检查实际任务状态与成绩，批次成功标志不能把未运行项变绿；通过项仍须完整原来宾预检与评分来源。

宿主私有配置 `dataset` 选择 `terminal-bench@2.0` 或 `terminal-bench@2.1`，锁/题集配置按版本加载，源码仍须匹配固定提交。2.0 的 `task_registry` 指向固定 Harbor registry 原始文件，须在 `host_assets` 登记摘要；2.1 默认使用仓库已有 registry。省略 dataset 仅为恢复原已安装 2.1 配置。`selection` 选择 `profile`（`smoke`、`regression` 或 `full`），或唯一显式 `tasks` 名单；`batch_size` 控制每批保留数量。2.0 题集的 `oracle_modes` 显式登记既有修补并核对原解答摘要，遇到不同模式拆批，不把修补用于 2.1。题集规范摘要写入 `selection_sha256`，配置改变产生新验收身份；在途运行按原配置恢复。自动模式只使用宿主批准配置，参数不授予额外资源。

手动入口为同一监督器的 `--candidate <批准的完整提交> --base <目标完整提交>`；可加 `--profile full --batch-size 4`，或重复 `--task <准确题名>`。通过带 `LoadCredential` 的受控 systemd 单元调用；不在 shell/仓库保存令牌。`--local-only` 不回传 GitHub 状态。唯一自动入口使用 `--follow-promotions`，私有配置明确批准 `auto_promotions=true`、固定仓库和 `promotion_floor=<已审查门槛实现的完整提交>`；只接收该最低版本之后的受保护分支，避免首次安装时执行旧 test。旧 `--follow-test`／`auto_test` 已退出候选源码，旧配置明确拒绝，不自动升级或回退。自动模式不接受命令行改题集、手动候选或 `--local-only`。

两级晋升规则由[开发指南](../CONTRIBUTING.md#5-github-配置)维护，两题预装环境的题集、判据与扩展验收范围由[验收清单](testing-plan.md#4-通用模板与-terminal-bench)维护；专用 App 的两题门槛已接通，部署证据留 #14，不在本页维护另一份进度或旧门槛。结果注明原题/兼容/预装环境、评分启动变体和实际范围；普通任务 PR 不跑真题。test/main 的端到端检查绑定专用 GitHub App 的 ID，运行中阻塞、真实成功后才放行；integration 的保护不增加真题门槛。手动覆盖使用 `/ diagnostic`，不能满足正式门槛；人工换题须独立身份，原超时不能改成成功。GitHub 页面手动入口仍未接通，受控命令行入口保留。

新双服务监督配置必须显式提供固定 `dk_rounds=6`，故障组还检查它严格超过实际四个保留位置。六轮用于在原 600 秒存活时间和逐轮 60 秒保留期内验证位置复用，不调高寿命或容量来容纳更多轮。`dk_checkpoint_tail_inputs` 同样必填（16～128，示例 128），在全新配置首次初始化前交给原维护策略，使有限场景确实越过声明的检查点触发条件；不改生产维护算法，也不靠空闲等待或删增长断言造通过。故障摘要只附有效整数 HTTP 状态（缺失仍为未知），不输出 SDK 异常正文。中心原等待与 Redis 查询失败另有每进程各最多 64 次输出尝试的固定阶段/错误类别及数值时间诊断；不输出请求、身份、令牌、路径或 Redis 错误原文，输出失败不重试，也不改变期限、围栏或返回值。故障组仍受原 7200 秒总期限约束，按同一配置摘要记录循环、采样、检查点输入界和原镜像/预算；它与两题共享原候选，但有独立的新测试数据和精确资源身份。`rootfs` 是该受保护配置批准的基础盘；两题预装档位的实际题目盘另由 `ci_fixtures` 固定，不能为了故障测试暗中替换题目盘或提高磁盘额度。非 root 角色的暂存父目录及祖先必须可遍历；不能放在 root 私有运行目录之下，具体角色子目录仍各自保持 0700。

给现有专用 App 增加 Checks 写入须由 owner 更新 App 及安装授权；私有仓库的自动源码获取另需 Contents 只读。普通执行器令牌仍仅请求 Actions 只读、Administration 写入、Metadata 只读，不自动获得 Checks 或 Contents 权限。E2E 检查客户端独立请求 Actions 只读、Checks 写入、Metadata 只读，不带 Administration；源码客户端仅请求 Contents/Metadata 只读。源码令牌仅进入一次 Git 网络调用的私有环境，不写入 argv、Git 配置或检出目录；不借用个人凭据。App 私钥只进入管理服务的 systemd 凭据目录，不进入独立准备/批次单元、来宾、产物或报告。原检查 ID 与回写意图先持久保存；丢终态回执只重试同一检查，不重跑题目。未授权 Checks 时只能执行 `--local-only`，不能称自动检查已回写。

安装前审查源码及批准配置、保留原 CI 文件恢复副本，验证单元；只重启管理服务，不停止在途工作。门槛按 owner 授权启用并通过正常晋升 PR 实测，安装和通过证据记录在 #14。单次安装不代表永久运行的缓存/历史保留已验收；未知资源由管理员核对，不自动忘掉。不加入绿色占位工作流，不通过移除必需检查合入失败版本。
