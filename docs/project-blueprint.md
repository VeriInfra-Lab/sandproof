# Sandproof 项目蓝图：有状态沙箱的可靠卸载与恢复

[文档目录](README.md) · [开发规则](../CONTRIBUTING.md) · [总计划 #1](https://github.com/VeriInfra-Lab/sandproof/issues/1)

本页是产品范围、版本基线、分工与交付目标的权威入口。2026-10-21 调整第一阶段目标：在管理服务崩溃、请求重试和并发操作下，沙箱从运行到卸载、再恢复时，状态不静默回退，执行资格不重复，恢复材料不被提前回收。交付真实系统、对指定 Rust 的条件证明和可复现实验。

日常开发以 `integration` 为集成基线，`test`、`main` 通过晋升 PR 更新；不再依赖已删除的 `stage1` 工作分支。分支名不代表功能或证明完成。认领任务时固定实际提交、所需函数与接口；已有组件、实机成绩和局部证明仅按[覆盖记录](proof-coverage.md)中的适用版本复用。

## 1. 第一阶段范围

| 项目 | 必须交付 | 明确限制 |
|---|---|---|
| 拓扑 | 一个有效中心写者、权威 Redis、一个固定 Linux/KVM 宿主及其 SQLite；多会话、至少两个用户 | 保留真实中心→宿主网络链路；不要求多宿主、动态发现、迁移或中心高可用 |
| 生命周期 | 创建、显式暂停并卸载、同宿主恢复、销毁、授权操作结果查询 | 同一逻辑会话恢复为新的运行代；不是冷启动替代，也不是只冻结仍占运行名额 |
| 恢复状态 | 全量内存、VM/设备状态、同一次冻结期间匹配的私有磁盘及完整 manifest | 本地受保护、自包含文件；File 内存后端，先加载为暂停状态；无增量链、UFFD、压缩或对象存储 |
| 资源 | 卸载后旧 VMM 退出并释放可复用运行位置；恢复材料和逻辑会话继续记账 | 材料仍被运行 VMM 使用时不能回收；准入同时预留正常转换及失败收尾余量 |
| 重试 | 客户端首次发送前已知操作键；全量请求绑定、结果查询、有界保留和过期拒绝 | 旧无键 SDK create 保持既有语义，不承诺对它提供恰好一次创建 |
| 访问 | 按用户、会话、当前运行代检查；暂停/终止关闭新访问并排空相关效果；恢复重新授权 | 不承诺旧 TCP/vsock 连接连续，不证明完整来宾命令/文件协议 |
| 时间 | 暂停、卸载、恢复均不重置会话总寿命；到期进入终止协议 | TTL 不直接删除文件；是否续期仍受原总寿命上限约束 |
| 故障 | 中心/宿主管理进程独立重启、消息丢失重复乱序、提交未知、部分文件写入、资源不足、destroy 竞争 | VMM/内核可能继续运行；不保证任意 VMM 死亡后的 RAM 恢复，不覆盖断电/盘损坏/恶意管理员或历史回滚 |

保留原冷启动模板作为初始环境；模板构建、OCI/镜像转换和模板平台仍采用工程测试和明确输入合同。**新的运行态快照管理、恢复资格、清理决策属于本项目必须证明的业务，不能套用模板子系统的排除条款。**

现有 get/list 全部投影、完整 Rust envd、两执行保密、所有队列/日志的长期容量、完整云平台与多宿主证明后置。阶段配置须禁止未纳入功能改变本阶段资源；若共用模块仍可运行，须证明它对生命周期状态和资源的修改范围。已有兼容/安全检查保留，缩小论文证明目标不等于删除产品检查。

## 2. 版本与既有工程基线

固定 Firecracker/jailer `1.16.1`、CPU/内核/设备组合及内存后端；每次实测记录实际二进制、镜像、配置和文件系统指纹。既有兼容基线如下，阶段收缩不擅自升级版本或将旧成绩迁记为新恢复功能通过。

| 项目 | 调研版本 | 用途 |
|---|---|---|
| E2B Python SDK 2.51.0 | `ccaf9fc0ffe6ac39c7ec786af7608ab1de19467b` | 选定同步/异步调用、接口、错误及生命周期行为依据 |
| E2B runtime | `f455fd58fa3f289e78ce1de690c35968d8d29322` | 运行方式、envd 和外部操作参考 |
| Harbor | `31668af15560fb50a9d0584816d12726036656cf` | E2B 接入及评测需求依据 |
| Terminal-Bench 2.0 / 2.1 | 当前 2.0 `69671fbaac6d67a7ef0dfec016cc38a64ef7a77c`；发布前 2.1 `c5ee500c185224c97cd6caff7866a990a0057f41` | 独立完整锁各含 89 题；当前兼容回归按配置选题并显式登记解答修补，不回退固定 base 配方；[锁与范围](../benchmarks/README.md) |
| 本项目 Firecracker/jailer | `1.16.1` | 已用于局部 Linux/KVM 实验；仍须按测试提交和摘要判断覆盖 |
| Rust / Lean | 仓库工具链文件 | 固定版本；变更须独立评审和回归 |

M0 由 C 记录客户端精确包版本、锁文件及 Harbor 源码版本；B 记录宿主、内核、rootfs、envd、Firecracker/jailer 和运行配置指纹；A 记录存储格式和协议版本。Harbor 联合依赖锁、任务 ID 与内容哈希归 #13 的评测准备，不阻塞 M0 合同冻结。版本只可通过有原因、有回归证据的 PR 升级，不能跟随上游 `main` 自动漂移。当前冻结 2.0 兼容回归，逐题修补留在评测层，不进入控制器或核心证明；历史跨版本成绩不能算新候选通过。2.1 原环境/原解答全量验收及逐项撤销本地补丁为发布前待办，2.0 结果不迁记为 2.1 通过。题集、构建来源与批次大小仍由批准配置选择。


## 3. 模块和交付顺序

继续使用轻中心、重宿主架构。中心管授权、固定绑定、全局预留和意图；宿主管本地执行资格、SQLite、实际快照及精确停止/回收。Redis、SQLite、文件目录和 VMM 不共享原子事务。组件安排见[系统架构](ARCHITECTURE.md)，状态及失败语义只在[模块合同](module-contracts.md)定义。

| 角色 | 范围 | 对应证明责任 |
|---|---|---|
| A 控制与持久化 | 中心纯决定/Redis、本地状态/SQLite、操作窗口及预算 | V1、V2、V4、V5 |
| B 执行与隔离 | 实际捕获/磁盘封存、加载/激活、原 VMM 身份、文件 pin 和回收 | V6，与 V5 共定持久接口 |
| C 接口与集成 | 请求键、协议/收件、授权查询、两端访问、固定实验 | V3、V7、V8、V9 集成 |
| 共同基础 | 只补本阶段真实调用需要的类型、序列化、并发/存储/OS 合同 | V0 内的 T0–T9 验收点 |

A/B/C 是职责占位符，实际认领在 issue；不宣称已分配给具体人。V0–V9 是责任模块，不是十个顺序阶段，也不另设 stage issue。

交付顺序：先固定 V0 最小公共合同与 V9 不变量；用真实 create→unload→resume→destroy 路径检查可行性；随后围绕暂停交接、恢复唯一资格、材料回收三个切片，每片同步交付必要业务实现、对应证明和故障实测；最后组合条件完成性和整套实验。保留原 create→丢回执→恢复→销毁作为基础用例，不再以它代替第一阶段闭环。不得等待所有通用库完工才接真实链路。

## 4. 系统论文要回答的问题

研究假设是：把活状态交接、唯一恢复资格、持久材料引用和真实资源回收放进同一可检查协议，能够在管理服务重启和不确定结果下，同时保住状态、安全释放资源，并支持正常恢复。贡献必须落在实际 Rust 到模型的连接、跨层不变量和故障证据上；不是“用了 Lean”，也不是已有快照、日志或代次概念本身。

现有工作提供不同基础：[Firecracker](https://www.usenix.org/conference/nsdi20/presentation/agache)提供专用 microVM 机制；[Catalyzer](https://ipads.sjtu.edu.cn/pub/projects/catalyzer)和[REAP](https://arxiv.org/abs/2101.09355)重点研究启动/恢复性能；[GoJournal/Perennial](https://www.usenix.org/conference/osdi21/presentation/chajed)研究并发崩溃安全存储验证；[Sabre](https://www.usenix.org/conference/osdi24/presentation/lazarev)及[Spice](https://www.usenix.org/conference/osdi26/presentation/holmes)提供快照实现/恢复优化的比较背景。这些来源用于定位研究问题，尚不能据此宣称首次解决或优于全部既有方案。

论文至少给出：正常状态连续性实证、关键故障窗口与错误实现对照、实际资源释放/长期引用成本、端到端暂停恢复延迟及证明/可信代码规模。性能比较固定硬件/镜像/工作集，分冷/热缓存，不预设速度收益；不能仅比较一个纯控制函数。如果最终只剩常见日志/代次机制加一组模型证明，系统贡献可能不足；应以跨层故障反例、真实代码连接、可检查的组合不变量以及资源可用性证据检验研究假设。E2B 的固定源码缺陷、本地模拟候选和公开云服务分开；没有独立实证不声称在线服务存在漏洞。详细实验仅在[验收清单](testing-plan.md)维护。

## 5. 完成含义与扩展

完成要求[验证总览](formal-verification-design.md)的 LC-G1–LC-G6 在声明前提下成立、实现连接闭合，并通过相应实机矩阵。只证明永远拒绝请求、只验证模型或只通过一次正常演示都不达标。

未来可以在明确版本接口后扩展增量快照、异地恢复、自动暂停、fork 和多中心，但须重新证明捕获来源、唯一执行和引用回收条件；第一阶段不预造通用平台。会话/运行代/捕获/操作身份与物理位置分离，为扩展留下明确接口。

项目进度见 #1 与新的 V0–V9，历史 M0–M5、旧证明 issue 及其证据保留在 Git/GitHub 历史。开发与发布门槛仍按[开发指南](../CONTRIBUTING.md)，本次范围调整不放宽 CI 或安全检查。
