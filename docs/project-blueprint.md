# Sandproof 项目蓝图：E2B 核心兼容沙箱

[文档目录](README.md) · [开发规则](../CONTRIBUTING.md)

范围确认：2026-09-30（更新通用模板路线与证明排除边界）。当前阶段：V1 功能开发，不要求新增功能同步完成形式化证明。

本文件是 Sandproof 当前范围、分工和验收的入口，与 [GitHub 总计划 #1](https://github.com/ningZhang-cs/sandproof/issues/1) 共同落实“先跑通，再集中证明”的开发顺序。研究安全目标保留，逐功能同步证明改为功能验收后集中证明；旧方案只保存在 Git 历史，不再在当前目录维护平行计划。

## 1. 固定目标和版本

交付单台 Linux/KVM 主机上的多用户、多沙箱服务，直接管理 Firecracker/jailer，在明确的功能子集内兼容固定版本的 E2B 客户端和生命周期语义。先完成真实运行、兼容性、故障和 Terminal-Bench 评测，再对安全关键 Rust 实现补齐 Lean 对应证明。最终研究版本包含暂停恢复；V1 可以先不实现。

V1 只围绕 E2B 的固定核心子集，不切换到其他隔离引擎，不承诺完整复制 E2B 云产品，也不以测试通过宣称整个系统已经形式化验证。

已有纯核心成果基线：`0f1901a210e24da50d259e07df75e8c2cb9d181f`。已有协议和 Rust 对应证明只适用于其明确覆盖的代码、输入和前提。旧的只读输入盘、自定义通信与结果导出原型已移除；此后新增的持久服务、兼容入口和 Firecracker 运行层已打通显式禁网及选定公网/静态 IPv4 的真实 SDK 场景，不表示完整 V1 或新增模块证明已完成。组件关系见[系统架构](ARCHITECTURE.md)，具体实验覆盖见[验收清单](testing-plan.md)，进度仍在对应 issue/PR 维护。

选定源码与客户端版本如下；具体测试机产物和证据层级见[版本基线](../references/v1-baseline.json)，不把不同批次的局部实测拼成一套已验收发布组合：

| 项目 | 调研版本 | 用途 |
|---|---|---|
| E2B Python SDK 2.51.0 | `ccaf9fc0ffe6ac39c7ec786af7608ab1de19467b` | 选定同步/异步调用、接口、错误及生命周期行为依据 |
| E2B runtime | `f455fd58fa3f289e78ce1de690c35968d8d29322` | 运行方式、envd 和外部操作参考 |
| Harbor | `31668af15560fb50a9d0584816d12726036656cf` | E2B 接入及评测需求依据 |
| Terminal-Bench 2.0 | `69671fbaac6d67a7ef0dfec016cc38a64ef7a77c` | 固定 Harbor registry 的全部 89 题；[逐文件锁与本地审计](../benchmarks/README.md) |
| 本项目 Firecracker/jailer | `1.16.1` | 已用于局部 Linux/KVM 实验；仍须按测试提交和摘要判断覆盖 |
| Rust / Lean | 仓库工具链文件 | 本轮不升级 |

M0 由 C 记录客户端精确包版本、锁文件及 Harbor 源码版本；B 记录宿主、内核、rootfs、envd、Firecracker/jailer 和运行配置指纹；A 记录存储格式和协议版本。Harbor 联合依赖锁、任务 ID 与内容哈希归 #13 的评测准备，不阻塞 M0 合同冻结。版本只可通过有原因、有回归证据的 PR 升级，不能跟随上游 `main` 自动漂移。

## 2. V1 功能边界

“兼容”指清单内的客户端调用、正常行为及已约定错误；启动速度、吞吐和云规模不要求等同于 E2B。不支持的请求必须明确拒绝，不能忽略参数或返回假成功。

| 编号 | V1 交付 | 必须说明的语义 |
|---|---|---|
| F01 | create、连接运行中的沙箱、get/list、kill | 按已授权的模板修订创建，保留默认 `base`；创建支持约定的环境变量和元数据；查询/列表支持 SDK 的分页、筛选和排序；销毁完成须有真实停止证据 |
| F02 | 沙箱寿命、续期、到期销毁 | 创建/连接省略寿命默认 300 秒；connect 只延长；set_timeout 从当前时刻重设；从启动起算总寿命上限；到期 kill |
| F03 | 重复使用同一沙箱执行命令 | 工作目录、环境变量、用户、后台执行、等待、输出、退出码、命令超时与终止 |
| F04 | 运行期间基本文件输入输出 | 至少满足选定 E2B 接入所用的读、写、列目录、建目录及文件传输；输出不得越界写入宿主 |
| F05 | 每个沙箱独有的可写系统环境 | 能安装依赖、修改自己的系统目录；共享基础镜像不可被写坏，不实时挂载宿主目录 |
| F06 | 通用模板构建与管理 | 用户提交 Dockerfile 和构建上下文或公开 OCI 镜像，经复用开源构建/转换工具获得可启动的不可变模板；支持多个软件环境与有界资源形状；不按题目名称增加产品逻辑 |
| F07 | 鉴权、多用户、多沙箱及资源限额 | 所有命令、文件和管理请求检查归属；受控 CPU、内存、磁盘及并发；保留收尾空间 |
| F08 | 受控网络 | 省略联网参数默认允许公网出站，但始终受平台禁区约束；支持显式禁网及原 SDK 提交的静态 IPv4 允许/拒绝规则；规则优先级写入兼容清单 |
| F09 | 持久记录和故障恢复 | 提交后派发，丢回执为未知，重启后核对真实资源；销毁和清理可重试 |
| F10 | 可复现的兼容和评测入口 | 固定客户端、配置及 Terminal-Bench 2.0 全部 89 题；同一接入分别运行我们的服务和 E2B 基线；缺能力、失败和未运行的题仍保留在完整报告中 |

F08 的公网 IPv4 与静态 IPv4 规则已在显式开启的隔离部署中接通并完成选定实机测试，包括一条宿主预检可通的真实公网 TCP 路径；默认部署配置仍关闭公网能力，通用互联网和完整 S10 尚未验收。V1 不承诺运行期间切换网络模式、域名/SNI 策略、IPv6 放行、任意公网服务端口发布；需要这些能力的任务事前标为不支持。命令/文件管理通道仍需可达并经过鉴权，不能把“用户程序禁网”实现成管理通道也不可用。

DNS 本身也是出站通道：禁网不得通过宿主解析器间接查询外部域名；静态 IPv4 规则不自动开放公共 DNS。来宾可修改自己的解析配置，但不能改变宿主强制的网络权限。普通公网模式的通用 DNS 通过统一部署/模板配置支持并单独验收，不靠每题临时修改；禁网/受限模式只能使用其策略明确允许的路径。按域名授权和查询内容过滤仍后置；仅固定 DNS 服务器地址不等于限制查询内容。

### 长期运行的容量目标（2026-10-02 owner 确认）

#99 增加现有状态机内的维护操作，采用 SQLite 检查点、满足前置条件的历史退休、永久身份与有限物理位置分离，以及自助构建的服务端请求窗口。活跃对象、未知工作、保留结果和模板都有显式条数/字节额度时，反复创建销毁应保持在线存储和登记有界；旧命令、回执及过期请求不能作用于新实例。保留期内的结果不得为新请求提前驱逐，接受时须留下未来收尾额度。未知外部结果永久不解除时可以拒绝新工作，不承诺无限接单；有限身份空间耗尽仍拒绝而不复用。保留时间、额度和位置数量是显式部署参数，不采用测试数值作为生产默认。

当前交付从纯核心基础分批推进，尚未启用生产历史删除或宿主复用；实机验收由 owner 后续运行。接口和迁移语义仅在[模块合同](module-contracts.md)维护，证明义务仅在[覆盖记录](proof-coverage.md)维护；不另写平行清理控制器，不扩大模板子系统的证明范围。

### 模板路线及验证边界

2026-09-30 的 owner 决策替代此前“固定 base＋逐题人工初始化”的最终产品路线；旧实验可保留为诊断资料，不是通用模板链交付。默认 `base` 是预置模板之一，普通用户不应为更换软件环境逐题请求管理员重启服务。

[#123](https://github.com/ningZhang-cs/sandproof/issues/123) 交付隔离的自助构建、转换与模板入口；[#6](https://github.com/ningZhang-cs/sandproof/issues/6) 交付可启动产物和多模板私有运行盘，[#9](https://github.com/ningZhang-cs/sandproof/issues/9) 核对资源准入与构建/运行预算，[#13](https://github.com/ningZhang-cs/sandproof/issues/13) 使用同一通用链路接入原任务环境。首版支持 Linux x86_64 的 Debian/Ubuntu 兼容镜像，冷启动即可；不复刻 E2B 的快照加速和完整模板平台。Dockerfile 多阶段由标准构建器处理，不自行解释。CPU/内存/磁盘在模板构建/注册时由用户选择并经准入校验，创建选择模板；不虚构固定 SDK create 没有的资源字段。总磁盘容量与构建后最小空闲空间分别记录，不把整个产品限定为题集的 10 GiB。

**模板子系统整体排除在形式化证明外**，包括第三方构建器、Dockerfile 执行、OCI 拉取/解包、镜像转换/制备，以及自有构建编排、模板登记/别名/查询/发布代码；采用工程测试验收。构建输入不可信，隔离、鉴权、限额、路径检查和失败收尾仍必须实现。核心证明以外部提供正确授权、不可变修订、摘要/资源清单正确且可启动的模板描述为显式条件；该合同不是已证明事实。核心实例身份、准入、生命周期、撤销、回执、恢复和精确停止/清理仍保留为后续证明目标；不宣称镜像供应链或整个沙箱全部已验证。准确状态只在[覆盖记录](proof-coverage.md)维护。

暂停、恢复、到期暂停和流量唤醒属于后续完整生命周期阶段。独立快照产品接口、fork/clone、多节点、高可用、共享卷、完整 POSIX/ACL 证明、动态域名策略、桌面和 GPU 不进入 V1。提供 E2B 式暂停恢复时内部必须保存内存和磁盘，不能用重启冒充恢复。

V1 使用 E2B 式运行期间文件接口，不恢复旧的启动前只读文件夹导入方案，也不增加“所有用户文件操作只能发生在一个工作目录”的限制来换取容易实现。

## 3. 三人模块划分

A/B/C 是岗位占位符，不是 GitHub 用户名。实际认领后，在任务板和本表填写人员；不生成含无效用户名的 CODEOWNERS。

| 负责人 | 模块与建议目录 | 自己交付的内容 | 主要复核者 |
|---|---|---|---|
| A：控制与恢复 | `controller-core/`、`controller-service/` | 唯一控制决策、事务记录、任务派发、授权判断、寿命、配额、恢复调度、状态发布 | B；接口变化另请 C |
| B：节点执行与隔离 | `sandbox-node/`、`sandbox-runtime/` 及镜像/部署工具 | jailer 启停、资源身份观察、独立磁盘、envd 接入、隔离构建与镜像转换、命令/文件传输、网络、真实停止及清理 | A；客户端行为另请 C |
| C：接口与集成 | `sandbox-api/`、`sandbox-server/`、`tests/compat/`、`tests/system/`、`.github/`、`benchmarks/` | E2B API 和访问网关、模板用户入口、SDK 兼容、Harbor 通用环境适配、系统测试框架及 CI | A；运行环境另请 B |

目录存在不代表工作包已完整交付。共享消息位于 `sandbox-protocol/`；`sandbox-server/` 的跨模块组装由 C 集成、A/B 复核各自语义。新增 crate 只在对应任务中加入 workspace。

每个人都写自己模块的单元、组件和故障测试。C 维护公共测试入口和结果汇总，不替 A/B 承担所有测试，也不单独判定安全语义。

交叉边界必须遵循 [模块合同](module-contracts.md)：

- C 解析请求并验证凭据，A 检查操作权限及当前状态，B 在实际执行前再次检查资源和代数；不能仅在 HTTP 入口检查一次。
- A 是沙箱业务状态的唯一写入者；B 返回动作观察和回执，不自行发布 Running/Destroyed；C 不另外维护生命周期。
- A 负责恢复决策，B 负责可靠发现和控制资源，C 负责用系统测试验证两者组合。
- A/B/C 分别为后续控制证明、执行合同证明、接口授权与对应验证负责；形式化阶段沿用模块归属，不另建一套脱离运行代码的实现。

## 4. 开发里程碑

里程碑按可运行能力划分，不以完成文件数或代码行数计进度。

| 里程碑 | 模块协作交付 | 退出条件 |
|---|---|---|
| M0：共同合同 | A 定状态/持久化，B 定执行/观察，C 定客户端/测试清单；范围由 owner 确认 | 共享合同与测试样例可执行；版本和不支持项记录齐全；最小真实 SDK/VM 闭环有对应证据；不以三人共同批准或完整 Harbor 评分为前提 |
| M1：第一条真实闭环 | 创建 → 执行 → 上传下载 → 销毁 | 原 E2B 客户端的选定调用在真实 VM 上通过；检查 VM 和文件残留；不是完整 V1 |
| M2：V1 功能与故障 | F01–F09、多用户并发、寿命、重启和竞争 | 兼容清单与必要系统/故障测试通过；未知结果和失败清理可观察 |
| M3：V1 验收 | 固定任务集的标准解答与智能体评测、部署复现 | F10 和测试计划完成；发布支持/差异/未验证清单 |
| M4：完整生命周期 | 暂停恢复及其失败/并发处理 | 单独生命周期验收；不靠 Terminal-Bench 代替 |
| M5：集中形式化 | 安全关键真实 Rust、持久化协调、执行资格和恢复的对应证明 | 完整证明、容量与条件化完成性义务闭合；依赖边界明确 |

M0 后可以并行：A 使用契约一致的假执行器开发，B 用驱动程序验证真实 VM，C 使用同一合同的假控制服务验证 API。假实现只能作测试替身，不成为第二份业务规范。M1 尽早接上三条线，不能等各模块全部完成才第一次集成。
