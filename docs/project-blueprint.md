# Sandproof 项目蓝图：E2B 核心兼容沙箱

[文档目录](README.md) · [开发规则](../CONTRIBUTING.md)

本文件是当前产品范围、版本基线、分工与里程碑的权威入口。目标架构为“轻中心、重宿主”：先固定合同，完成中心/宿主拆分与功能、故障和实机验收，再冻结真实组合提交，推进分模块及系统组合证明。任务进度见 [GitHub 总计划 #1](https://github.com/ningZhang-cs/sandproof/issues/1) 及关联 issue；本页不记录实时进展。

## 1. 固定目标和版本

交付一个统一 E2B 核心兼容入口和多个静态登记的 Linux/KVM 宿主。中心负责用户鉴权、全局身份、资源准入、节点选择、意图与路由，使用权威 Redis；每个宿主保留完整的本地控制、SQLite 持久化、执行、观察、恢复与精确清理，管理 Firecracker/jailer。一个宿主可承载多个用户，同一用户的不同沙箱可分配到不同宿主；同一沙箱的宿主绑定固定，不自动迁移或失联后异地重建。

[#292](https://github.com/ningZhang-cs/sandproof/issues/292) 的第一交付版本在一台物理 KVM 主机上运行中心、Redis 和一个真实宿主服务，进程、账号、目录分离，经双向认证 HTTPS 通信，不用直接函数调用替代网络协议。同仓库构建两个独立服务产物；两台/多台真实宿主验收另立关联后续任务，必须在 #292 关闭前建立。

原本地控制/执行链继续复用；中心纯决策、Redis 协调、内部网络协议及两端网关已有组件实现。#292 交付唯一的中心/宿主产品入口、模板与既有 CI 的完整迁移，工程结论只绑定该候选的实际验收，不将旧单宿主成绩记作新架构通过。有限静态节点、一个有效中心写入者、一个权威 Redis 是当前交付条件，不承诺中心多活、存储自动故障切换或完整 E2B 云平台。

V1 只围绕 E2B 的固定核心子集，不切换到其他隔离引擎，不承诺完整复制 E2B 云产品，也不以测试通过宣称整个系统已经形式化验证。

已有本地纯核心证明按[覆盖记录](proof-coverage.md)中的明确代码、输入和前提复用，不覆盖新增服务或中心。组件关系见[系统架构](ARCHITECTURE.md)，接口和故障语义见[模块合同](module-contracts.md)，工程验收见[验收清单](testing-plan.md)，最终性质与组合方法见[形式化验证设计](formal-verification-design.md)。测试、模型证明和真实实现证明分别报告。

## 2. V1 功能边界

“兼容”指清单内的客户端调用、正常行为及已约定错误；启动速度、吞吐和云规模不要求等同于 E2B。不支持的请求必须明确拒绝，不能忽略参数或返回假成功。

| 编号 | V1 交付 | 必须说明的语义 |
|---|---|---|
| F01 | create、连接运行中的沙箱、get/list、kill | 按已授权的模板修订创建，保留默认 `base`；创建支持约定的环境变量和元数据；查询/列表支持 SDK 的分页、筛选和排序；销毁完成须有真实停止证据 |
| F02 | 沙箱寿命、续期、到期销毁 | 创建/连接省略寿命默认 300 秒；connect 只延长；set_timeout 从当前时刻重设；从启动起算总寿命上限；到期 kill |
| F03 | 重复使用同一沙箱执行命令 | 工作目录、环境变量、用户、后台执行、等待、输出、退出码、命令超时与终止 |
| F04 | 运行期间基本文件输入输出 | 至少满足选定 E2B 接入所用的读、写、列目录、建目录及文件传输；输出不得越界写入宿主 |
| F05 | 每个沙箱独有的可写系统环境 | 能安装依赖、修改自己的系统目录；共享基础镜像不可被写坏，不实时挂载宿主目录 |
| F06 | 通用模板构建与管理 | 用户提交 Dockerfile 和构建上下文或公开 OCI 镜像，经复用开源构建/转换工具获得可启动的不可变模板；支持多个软件环境与有界资源形状；不按题目名称增加产品逻辑 |
| F07 | 鉴权、多用户、多沙箱及资源限额 | 所有命令、文件和管理请求检查归属；受控 CPU、内存、磁盘及并发；保留收尾空间 |
| F08 | 受控网络 | 省略联网参数默认允许公网出站，但始终受平台禁区约束；支持显式禁网及原 SDK 提交的静态 IPv4 允许/拒绝规则；规则优先级写入兼容清单 |
| F09 | 持久记录和故障恢复 | 提交后派发，丢回执为未知，重启后核对真实资源；销毁和清理可重试 |
| F10 | 可复现的兼容和评测入口 | 固定客户端与配置，当前 2.0 兼容回归、发布前 2.1 全量验收；同一接入分别运行我们的服务和 E2B 基线；修补、失败和未运行不得冒充原题通过 |

F08 的公网 IPv4 与静态 IPv4 规则已在显式开启的隔离部署中接通并完成选定实机测试，包括一条宿主预检可通的真实公网 TCP 路径；默认部署配置仍关闭公网能力，通用互联网和完整 S10 尚未验收。V1 不承诺运行期间切换网络模式、域名/SNI 策略、IPv6 放行、任意公网服务端口发布；需要这些能力的任务事前标为不支持。命令/文件管理通道仍需可达并经过鉴权，不能把“用户程序禁网”实现成管理通道也不可用。

DNS 本身也是出站通道：禁网不得通过宿主解析器间接查询外部域名；静态 IPv4 规则不自动开放公共 DNS。来宾可修改自己的解析配置，但不能改变宿主强制的网络权限。普通公网模式的通用 DNS 通过统一部署/模板配置支持并单独验收，不靠每题临时修改；禁网/受限模式只能使用其策略明确允许的路径。按域名授权和查询内容过滤仍后置；仅固定 DNS 服务器地址不等于限制查询内容。

### 长期运行的容量目标

#99 增加现有状态机内的维护操作，采用 SQLite 检查点、满足前置条件的历史退休、永久身份与有限物理位置分离，以及自助构建的服务端请求窗口。活跃对象、未知工作、保留结果和模板都有显式条数/字节额度时，反复创建销毁应保持在线存储和登记有界；旧命令、回执及过期请求不能作用于新实例。保留期内的结果不得为新请求提前驱逐，接受时须留下未来收尾额度。未知外部结果永久不解除时可以拒绝新工作，不承诺无限接单；有限身份空间耗尽仍拒绝而不复用。保留时间、额度和位置数量是显式部署参数，不采用测试数值作为生产默认。

当前显式配置已接通宿主位置复用、单库检查点/终态历史退休、构建请求窗口与有限结果保留；完整容量模式另要求明确的工作流/SQL/数据库/WAL/SHM/检查点预算及 VMM console 丢弃选择。准入保留已接受工作的后续转换和结果额度，构建锚点及模板验证证据按原身份结算后才解除历史引用；模板本身不随构建结果到期删除。正式服务只接受完整容量配置和当前格式，不提供旧库升级、自动导入或静默降级；自助构建未启用时仍可使用预置模板。组件/故障/连续 churn 检查不能代替实机验收、真实题集或形式化证明；宿主可观察性、受管 SQLite 读写者和真实磁盘可用性仍须满足合同。接口和格式拒绝语义仅在[模块合同](module-contracts.md)维护，证明义务仅在[覆盖记录](proof-coverage.md)维护；不另写平行清理控制器，不扩大模板子系统的证明范围。

### 模板路线及验证边界

模板由通用 Dockerfile/OCI 构建链产生，默认 `base` 是预置模板之一；不把所有模板名映射到它，不为每道题增加产品分支。普通用户可在已部署的自助构建服务中选择软件环境与有界资源形状。中心管理归属、别名与不可变描述，产物服务提供受保护的 HTTPS 只读下载；Redis 不存虚拟磁盘正文。宿主有界下载、校验、缓存，实例使用私有运行盘；不要求每次创建都重新拉取产物，也不强制采用云对象存储。

[#123](https://github.com/ningZhang-cs/sandproof/issues/123) 交付隔离的自助构建、转换与模板入口；[#6](https://github.com/ningZhang-cs/sandproof/issues/6) 交付可启动产物和多模板私有运行盘，[#9](https://github.com/ningZhang-cs/sandproof/issues/9) 核对资源准入与构建/运行预算，[#13](https://github.com/ningZhang-cs/sandproof/issues/13) 使用同一通用链路接入原任务环境。首版支持 Linux x86_64 的 Debian/Ubuntu 兼容镜像，冷启动即可；不复刻 E2B 的快照加速和完整模板平台。Dockerfile 多阶段由标准构建器处理，不自行解释。CPU/内存/磁盘在模板构建/注册时由用户选择并经准入校验，创建选择模板；不虚构固定 SDK create 没有的资源字段。总磁盘容量与构建后最小空闲空间分别记录，不把整个产品限定为题集的 10 GiB。

**模板子系统整体排除在形式化证明外**，包括第三方构建器、Dockerfile 执行、OCI 拉取/解包、镜像转换/制备，以及自有构建编排、模板登记/别名/查询/发布代码；采用工程测试验收。构建输入不可信，隔离、鉴权、限额、路径检查和失败收尾仍必须实现。核心证明以外部提供正确授权、不可变修订、摘要/资源清单正确且可启动的模板描述为显式条件；该合同不是已证明事实。核心实例身份、准入、生命周期、撤销、回执、恢复和精确停止/清理仍保留为后续证明目标；不宣称镜像供应链或整个沙箱全部已验证。准确状态只在[覆盖记录](proof-coverage.md)维护。

暂停、恢复、到期暂停、流量唤醒、快照、fork/clone、共享卷、自动迁移、动态节点发现、中心多活、Redis 自动切换、完整 POSIX/ACL 证明、动态域名策略、IPv6 放行、桌面和 GPU 不进入当前交付。暂停/恢复可作为独立后续扩展，不是当前集中证明的前置条件；若以后提供 E2B 式恢复，不能用冷重启冒充运行状态恢复。

文件采用 E2B 式运行期间接口，不将用户文件操作限制在单一工作目录；来宾路径不会成为宿主操作路径，完整 POSIX/ACL 证明不属于当前承诺。

## 3. 三人模块划分

A/B/C 是岗位占位符，不是 GitHub 用户名。实际认领后，在任务板和本表填写人员；不生成含无效用户名的 CODEOWNERS。

| 负责人 | 模块与实现目录 | 自己交付的内容 | 主要复核者 |
|---|---|---|---|
| A：控制与恢复 | `sandbox-center-core/`、`sandbox-center-store/`、`controller-core/`、`controller-service/` | 中心全局身份、绑定、准入、调度与持久协调；本地控制、事务、寿命、容量及恢复；不复制本地算法 | B；接口变化另请 C |
| B：节点执行与隔离 | `sandbox-node/`、`sandbox-runtime/` 及镜像/部署工具 | 节点内部入口、本地身份映射、执行资格、jailer 启停、观察与精确清理、网络、模板落地及隔离构建 | A；客户端行为另请 C |
| C：接口与集成 | `sandbox-api/`、`sandbox-center-service/`、`sandbox-host-service/`、`sandbox-internal/`、`sandbox-data-transport/`、服务组装与测试目录 | 统一公开入口、两端网关、模板用户入口、共享协议/组装、SDK 与 Harbor 兼容、双服务部署和 CI | A；运行环境另请 B |

目录存在不代表工作包已完整交付。共享消息位于 `sandbox-protocol/`；`sandbox-center/` 组装公开中心，`sandbox-server/` 仅构建受保护的 `sandproof-host`，跨模块组装由 C 集成、A/B 复核各自语义。不存在旧公开宿主模式；新增 crate 只在对应任务中加入 workspace。

每个人都写自己模块的单元、组件和故障测试。C 维护公共测试入口和结果汇总，不替 A/B 承担所有测试，也不单独判定安全语义。

交叉边界必须遵循 [模块合同](module-contracts.md)：

- C 在中心公开入口解析请求并验证用户凭据，A 检查全局授权和准入；节点验证中心证书、完整身份与本地映射，B 在实际执行前再次检查当前资格、寿命、围栏和资源。
- 中心是全局身份、固定绑定、意图与预留的唯一决定者；每个节点的本地控制器是其本机业务阶段的唯一决定者。执行层返回观察与回执，不能自行发布 Running/Destroyed；查询缓存和网关不是新的状态权威。
- A 负责两层恢复决策，B 提供原资源证据，C 验证组合。两层独立持久化，不假设 Redis 与 SQLite 有跨库原子事务；失联和心跳过期不释放未知责任。
- A/B/C 分别为后续控制证明、执行合同证明、接口授权与对应验证负责；形式化阶段按[验证总览](formal-verification-design.md#2-按真实模块划分证明责任)的V0–V9在真实代码上细分，可按中心、本地控制/执行、公开/数据三线认领。工程M0–M5与证明V0–V9不是同一编号；组合负责人持续核对邻接合同，不另建一套脱离运行代码的实现。

## 4. 开发里程碑

里程碑按可运行能力划分，不以完成文件数或代码行数计进度。

| 里程碑 | 模块协作交付 | 退出条件 |
|---|---|---|
| M0：共同合同 | A 定状态/持久化，B 定执行/观察，C 定客户端/测试清单；范围由 owner 确认 | 共享合同与测试样例可执行；版本和不支持项记录齐全；最小真实 SDK/VM 闭环有对应证据；不以三人共同批准或完整 Harbor 评分为前提 |
| M1：第一条真实闭环 | 创建 → 执行 → 上传下载 → 销毁 | 原 E2B 客户端的选定调用在真实 VM 上通过；检查 VM 和文件残留；不是完整 V1 |
| M2：V1 功能与故障 | F01–F09、多用户并发、寿命、重启和竞争 | 兼容清单与必要系统/故障测试通过；未知结果和失败清理可观察 |
| M3：兼容与回归 | 固定任务标准解答、通用模板和部署复现 | 固定 SDK 与选定回归通过；发布支持/差异/未验证清单；不接付费模型作为前置 |
| M4：中心/宿主工程交付 | #292 的合同、双服务、Redis 协调、数据/模板和 CI | 同一单机双服务候选通过组件、KVM 故障组和两题晋升，并进入 main；建立多台真机后续任务 |
| M5：集中形式化 | 按模块完成模型性质、指定 Rust 精化与系统组合 | 先闭合中心创建→丢回执→恢复→销毁链路，再按批扩展；目标性质及容量、保密、条件完成性闭合 |
| 后续扩展 | 多台真实宿主验收；暂停/恢复等独立功能 | 按关联任务分别验收和新增证明，不将其当成当前工作已交付 |

M0 后可以并行：A 使用契约一致的假执行器开发，B 用驱动程序验证真实 VM，C 使用同一合同的假控制服务验证 API。假实现只能作测试替身，不成为第二份业务规范。M1 尽早接上三条线，不能等各模块全部完成才第一次集成。

## 5. 可直接拆分的任务

后续 P1 [Rust 来宾服务 #311](https://github.com/ningZhang-cs/sandproof/issues/311) 由 B 主责，C 核对 SDK/网关，A 核对状态与证明连接。按已有命令/文件能力替换固定 envd，首批建立合同样例与独立纯核心；进程、文件、认证/预算、模板和真实 KVM 分批交付。集成沿用 #292 已交付的中心/宿主链，不新增本轮 V1 发布阻塞项；未验收时不替换现役模板。接口以[模块合同](module-contracts.md)为准，后续实际证明归 #101。

工作包已建立远端 issues，编号链接如下。每项任务的“完成”都包含测试及相关文档；一个任务可以拆成多个小 PR。里程碑表示整个工作包的最终验收点，不妨碍提前开发和按可联调小步骤交付。

#311 的独立来宾组件已连接真实 Linux 进程、PTY、持久 PID 登记、初始化/鉴权和文件接口；固定 SDK 经受限回环夹具的选定命令/文件场景已在普通隔离 Linux CI 通过，精确版本与未运行项只在[验收清单](testing-plan.md)维护。共用来宾 HTTP 装配、跨接口鉴权/轮换与有界监听器组合已在普通隔离 Linux CI 实测。正式 daemon 已实现显式配置及 check/initialize/serve 入口，连接同一组件、持久服务会话和受信任启动文件；仍未安装到现役模板。完整兼容错误与 keepalive、待决 tag 规则、不可变模板版本登记及 S4 的实机/故障/资源验收仍须补齐。接口边界见[模块合同](module-contracts.md)，旧组件/回环证据不表示该入口已实机通过、已部署来宾替换、完整 SDK 双端或 KVM 验收。
