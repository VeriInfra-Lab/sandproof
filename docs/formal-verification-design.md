# 形式化验证设计

[文档目录](README.md) · [项目蓝图](project-blueprint.md) · [模块合同](module-contracts.md) · [证明覆盖](proof-coverage.md) · [证明工作流](proof-workflow.md)

本文是证明目标、故障模型、外部前提、状态与精化/组合方法的设计依据，不是已完成的证明报告。产品范围以蓝图为准，实际接口和失败语义以模块合同为准；本页将它们连接为证明义务，不另定义兼容协议。当前实现、适用版本及未闭合义务只在证明覆盖记录维护。

目标架构为单有效中心、权威 Redis 与有限静态登记宿主，每个沙箱固定绑定一个宿主。中心/宿主拆分及工程交付由 [#292](https://github.com/ningZhang-cs/sandproof/issues/292) 跟踪，设计评审由 [#277](https://github.com/ningZhang-cs/sandproof/issues/277) 跟踪，实际证明由 [#101](https://github.com/ningZhang-cs/sandproof/issues/101) 跟踪。模块合同与设计可先固定；完整证明在功能、故障与实机验收后冻结的真实组合提交上推进。本文所有目标性质均为待交付要求，不因写成公式而成为已证定理。

## 1 我们需要证明什么

以创建过程中的故障场景为例。

用户请求创建沙箱。控制器将计划写入数据库，虚拟机随后启动；但在“启动完成”回执持久保存之前，控制器发生崩溃。

控制器重启后的处理必须满足以下要求：

1. **不得直接创建替代实例。** 原虚拟机可能仍在运行，重复创建会产生未被正确管理的额外资源。
2. **不得仅因缺少回执判定创建失败。** 回执缺失表示结果未知，不代表启动未发生。
3. **不得接管身份未经核实的虚拟机。** 必须核对原登记身份，避免操作其他实例。
4. **必须继续处理原操作。** 确认原执行结果，或者停止并清理原资源，确保已接受的责任不会丢失。

形式化验证要把这些要求写成精确规则，再证明代码的每一种允许执行都遵守它们，包括异常分支。

目标可以归成三类：

| 目标 | 含义 | 示例 |
|---|---|---|
| 安全 | 排除规约禁止的行为 | 不越权、不误删、不将未知结果判为成功 |
| 功能正确 | 合法请求产生约定结果 | 参数不被静默忽略，截断输出不被报告为成功 |
| 有条件的最终完成性 | 所需条件成立时，操作最终达到约定结果 | 已接受的销毁最终完成清理 |

第三类需要额外前提：如果宿主磁盘持续不可写或进程始终无法停止，就不能承诺操作一定完成；但系统仍不得错误报告成功或影响其他实例。

## 2 如何界定验证边界

**边界不是简单列出“哪些软件不证明”，而是说明：我们相信它们提供什么，以及我们必须怎样使用它们。**

### 哪些由我们证明

我们负责公开请求检查、中心全局身份/固定节点/准入/额度、Redis 提交派发、内部请求身份与去重、宿主本地生命周期/恢复/执行、两端数据转发及组合。中心不远程指挥 PrepareVm 等子步骤，宿主保留唯一的本地算法。

例如，Linux 提供删除文件的能力，但“被删除的是否为原沙箱目录”，必须由我们的代码保证；SQLite 提供事务能力，但“哪些记录必须放在同一个事务里”，也是我们的责任。

### 哪些依赖外部软件

| 外部部分 | 依赖它提供什么 | 仍由我们负责什么 |
|---|---|---|
| Firecracker、jailer 和 Linux | 在规定部署条件下隔离和运行虚拟机 | 传入正确的磁盘、网络、权限和资源配置 |
| Redis、SQLite 和文件系统 | 按冻结版本/配置提供提交、持久与恢复合同 | 两端分别先持久责任再执行，处理未知提交，不假设跨库原子事务 |
| envd | 在正常功能条件下执行命令、读写来宾文件 | 准确定位实例、忠实转发、处理失败与限额 |
| 模板构建与管理 | 交付经过授权、不可变的模板产物 | 创建时固定模板、核对产物、正确计费 |
| 编译器、运行库、认证和加密工具 | 按声明的接口和安全条件工作 | 正确调用，不省略自身的检查与错误处理 |

这里的 envd 是**虚拟机内部负责接收命令和文件请求的程序**；宿主则是运行这些虚拟机的 Linux 服务器。

Firecracker 不负责判断用户是否有权使用指定磁盘，也不负责实施完整的出站网络策略。jailer 的官方要求将调用输入视为可信输入，因此路径与配置的安全性由调用方负责。[Firecracker 设计](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/design.md)、[生产部署要求](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/prod-host-setup.md)

### 覆盖的故障与范围外情形

网络断开、磁盘满、重复请求、丢回执、控制器崩溃和恶意来宾，都要考虑。宿主内核被攻破、管理员恶意篡改控制数据、硬件静默损坏和任意回滚旧备份，不在这份证明的承诺里；未约定的断电持久性也不包含。

另一个重要区别是：**来宾可以不可信，但不能因此相信它报告的所有业务结果。**

即使来宾谎报文件内容，控制器仍应保证它不能影响别人的实例；但若要证明“返回的确实是那个文件的真实内容”，还要假设此次调用中的 envd 和来宾文件系统遵守功能约定。这是两种不同的证明条件。

目标包含一个有效中心写入者、单个权威 Redis、多个静态登记宿主，每个沙箱固定绑定一个宿主；覆盖创建、连接、查询、续期、销毁、命令、文件、受控 IPv4 网络及两端恢复。首批工程交付为单台 KVM 上中心/Redis/一个真实宿主经鉴权网络通信，多台真机验收另立任务。暂停恢复、快照、共享卷、自动迁移/异地重建、多中心多活及 Redis 自动切换仍排除；模板子系统整体不证明。

外部软件的详细条件见[附录 A](#a-底层依赖的详细约定)。

## 3 状态机需要记录什么

状态机可以理解为：**系统状态，以及规定状态何时可以变化、如何变化的一组规则。**

只记录“沙箱正在运行”是不够的。它至少需要记录五类信息：

- **资源归属**：用户、沙箱、虚拟机、目录和网络资源的身份。
- **操作计划**：创建或销毁计划，允许使用的资源和预算。
- **执行进度**：尚未执行、正在执行、结果未知、成功或明确失败。
- **确认依据**：原虚拟机的真实观察、完成回执、停止和清理证据。
- **在途使用情况**：命令连接、文件传输和辅助进程是否已经结束。

尤其要把三件事分开：数据库记录、宿主实际状态与最近一次观察结果。

在前面的例子中，数据库可以记录“启动结果未知”，机器上却已经有一台运行中的虚拟机。这是故障期间的正常组合，不是应当从模型中排除的情况。我们要证明系统能够安全地处理它。

还有两类容易混淆的编号：

**工作身份**回答“这是哪一个动作”；**尝试编号**回答“这是该动作的第几次尝试”。旧尝试迟到的回执，不能冒充新尝试的结果。同样，物理位置可以复用，但新沙箱不能继承旧沙箱的身份和许可。

完整字段见[附录 B](#b-完整状态定义)，允许的变化见[附录 C](#c-输入和状态转换规则)。

## 4 如何定义输入输出正确性

### 输入转换必须保留请求含义

例如用户申请一段寿命：省略参数时采用约定默认值；超过创建上限时应拒绝，不得静默缩短。命令的用户、工作目录和环境变量也必须完整保留。

所以输入正确性不只是“格式能解析”，还包括：身份正确、含义保留、单位换算正确，以及缺失、零值和非法值按约定处理。

### 输出成功必须有明确含义

假设用户上传一个 100 字节的文件，系统只收到 80 字节就断线了。

可以报告失败，也可能只能报告写入结果未知；**不得将声明长度改为 80，再报告上传成功。**

接收到 100 字节也不足以证明写入正确：内容可能发生变化、目标实例可能不符，或者旧文件尾部仍有残留。因此，成功的文件写入需要同时满足以下条件：

1. 目标实例和路径是否属于原用户的授权范围？
2. 内容是否逐字节相同，长度是否符合本次写入的约定？
3. 协议是否完整结束，文件服务是否已确认完成？

还要区分三个层次：网关写出了数据、客户端收到了数据、来宾文件完成写入。它们不是同一件事。

命令也是如此。“已启动”不等于“已结束”；退出码非零可以是命令正常结束的结果，不一定是控制器故障。HTTP 200 也不能单独证明流式调用成功，仍要看协议规定的结束信息。[Connect 流式协议](https://connectrpc.com/docs/protocol/#streaming-rpcs)

精确定义和转发小状态机见[附录 E](#e-数据完整性的精确定义)。

## 5 故障处理需要遵守哪些规则

故障处理应保持原操作身份，不得通过反复新建实例规避未知结果。主要规则如下。

**先持久记录，再执行。** 启动虚拟机前，先保存计划和身份。即使执行中途崩溃，恢复程序仍能识别和清理原资源。

**保留未知状态。** 超时不代表没有执行，文件写失败不代表自动回滚。只有明确失败，或已证明重复执行安全的动作，才允许按对应规则重试。

**销毁分阶段完成。** 先关闭新访问，再阻止旧启动工作继续，随后停止进程、结束已有连接并清理资源。已经进入网络缓冲区的字节可能稍后才被读到，所以不能承诺“点击销毁后立即没有任何字节到达”。

**确认释放后才退还额度。** 目录、进程或连接仍未确认清理，就仍占资源预算。磁盘使用稀疏文件也一样：现在占块少，不代表以后写满不需要空间。

这些规则还必须能相互配合。例如，不能出现“清理要等引用解除，而引用解除又要等清理”的永久等待。

崩溃位置、持久记录和容量公式见[附录 F](#f-故障恢复和资源边界)。

## 6 证明工作如何划分

按状态权威、证据来源和下游前提分模块。以下是证明责任，不要求每行新增 crate 或运行服务；共享类型、查询更新、整数、身份和容量引理复用。

| 模块 | 主要证明责任 |
|---|---|
| 公开入口 | 认证、完整请求语义、结果/错误和可见投影 |
| 中心控制核心 | 全局身份、唯一固定节点、准入/预留、意图版本、终止及窗口退休 |
| 中心持久协调 | Redis 权威表示、原子/耐久提交、提交后派发、回执与恢复 |
| 内部协议与节点入口 | 编解码、认证绑定、高级操作去重、版本、窗口及本地映射 |
| 宿主本地控制与持久化 | 既有核心/SQLite、调度、寿命、未知处理、收尾和历史退休 |
| 宿主执行 | 获批配置、原资源观察、围栏、停止和精确清理 |
| 两端数据网关 | 固定路由、本地当前资格、完整性、有界驻留、撤销与排空 |

系统组合证明连接各模块，不是新增运行服务。中心全局协调模型和宿主本地执行模型职责不同；禁止的是复制第二套本地算法，不是禁止两层状态机。

丢回执时中心保留原绑定/额度，节点恢复原本地计划，宿主提供原实例事实，节点持久保存，中心核对身份/版本后保存结果，公开入口返回约定语义。所有连接都需合同与实现对应；不能只分别证明正常返回。

分别报告模型性质、指定实现精化与列明条件下的组合结论；不能将自有通信/恢复/鉴权统称可信外壳。性质见 G，接口/组合见 H，实际证明归 #101，功能交付归 #292。

## 7 如何验证实际 Rust 实现

我们保留两份不同用途的描述：

- **手写 Lean 模型**：独立规定“什么行为是允许的”。
- **Rust 翻译得到的 Lean 程序**：描述“实际代码怎样执行”。翻译使用 Charon 和 Aeneas。

然后证明两者对应。对应关系包括状态字段映射和逐步行为核对：

1. 初始化后的代码状态，对应一个合法模型状态。
2. 代码接受请求时，结果和状态变化符合模型。
3. 代码拒绝请求时，原因正确，没有发生不该发生的副作用。
4. 合法且条件满足的请求，代码不能无理由拒绝或因内部处理逻辑而永久阻塞。
5. 崩溃、重启和外部调用，也遵守各自的状态与接口约定。

两个程序都写成 Lean，并不会自动使它们相等；必须逐模块建立这些对应证明。

最终应分别报告：**模型性质是否成立、哪一版 Rust 已对应模型、在什么外部条件下完整服务的结论成立。** 测试用于核对真实环境和外部约定，证明用于覆盖模型允许的全部情况，两者各有作用。

## A 底层依赖的详细约定

本附录把正文中的“依赖外部软件”细化为证明前提。总目标写成：

```text
外部原语合同 A ∧ 合法部署 D ∧ 实现与模型对应 R
    ⇒ 每条真实执行历史都满足规约 P

A_safe     := 宿主隔离、受保护控制数据、依赖原语的安全合同
A_function := A_safe，加上本次调用期间 envd、来宾文件系统
              和固定客户端遵守功能协议
```

自己编写的适配器、恢复程序和鉴权逻辑属于待证明代码，不能直接放进外部前提。能由程序建立和保持的部署条件，也应成为它的证明义务。

允许的故障包括恶意或格式错误的请求、并发、重复和迟到消息、拥有自身 root 权限的来宾、伪造响应、网络中断、超时、资源不足、部分完成，以及控制器或工作进程在任意两步之间崩溃。权限错误或观察失败都必须有明确分支。

不承诺宿主隔离已被攻破、管理员恶意篡改受保护数据、硬件或存储静默损坏、任意回滚旧备份、未约定的断电行为，以及外部窃取有效凭据后仍识别真实持有人。不证明用户程序计算正确或必然终止，也不承诺在允许任意内容的外部通道上阻止所有信息外传。

模板边界包含自有构建编排、注册、别名、发布和产物服务，均工程测试；核心使用时仍证明授权/不可变绑定、准入、资源和清理。暂停恢复、快照、共享卷、迁移、多中心及存储自动切换本次不启用，相关类型需证明所选初态/允许输入不进入排除分支。多宿主协议与组合纳入验证，部署限制见[项目蓝图](project-blueprint.md)。

每个外部操作使用四项合同：**调用前提、成功后果、失败可能留下的状态、崩溃后可用的证据**。失败默认不等于没有副作用。

### A1 Firecracker 和 jailer 的具体边界

Firecracker 官方将来宾视为不可信方，并说明网络流量过滤由宿主负责。它不是我们租户授权和出站访问规则的实现者。[Firecracker 设计](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/design.md)

官方生产部署要求特别指出：jailer 的输入是可信输入；相关路径及其父目录需受保护；宿主安全更新、系统调用过滤和资源限制也是部署责任。因此不能推理为“用了 jailer，所以用户传来的任意路径和配置都安全”。[生产部署要求](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/prod-host-setup.md)

定义 `SafeLaunch(b, cfg, h)`，其中 `b` 是获批实例绑定、`cfg` 是将交给 Firecracker/jailer 的配置、`h` 是宿主状态。它必须同时满足：

1. `cfg` 来自已提交计划，完整绑定所有者、沙箱、代次、虚拟机和运行位置，不由客户端直接指定宿主路径。
2. 二进制、控制套接字、配置、登记文件、监狱目录及父目录受保护；校验至使用期间，目标身份不会被未授权替换。
3. 使用匹配的 Firecracker/jailer 版本和支持的构建；实际降权身份、隔离目录、系统调用过滤、资源控制组均符合部署方案。
4. 每个传入磁盘、网络接口及其他句柄只指向获批资源；基础镜像不因实例运行而被改写。
5. 客户获批的处理器、内存和磁盘形状被准确转换；单位换算与序列化无溢出、缩窄或静默截顶。
6. 宿主网络路径已处于批准规则之下，默认拒绝未获批路径；来宾不能修改这层规则。
7. 启动中的资源已有可恢复登记，故障或丢回执不会留下无法归属的实例。

其中第 1、2、4–7 项包含我们的程序义务，不是外部软件保证。第 3 项同时包含外部部署前提与我们对实际配置的核对义务。

一个容易忽略的细节：jailer 在特定的第二版资源控制组配置下，指定父控制组不存在时可能继续运行而不加入它。因而“jailer 成功退出配置阶段”不足以证明资源限制生效；需要核对实际控制组成员与限制。[jailer 参数和行为](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/jailer.md)

对启动分三层记录，不能合并：

| 事件 | 可以推出 | 不能推出 |
|---|---|---|
| 配置请求被接受 | 对应配置操作满足 Firecracker 接口的接受条件 | 资源属于请求租户、全部宿主约束已生效 |
| 启动操作被接受或观察到运行 | 该虚拟机在相应观察点已经启动 | envd 就绪、用户程序健康、以后不会退出 |
| 同一绑定的宿主检查和 envd 初始化完成 | 已达到本项目规定的服务就绪条件 | 用户任意应用已启动成功或未来持续健康 |

Firecracker 的接口分别暴露配置、启动动作和实例状态；我们的“沙箱可用”需要在这些接口之上定义。[固定版接口模式](https://raw.githubusercontent.com/firecracker-microvm/firecracker/v1.16.1/src/firecracker/swagger/firecracker.yaml)

这里的成功证据通常是带身份的历史事实。定义 `ReadyObserved(b,k)` 为第 `k` 个事件中对原绑定取得规定就绪证据。运行发布需要这样的证据、没有已知的失效事件，并再次核对围栏和期限；不能推出“在响应到达客户端的那一刻，进程一定仍活着”。来宾可以在观察后立即退出，任何普通健康检查都无法消除这个时间间隔。

### A2 外部原语的合同清单

| 编号 | 原语与前提 | 可依赖的结果 | 我们需要证明的使用方式 |
|---|---|---|---|
| A1 | 固定受支持环境中的虚拟化隔离 | 来宾只能通过获准设备与宿主交互，不任意改写宿主内存 | 设备、磁盘、控制套接字和网络绑定不越权；禁用未纳入模型的设备路径 |
| A2 | 对已验证原对象持有稳定进程句柄 | 终止或观察作用于该句柄指向的进程 | 句柄创建前后核对原进程身份；跟踪所有受管辅助进程，不能把单一进程退出当作子进程全部退出 |
| A3 | 受保护目录及带身份约束的文件操作 | 读取、替换、删除作用于指定对象；显式错误保持可见 | 先登记身份再产生副作用，清理前核对原身份，处理路径替换和部分写入 |
| A4 | 指定 SQLite 配置和排他写入纪律 | 事务恢复为提交前或提交后的一致状态 | 核心、派发计划、身份、额度和期限同事务；未知提交按两种可能处理 |
| A5 | 已确定网络空间与规则集合的内核执行 | 经过该路径的数据包服从安装的规则 | 所有来宾出口都经过此路径，规则对应获批策略，安装期间无放行窗口 |
| A6 | 库提供的有序字节流、错误和取消语义 | 读写返回值与已接受字节对应；失败可发生在部分传输后 | 短写循环、背压、结束标记、预算、取消和半关闭组合正确 |
| A7 | 固定 envd 和客户端的功能协议 | 请求、输出、退出事件、文件完成回执具有约定含义 | 不改变请求含义，不伪造成功，不把超时当作未执行 |
| A8 | 可信时钟和约定的漂移范围 | 读数与真实时间的关系满足声明 | 单位、溢出、持久时间下界、重启和期限竞争正确 |
| A9 | 密码学和认证边界 | 未授权方不能在威胁模型内伪造身份或有效凭据 | 凭据精确绑定实例，撤销生效；一个实例的凭据故障不影响无关实例 |
| A10 | 不可变模板交付合同 | 描述、授权和产物对应，产物在使用期间受保护 | 固定实际修订、核对长度与摘要、按形状计费，不在恢复时重解析别名 |
| A11 | 固定 Redis 版本、[中心持久化合同](module-contracts.md#中心持久化与恢复)中的 AOF/内存/重写配置、可靠存储及单有效写者 | 原子生效与冻结耐久/未知合同，恢复不补造账本 | 自有 CAS/Lua、编码、版本、缓存失效、耐久确认及派发；原子执行不是多命令错误回滚 |
| A12 | 双向认证连接和明确连接错误语义 | 认证对端与连接内字节合同；跨请求/连接仍可能重复、延迟、丢失或乱序 | 证书到部署/节点映射、字段绑定、端点白名单、参数保真、去重和旧消息拒绝 |

进程句柄解决的是“打开后不要因进程编号复用而改指向”；它不会自动证明打开时就是我们原来登记的那个进程。[Linux 进程句柄说明](https://man7.org/linux/man-pages/man2/pidfd_open.2.html)

SQLite 的原子提交也依赖底层输入输出合同，且不替我们把数据库之外的虚拟机或目录变成同一事务。[SQLite 原子提交](https://sqlite.org/atomiccommit.html)、[日志与检查点机制](https://sqlite.org/wal.html)

摘要不是数学上无条件唯一的身份。模型优先使用完整描述相等；若实现仅比较摘要，应单列抗碰撞前提。类似地，随机令牌的不可伪造性是密码学前提，不应伪装成确定性程序定理。

### A3 哪些前提可以检查

部署预检可以检查二进制版本、配置格式、权限、路径、控制组、转发设置和资源预算；运行期间还需保持受保护目录、排他控制和规则不被外部写者破坏。

预检不能证明内核没有漏洞、未来磁盘永远可写或外部命令永远及时返回。因此“预检通过”不是 `A1–A12` 全部成立的证明。凡是可失败的观察，都保留 `未知/错误` 分支，不用一个布尔值把“没看到”当作“不存在”。

## B 完整状态定义

### B1 不能只建模纯核心

定义全系统状态，N 是任意满足部署预算的有限登记节点集合，不写死一/二个节点：

```text
Σ = (配置 Cfg，中心控制 Cc，中心持久/缓存 Jc，
     {Ni = (Ki, Ji, Hi, Gi)} i∈N，中心通道 Gc，在途消息 M，环境 E)
```

Cc 保存全局身份、固定节点、意图/版本、预留、待发送责任与已确认事实；Jc 保存 Redis 权威提交及派生视图。Ki/Ji/Hi/Gi 分别为节点核心、本地持久与易失协调、真实资源和通道。B3–B7 的既有 K/J/H/G 按单节点解释，不把中心与节点阶段合成同一个枚举。

M 包括发送、投递、重投、丢失和待确认消息及完整身份/版本，不假设跨请求 FIFO 或 exactly-once；无效消息在解析/身份边界拒绝。E 包括各进程/存储及各机时钟/声明误差，不假设所有机器时钟相同。中心未知但节点已经运行是允许状态，不能要求各层副本始终相等。

证明另外使用历史 `T` 记录已经发生的事件。`T` 是推理用的历史，不要求真实数据库永久保存无限日志。

三个状态必须分开：`K` 认为虚拟机怎样，`H` 中虚拟机实际怎样，宿主适配器最近观察到了什么。进程可能已经启动而 `K` 尚未收到回执；也可能 `K` 曾发布运行而进程随后退出。把它们定义成同一个变量，会直接排除最需要验证的故障。

### B2 身份和数值域

| 类型 | 含义与必要限制 |
|---|---|
| 租户、沙箱、工作区、虚拟机、网络资源编号 | 不同类型不混用；在同一持久部署命名空间内按各自规则分配 |
| 操作键 | 沙箱与操作编号的组合；同键绑定相同操作种类和完整参数 |
| 代次 `generation` | 区分同一沙箱的运行代；不是虚拟机编号的替代品 |
| 控制轮次 `epoch` | 撤销旧工作权限；与代次分开，销毁可以改变轮次而不产生新运行代 |
| 逻辑工作键 | 完整工作命令；包括命令种类和其全部身份、策略参数 |
| 尝试键 | 逻辑工作键与尝试编号的组合；不同尝试不能共用回执 |
| 宿主位置编号 | 节点命名空间内的可复用位置；复用不复用原实例身份 |
| 部署/节点身份与节点代际 | 持久身份；地址不是身份，节点重装不能认领旧资源 |
| 全局沙箱/操作与本地映射 | 中心持久分配，节点持久映射原本地实例/操作；计数器不混用 |
| 中心修订/意图版本/节点观察版本 | 分别约束提交、实例意图与事实次序，不代替本地 epoch/generation/attempt |
| 毫秒、秒、字节、资源数量 | 模型中用非负整数或明确的有符号整数；实现转换时另证范围和单位 |

令 `U64 = {n ∈ ℕ | n < 2^64}`。模型中的加一不能自动代替 Rust 的有界加一：必须证明未到上界，或明确拒绝分配。不得回绕。记录退休后保留必要高水位，不能把老请求当成第一次出现的新请求。

### B2.1 中心字段与节点映射

中心至少完整建模 [中心状态合同](module-contracts.md#中心状态与节点责任)的部署/格式、修订、高水位、节点登记、租户/平台预留、owner 与固定节点/代际、不可变模板/形状、原输入、意图/版本、期限、未决操作/outbox、已确认事实、保留结果/窗口和退休责任；内存索引从提交修订派生，不另设权威。

节点持久维护全局绑定到原本地身份、完整高级操作参数/结果、终止围栏及窗口；回执丢失、重启和历史回收不能重新分配映射。节点代际改变不能迁移认领旧实例。

### B3 规则核心的字段全集

下表对应 [World 与相关类型](../controller-core/src/model.rs)及[维护状态](../controller-core/src/maintenance.rs)。每个字段必须在表示关系中出现；不能只选最容易证明的子集。

| 字段组 | 内容 | 作用 |
|---|---|---|
| `sandboxes` | 所有者、阶段、终止标记、轮次、代次、当前虚拟机、工作区及访问模式、文件策略、网络位置与策略、期望和生效授权、当前操作；另有快照相关可选字段 | 实例身份与授权的主要记录 |
| `vms` | 所有者、沙箱、代次、虚拟机状态 | 逻辑虚拟机资源 |
| `filesystems` | 所有者、沙箱、创建代次 | 工作区归属 |
| `snapshots` | 所有者、来源代次、工作区、清单、阶段、不可变标记 | 既有快照模型；本功能子集证明不可达 |
| `net_slots` | 所有者、沙箱、代次、虚拟机、策略、已配置、已激活、已回收 | 网络资源及策略绑定 |
| `applied_file_policies` | 沙箱、代次、工作区、策略 | 文件策略已应用的逻辑事实，不自动等于宿主权限已正确设置 |
| `worker_fences` | 每个沙箱的控制轮次与终止标记 | 拒绝过期的启动或授权工作 |
| `operations` | 操作键、完整输入、状态与结果 | 请求重放和终局结果 |
| `operation_plans` | 操作键、轮次、代次、资源选择、停止与关闭集合、重试额度、封定标记 | 固定一次操作允许影响的资源 |
| `resource_indexes` | 每个沙箱的虚拟机、网络、快照索引 | 不能漏掉非当前资源的停止和清理 |
| `logical_effects` | 工作来源、当前尝试、剩余重试次数、终局结果 | 工作与重试总账 |
| `effect_keys`、`effects` | 尝试身份索引和各次尝试状态 | 防重复、拒绝错误回执 |
| 四个 `next_*` 计数器 | 虚拟机、网络位置、快照、清单编号 | 有限身份分配 |
| `inflight`、`controller_up` | 在途工作和控制器存活标记 | 派发及核心恢复模型 |
| `maintenance` | 编号高水位、保留结果、时间下界、容量限制、位置记录、准入窗口 | 有界历史和安全复用 |

`maintenance` 内的位置为 `Occupied / Releasing / Free`，即占用、释放中、可复用；`Free` 仍保留上次绑定。窗口记录包括窗口编号、租户、发出时间、到期时间和已发出编号上界。窗口本身不是资源准入的替代品。

### B4 核心状态取值

| 对象 | 全部主要取值 | 本功能子集的约束 |
|---|---|---|
| 沙箱阶段 | `Starting / Running / Pausing / Paused / Revoking / Destroyed` | 启动、运行、撤销、销毁；暂停相关状态不可达 |
| 虚拟机状态 | `Prepared / Executing / Frozen / Stopped / Reclaimed` | 准备、执行、停止、回收；冻结不可达 |
| 操作种类 | `Create / Pause / Resume / Kill` | 创建、销毁；连接和续期不等于创建新虚拟机 |
| 操作状态 | `Pending / OutcomeUnknown / Compensating(f) / Succeeded / Failed(f)` | 等待、未知、为失败收尾、成功、失败；失败是操作结果，不是新增沙箱运行阶段 |
| 授权 | `Closed / Running(binding) / Paused(source)` | 关闭或完整运行绑定；不能仅凭阶段名字授权 |
| 工作状态 | `Committed / Dispatched / OutcomeUnknown / Acknowledged(outcome) / RetiredByStop(coverage)` | 已提交、已派发、未知、已确认、被精确停止证据覆盖并退休 |
| 工作结果 | 成功摘要、明确失败、被停止覆盖退休 | 退休不是伪造一次启动成功或失败 |
| 失败种类 | `Cancelled / DeadlineExceeded / ResourceFailure / PolicyFailure / StorageFailure / InternalFailure` | 是否可重试由明确规则决定，不是所有失败都重试 |

### B5 持久服务还需要哪些状态

`J` 至少包含：数据库已提交版本、持久核心表示、操作与工作日志、检查点及其后的日志、身份高水位、创建参数、不可变模板绑定、寿命记录、资源与未来清理预算、凭据索引、内存缓存所对应的提交版本、恢复阶段、物理释放见证和阻止退休的引用。

事务可处于 `Idle / Executing / CommitUnknown / Committed / Aborted`。`CommitUnknown` 是调用方不知道提交结果，不是数据库允许“提交一半”。外部动作不与 SQLite 共享原子事务。

### B6 宿主和观察状态

对每个受管绑定 `b`，`H` 记录：

- 原进程身份及稳定句柄、关联辅助进程、实际运行或退出状态。
- 监狱目录、磁盘、内核副本、登记文件、控制套接字的原对象身份。
- 网络空间、接口、规则、路由及实际生效策略。
- 控制组成员与限制、运行位置、受保护模板引用。
- 宿主侧已安装围栏、正在执行的工作及其完整尝试键。

观察结果用三类表示：`Present(identity, facts)`、`Absent(scope)`、`Unknown(error)`。证据还绑定观察对象、操作或尝试、观察顺序和保护条件。`Absent` 只能覆盖真正检查过的资源范围；权限错误不能生成 `Absent`。

目录的设备号和 inode、进程编号、网络接口名称都可能被复用。因此“同名”不等于“原对象”；原身份比较还需受保护生命周期或稳定句柄，不能假设有限编号永不重复。

### B7 数据通道状态

`G` 对每次请求记录：认证租户、绑定实例、代次、虚拟机与令牌身份、目标路由、许可、注册的连接与辅助进程、撤销状态、两个方向的输入和输出字节序列、协议解析状态、按操作种类适用的字节预算、在途缓冲与单消息预算、空闲与总期限、结束状态。

结束状态至少区分：`Open / Completed / Failed(reason) / Cancelled / OutcomeUnknown`。另外记录请求类型的业务结果，例如命令进程编号、退出码、文件写入确认。一次后台命令“已启动”不等于“已执行完成”。

### B8 初始化、可达状态与归纳

纯本地核心空初态仍对应 initial_world；完成原配置、维护、位置、租约及持久初始化前不能接受用户请求。

FreshReady_node(Ni) 要求合法配置/受管根与库租约、允许空部署、预算/位置持久建立、Decode(Ji)=Ki、无未登记物理资源及空在途通道。RecoveredReady_node 要求原持久格式与完整配置匹配，从完整检查点和连续尾恢复，保留原资源/未知责任，不继承未重建许可，按规定启用观察/恢复，不要求所有 VM 停止；损坏或不匹配的原库不能当新部署。

FreshReady_center(Cc,Jc) 要求显式一次性部署初始化、受保护节点登记、合法格式/预算/Redis配置、有效单写者及权威块/派生视图对应。RecoveredReady_center 从原耐久提交恢复绑定、意图、额度和 outbox；原库为空/损坏不能自动新建，节点结果未知继续未知。

中心、节点和 Redis 分别 Crash/Restart；一个重启不清空全部系统。上述条件是自有初始化/恢复程序的后置条件，不是任意给原库加的假设。系统从全新部署或其合法历史恢复，未就绪服务拒绝新工作。

WellFormed 包含局部表示/身份/索引/窗口，以及跨模块绑定/责任/版本关系；不要求中心、节点逻辑和真实资源相等。I_global 为 G3 所需共同不变量。

```text
Init(Σ) ⇒ WellFormed(Σ) ∧ Safe(Σ) ∧ I_global(Σ)
Reachable(Σ) := 从合法初态经允许步骤得到的有限执行前缀
WellFormed(Σ) ∧ Safe(Σ) ∧ I_global(Σ) ∧ Step(Σ,a,Σ')
  ⇒ WellFormed(Σ') ∧ Safe(Σ') ∧ I_global(Σ')
```

Step 包括中心/节点决定、存储、消息、宿主、流、时钟和故障，不能只证明正常调用。先后关系用辅助历史 T，保密另比较两条历史，最终完成性另分析无限执行条件。

## C 输入和状态转换规则

### C1 真实核心输入不能漏项

[统一核心入口](../controller-core/src/controller.rs)包含九组输入：

| 输入组 | 必须覆盖的内容 |
|---|---|
| `Request` | 创建、暂停、恢复、销毁、重放、查询、补偿；其中暂停、恢复按功能子集证明不可达 |
| `Effect` | 派发、回执、超时、重试、终结失败、用停止证据退休未知激活 |
| `Scheduler` | 启动资源预留、暂停快照预留、准备派发、封存、提交、停止、撤销准备、清理虚拟机、清理网络资源 |
| `Worker` | 执行一个完整尝试键对应的命令 |
| `Publication` | 发布运行、暂停、销毁、失败 |
| `RpcTimeout` | 客户端等待超时的核心语义；不能等同取消成功 |
| `Access` | 执行、文件读、文件写、入口访问、出口访问 |
| `Runtime` | 崩溃、恢复、重复或迟到投递 |
| `Maintenance` | 启用维护、退休、过期结果移除、位置管理、窗口管理 |

还需覆盖公开请求、中心准入/意图/额度、Redis结果、内部高级请求/映射、两端回执/确认、流与取消、各机时钟、SQLite、宿主观察/部分效果、进程退出、断线与独立恢复。Worker 或本地九组输入不能代替中心/通信输入；新增实际入口需逐项穷尽对照。

输出也要带类型，至少区分 `Rejected(reason)`、`Accepted(operation)`、`Pending(operation)`、`Unknown(operation)`、`Completed(result)`。具体接口可以有不同编码，但不能因为它们同用成功状态码就合并含义：续期成功表示期限已提交，不表示到期停机完成；后台命令已接受也不表示执行完成。

### C2 每个接口的输入合同

对方法 `m` 定义：

```text
Normalize_m(认证上下文, 原始请求)
    : 拒绝(错误类别) 或 完整语义请求
```

每个字段都必须在接口合同中指定：数据类型、缺失值、显式空值、零和负数、最大值、重复字段、非法编码、未知字段、单位与跨字段限制。不是一律严格拒绝，也不是一律忽略：应实现固定兼容合同规定的行为。

归一化正确性分三项：

1. 认证租户仅来自认证上下文；原始正文不能覆盖它。
2. 两个请求若归一化成同一值，必须在合同定义的意义下等价；不能把不同的命令、环境变量或网络规则压成同一请求。
3. 对字节载荷，除明确规定的协议编码外不裁剪、不补零、不转码；对数值，默认、拒绝和截顶分别证明，不能混为一种“规范化”。

例如，创建寿命超过上限时应拒绝，不得静默缩短；设置寿命则有约定的截顶语义。这些不是同一个算术函数。

从完整请求到外部参数还需要第二个对应关系。例如命令请求包括原实例、用户、工作目录、环境变量、命令内容、后台选项与期限；虚拟机启动描述包括原绑定、内核、私有磁盘、处理器、内存、网络和初始化参数。对允许的描述 `p`，应证明 `DecodeExternal(EncodeExternal(p)) = p`，再证明调用目标属于 `p` 的原绑定。只证明 JSON 格式合法，不足以排除内存单位错一千倍、工作目录遗漏、参数转义改变命令含义等错误。

### C3 转换关系和拒绝

纯核心规则定义为全函数：

```text
δ(K, input) = Reject(error)
           或 Accept(event, K')
```

每条规则按顺序列出检查 `g1…gn`：第一个失败检查决定拒绝结果；全部通过才做更新。需要证明：

```text
全部检查通过 ⇔ 该规则被接受
拒绝 ⇒ 没有核心后继状态，也不产生宿主工作
接受 ⇒ 指定字段按规则更新，其他字段不变
```

“其他字段不变”叫修改范围条件。例如租户甲的读取请求不能顺便修改租户乙的操作账本。

这只适用于该次纯核心调用。服务为了持久记录到期观察，可能先提交一个时间推进事务，再拒绝后续准入；不能扩大为“每个失败的外部请求都不改任何状态”。

全系统一步 `Σ —a/o→ Σ'` 则包含控制器步、数据库步、宿主步、网络步和崩溃步。一个 Rust 处理函数可能对应多步，不能把整个处理函数假设成原子操作。

### C4 公共检查的精确定义

下列谓词展开为字段比较，而不是“状态合法”这样的占位条件：

```text
Own(u,s)           := sandboxes[s].owner = u
Current(s,e,g)     := sandboxes[s].epoch = e ∧ sandboxes[s].generation = g
Fence(s,e,t)       := worker_fences[s] = (e,t)
VmBound(s,g,v)     := vms[v].sandbox = s ∧ vms[v].generation = g
                     ∧ vms[v].owner = sandboxes[s].owner
SlotBound(s,g,v,n) := net_slots[n] 的 owner、sandbox、generation、vm
                     分别等于 sandboxes[s].owner、s、g、v
CurrentAttempt(x) := logical_effects[x.logical].current_attempt = x.attempt
ExactPlan(x,p)    := x 的完整命令参数与 p 中该动作的身份、策略、资源选择相等
```

再定义 `AttemptExecutable(x)`：存在该尝试记录、其逻辑工作未终结、该尝试是当前尝试，且尝试状态属于该入口允许的执行状态。派发、观察和应用成功各自使用独立的允许状态集合，不能统一替换为同一个“可重试”判断。

例如工作更新入口要求 `x ∈ inflight`，且 `effects[x]` 为 `Dispatched` 或 `OutcomeUnknown`；派发入口则接受 `Committed` 或 `OutcomeUnknown`。后者只是允许重新进入派发协议，不是对任意宿主副作用的重放许可。当前尝试与终局账本之间的关系还需由可达状态不变式连接，不能仅凭单个枚举值证明整体合法。

回执匹配使用完整尝试键，不仅是沙箱编号或结果摘要。旧代资源清理则使用其原绑定，不强制等于沙箱当前代次；否则旧资源会永远无法清理。

### C5 主要转换

| 规则 | 必要检查 | 状态更新与输出 |
|---|---|---|
| 接受创建 | 身份与参数通过；模板绑定有效；不存在冲突的原操作；标识和预算足够；未跨过退休高水位 | 同一事务建立启动状态、关闭授权、完整创建输入、固定资源计划、启动期限及清理预算；只创建原计划工作 |
| 原请求重放 | 操作键、种类和完整输入相同；调用者有权查询 | 返回原结果或原等待状态，不分配新虚拟机；参数不同明确冲突；超过保留期按退休合同处理 |
| 预留和入队 | 当前操作与计划一致；计数器未耗尽；总账和后续收尾额度足够 | 一次分配计划中的原资源身份，建立逻辑工作和初始尝试 |
| 派发 | 原工作已持久提交；当前尝试允许派发；执行前提未失效 | 登记在途身份，再调用宿主；不能先产生物理副作用再补账 |
| 接受回执 | 完整尝试键、来源、状态、结果与所需证据匹配 | 保存该尝试结果；同一终局结果不可被迟到回执改写；推进合法后续工作 |
| 明确失败后重试 | 失败类别允许重试；有重试余额；新尝试编号可表示 | 同一逻辑工作的新尝试编号增加，余额减少；不新建替代沙箱 |
| 超时或丢回执 | 尚无可信终局结果 | 保持原身份，记录结果未知；不因此证明动作没有发生 |
| 发布运行 | 非终止启动状态；计划、虚拟机、网络、文件策略和各项成功证据匹配；启动期限未到 | 同事务发布运行授权、操作成功结果、首次运行时间及寿命；返回该实例而非重建 |
| 接受销毁或到期 | 请求有权，或可信内部到期事件重新核对期限；结果重放规则成立 | 持久终止意图，关闭新访问授权，更新控制轮次和终止围栏计划，安排原资源停止 |
| 发布销毁 | 终止状态和围栏一致；资源索引中虚拟机已关闭；停止证据齐全；网络已关闭 | 发布终局销毁结果；移除当前运行引用；不据此直接声称所有磁盘已物理删除 |
| 创建失败收尾 | 原创建已进入补偿；错误种类和相关证据有效 | 保持终止与关闭授权，停止或撤销原准备工作；满足失败发布条件后保存失败结果 |
| 清理及释放 | 原对象身份一致；不再是当前资源；工作、连接、辅助进程和引用已排空 | 精确清理、保存释放见证、返还相应额度，最后允许位置复用 |
| 历史退休 | 操作终结；资源和引用满足退休条件；保留结果容量可用 | 用有界终局摘要和高水位替代活跃历史；不恢复旧身份的准入资格 |

上表是证明分解，不把整行视为一个真实原子步骤。数据库事务、宿主动作和回执分别建模；只有实际同事务提交的字段才能共享一个提交点。

### C6 十二种命令中的九种产品命令

[工作处理函数](../controller-core/src/worker.rs)的命令集合有十二种。本功能子集启用以下九种；冻结、封存快照、提交快照三种不启用。

| 命令 | 核心接受条件的关键字段 | 宿主侧必须建立的事实 |
|---|---|---|
| `InstallFence` | 沙箱、控制轮次、终止标记与合法操作相符 | 旧工作不能越过新围栏产生新的授权副作用；与已经开始的工作正确协调 |
| `PrepareVm` | 启动且非终止；轮次和代次当前；计划封定且资源选择相同；非终止围栏已装；逻辑资源不存在 | 原身份目录、磁盘和启动登记成立；部分准备也可识别与清理；无快照来源 |
| `ConfigureNetwork` | 当前启动；原虚拟机与网络位置完整绑定；完整策略相同；围栏匹配 | 原网络空间的实际规则等价于获批策略，失败不放宽网络 |
| `ApplyFilePolicy` | 当前启动；工作区、代次和策略匹配；围栏匹配 | 实际工作区隔离与文件策略符合本功能子集定义，不能只写一个“已应用”标记 |
| `ActivateVm` | 当前虚拟机已准备；网络已配置；当前非终止围栏；该沙箱没有其他执行中虚拟机 | 对原虚拟机完成启动及约定初始化，获得同身份就绪证据；不是只看进程存在 |
| `StopVm` | 原资源绑定；本子集中为终止撤销状态；匹配终止围栏 | 精确进程及约定执行资源停止，原网络访问关闭；发送终止信号不等于已停止 |
| `AbortPrepare` | 创建补偿；封定原计划含该虚拟机和网络资源；终止围栏；核心尚无对应资源记录 | 已检查并收尾可能存在的部分物理准备；核心“尚无记录”不等于物理上从未创建 |
| `CleanupVm` | 原沙箱与代次匹配；状态已停止；不再是当前虚拟机 | 仅删除原对象；目录替换、观察错误或仍有使用者时不能宣告释放 |
| `CleanupSlot` | 原沙箱与代次匹配；未激活、未回收、不再当前引用 | 原网络资源及关联引用排空后精确回收 |

上述宿主事实不是现有纯核心更新能单独证明的。需要宿主模块定理将真实证据翻译为核心工作成功输入。

对 `ApplyFilePolicy`，本子集是每实例私有可写系统环境和受控宿主路径，不额外承诺来宾 root 不能改自己的文件权限。策略编号是身份标签；若要证明任意目录级权限策略，必须另外定义其文件访问判定函数，不能从编号相等推出权限语义正确。

### C7 未知结果不能用重试掩盖

只允许两种推进未知工作的办法：

1. 观察原资源，获得足以确认该工作后果的证据。
2. 对特定命令证明重复执行保持相同效果，且不会重复非幂等副作用，再重放同一身份的动作。

“幂等”必须是逐命令定理：执行两次与一次在允许观察上等价。它不能自动用于用户命令、追加文件或镜像中的启动程序。初始化连接可以重试，不表示其中的任意启动命令可以重跑。

未知激活在原虚拟机已被精确停止后，可以被 `RetiredByStop` 覆盖退休。这证明“这次未知激活不再能使实例运行”，不证明我们知道它历史上究竟有没有成功。

核心的工作结果检查使用逻辑资源状态。例如逻辑成功结果尚未出现，是某些失败回执的核心检查条件；它不自动证明物理副作用从未发生。真实适配器必须给出独立的明确失败证据；观察不到或回执丢失只能产生未知，不能借用逻辑记录缺失来伪造失败。

### C8 终止不是一个瞬时事件

定义三个不同时间点：

```text
t_intent：终止意图和关闭新访问授权提交。
t_fence ：宿主执行围栏生效，旧启动工作被阻止或已纳入停止集合。
t_drain ：已登记的数据通道与辅助执行全部排空。
```

需证明：`t_intent` 之后不授予新许可；`t_fence` 之后旧工作不能再产生新的运行；`t_drain` 之后旧连接不再转发新的字节。已经进入网络或客户端缓冲区的字节仍可能稍后被读取，不能承诺“用户点击销毁后世界上立即没有任何字节到达”。

### C9 完整规则示例 失败后的新尝试

以 `Retry(logical,failure)` 为例，令 `l` 为逻辑工作记录，`a = l.current_attempt`，`x = (logical,a)`。按顺序检查：

| 顺序 | 必须满足 | 否则拒绝 |
|---|---|---|
| 1 | 控制器存活 | `ControllerDown` |
| 2 | 存在逻辑工作 `l` | `LogicalEffectNotFound` |
| 3 | `l.result = None` | `LogicalEffectAlreadyFinal` |
| 4 | `effects[x] = Acknowledged(Failed(observed))` | `CurrentAttemptNotFailed` |
| 5 | `observed = failure` | `FailureMismatch` |
| 6 | `failure` 属于期限、资源、存储或内部失败 | `FailureNotRetryable` |
| 7 | `l.remaining_retries > 0` | `RetryBudgetExhausted` |
| 8 | `a < 2^64 - 1` | `CounterExhausted` |
| 9 | `effects[(logical,a+1)]` 不存在 | `NextAttemptExists` |

全部通过后，令 `y=(logical,a+1)`：

```text
logical_effects'[logical] = l[current_attempt := a+1,
                            remaining_retries := l.remaining_retries-1]
effects'[y] = Committed
effect_keys' = 将 y 不重复地加入原索引
inflight' = 将 y 不重复地加入原在途集合
输出 = StartNextAttempt(x,y)
```

原尝试 `x` 的失败记录保留；其他工作、资源、授权、计划和全局编号不变。拒绝时上述字段全部不变。

这条规则的证明至少包含：接受当且仅当九个检查通过；失败错误是最先失败项；新尝试与原逻辑命令相同但编号不同；重试额度恰好减少一次；不会把未知结果变成可重试失败；计数不回绕；保留状态不变式。

该示例对应[真实重试入口](../controller-core/src/effect.rs)，但“与代码逐行相同”本身不是安全理由；还需独立证明这些检查足以维护附录 G性质。其余规则应以同样粒度形成定义与定理，而不是用“执行适当检查”代替。

### C10 中心与节点的协议步骤

中心只使用高级生命周期/查询操作，节点连接原本地核心。以下区分实际可并发/失败/崩溃的步骤，不把一整行视为跨库原子事务。

| 步骤 | 必要合同 |
|---|---|
| CenterCommitIntent | 同次保存身份、固定节点、参数、预留/收尾、意图及 outbox；失败/未知不派发候选状态 |
| CenterSend / NetworkDeliver | 仅发送确认耐久的原操作；可重复/延迟/丢失/乱序，重发不新分配 |
| NodeAcceptHighLevel | 核验证书映射、部署/节点代际/租户/绑定/窗口/意图；持久原本地映射；同键异参数拒绝 |
| NodeLocalAdvance | 运行既有本地算法，部分效果/未知保留原身份；传输失败不等于未执行 |
| NodePersistFact / SendFact | 先保存事实及版本，再回报接受/就绪/停止/清理等不同事实 |
| CenterApplyFact | 核对来源、全身份、操作/观察版本和终止状态；耐久保存原结果，迟到事实不回退 |
| CenterConfirmRecorded | 只在中心相应耐久提交后产生接收确认；发送确认不等于已经投递 |
| NodeRetire / CenterRetire | 各自满足责任、保留、窗口与引用合同，不因发送或心跳到期即遗忘 |
| Crash / Restart / CommitUnknown | 保留各自持久状态、真实资源及可能已发生的投递/副作用 |

协议编码、具体端点和截止裕量由[模块合同](module-contracts.md#中心与宿主的高级操作合同)在实现首批冻结；这些是语义事件，不强制每项新增 HTTP 端点。中心操作、节点高级操作、本地工作/尝试不是同一编号。无外部幂等键的两次公开 create 不自动合并；可靠派发不为任意用户命令/文件写提供 exactly-once。

**公开创建的已知限制**：中心内部 operation_id 只保护同一已接受操作的派发/恢复；用户未收到创建回复时，再发无幂等键的 create 可能得到第二个沙箱。metadata/list 查询不能原子地排除原请求稍后提交，客户端也可能根本收不到服务端生成的编号。因此当前不承诺用户能安全重试并找回唯一原创建。可选公开幂等键及经授权的操作查询是未来候选，须另经 owner 确认，不加入 #292 基本兼容或 #101 首条证明链路的必做接口。[E2B 公开幂等需求 #1658](https://github.com/e2b-dev/E2B/issues/1658)

## D 授权查询网络和寿命

### D1 获得许可不等于一直有许可

对用户 `u`、请求 `r` 和时刻 `t`：

```text
CanGrant(u,r,Σ,t) := Authenticated(u)
  ∧ Own(u,r.sandbox)
  ∧ phase = Running ∧ ¬terminal ∧ t < deadline
  ∧ effective = Running(与 r 完整一致的绑定)
  ∧ 请求能力属于该授权 ∧ 数据通道预算允许
```

网关授予许可和登记在途连接必须与撤销协调。若先检查许可、后无限延迟登记，销毁可能以为已经排空，再出现旧连接。这是并发顺序的证明义务，不是再加一次普通查询就能证明。

保密性质只包含明确的观察：管理响应、错误类别、列表字段、网关有效载荷和公开计数。不承诺执行时间、共享容量变化或硬件旁路不泄漏信息。

### D2 列表不是另一份数据库

定义 `Visible(u,t,K,J)` 为调用者拥有、按合同可见且未到期的实例集合。每一页结果定义为：

```text
Page = Take(page_size,
         AfterCursor(cursor,
           Sort(order,
             Filter(query, Visible(u,t,K,J)))))
```

过滤先于排序和分页；默认按启动时间降序、同时间按外部编号升序，升序反转两个键。元数据各项同时精确匹配，时间边界按合同精度比较。运行总数在游标和页大小之前计算，不能泄漏其他租户数量。

游标是排序位置，不是授权凭据。它绑定方向和排序键；游标目标后来删除，不妨碍按键继续翻页。每次翻页重新检查当前归属和可见性，不承诺并发修改期间得到数据库快照。非法游标、越界页大小和不支持的筛选值按固定合同明确处理。

### D3 地址策略是可执行判定函数

对 IPv4 目的地址 `d`，定义平台禁止集合 `P`、用户允许集合 `A`、用户拒绝集合 `D`、默认公网开关 `I`：

```text
AddressAllowed(d) := d ∉ P ∧ (d ∈ A ∨ (I ∧ d ∉ D))
```

这表达平台禁止优先，用户显式允许高于用户拒绝，显式禁网仍可配合允许项。网段匹配须证明规范化及边界位数正确。平台集合及控制通道例外按部署合同固定，不能由用户允许列表覆盖。

真实网络定理不是“配置文本长得对”，而是：

```text
GuestEgress(packet,b) ⇒ 属于明确的控制通道例外
                       或 AddressAllowed(packet.dst)
```

还需证明来源绑定、路由、地址转换、返回流量和规则安装时序不会绕过该判定。地址授权不等于协议内容授权：允许访问某个 DNS 解析地址，不能推出 DNS 查询中没有数据外传；允许加密网页访问，也不能推出其中没有承载其他协议。

IPv6 放行和 DNS 查询内容策略不在本次功能范围，但“不支持”不能等于“留下不受控出口”。网络安全定理必须覆盖未启用协议被阻断、或该部署没有相应出口的条件；否则只能声称 IPv4 路径受限，不能声称整个沙箱无旁路联网。

### D4 寿命和时间

寿命不是一个 `timeout` 字段，而是几种不同期限。令 `a` 为创建准入时间，`s` 为首次持久发布运行时间，`d` 为获批可用时长，`D_start` 为启动等待上限，`D_max` 为实例总寿命上限：

```text
启动截止 = a + D_start
首次运行发布要求：now < 启动截止
初始可用截止 = s + d
总截止 = s + D_max
```

创建和连接省略寿命使用固定合同的 300 秒；创建必须通过单次和总寿命上限，不静默缩短。连接只延长原实例，设置寿命允许缩短。对已经通过对应前置检查的请求：

```text
connect：deadline' = max(deadline, min(now + d, 总截止))
set_timeout：deadline' = min(now + 有符号时长, 总截止)
```

非正设置结果可立即到期；算术在足够宽的域中计算，转换回持久类型时检查范围。创建或连接的参数拒绝、已到期、正在撤销、外租户与不存在的错误区别由模块合同决定。

到期扫描读取的实例列表只是候选。真正接受到期销毁时，必须在事务内重新比较最新截止，避免续期后仍被旧扫描结果杀死。重启加载已经提交的期限，不根据新配置重新延长。

持久时间下界只防止逻辑时间倒退，不能证明物理时钟正确。若只假设逻辑时钟单调，能证明“观察到到期后不再授予许可”；若要证明“现实时间截止后最多 Δ 毫秒关闭”，还需要时钟误差、扫描延迟、调度及撤销耗时的上界。没有这些上界，就不能把条件最终完成性写成实时承诺。

### D5 两端授权、全局查询和跨机时间

中心从认证上下文产生 tenant_id，依据权威绑定/意图/期限授予新资格，路由只来自受保护登记。节点实际派发再次核对本地映射、VM、许可、围栏和寿命。两端分别证明，不用中心曾经通过代替节点当前资格，也不每块数据运行全局控制转换。

全局 get/list 先在同一中心权威视图筛选，再排序/分页，不能拼各节点第一页。节点事实带身份和观察版本；需要当前确认而无法获得时返回约定未知/不可用，不把心跳/旧 Ready 当当前健康证明。

运行起点来自节点首次持久发布就绪，中心晚收不重算。续期意图与参数固定，节点持久应用后才公开确认成功；重放不反复从新的 now 增加时长。本机到期独立执行，失联不延长期限。

中心终止提交后不授予新的中心资格；节点收到并持久落实后撤销本地资格，围栏与排空另有事件。分区期间不承诺中心提交瞬间所有来宾停止。各机时钟误差/裕量为冻结部署前提，单位、溢出、重启和续期/到期竞争属自有义务，不假设时钟相同。

### D5.1 查询的可观察顺序

本条细化 S10/S12、F1/F2 与 G3 的查询合同，不新增公开 SDK 字段。

- 成功的管理查询须对应本次调用开始与结束之间某个合法的、已提交的中心权威视图；不能任意返回调用前的历史缓存。单次 list 从同一视图筛选/排序/分页，跨页仍不承诺快照。
- 若成功续期回复已经返回，之后才发起的查询不得返回该次续期之前的旧期限；允许更晚合法续期、到期或终止改变结果。并发调用按其合法提交/观察顺序解释，不能仅比较网络回复到达先后。
- 中心提交的意图版本与节点事实的身份/观察版本分别记录。旧事实不得覆盖较新的期限/终止决定；最近一次节点观察不是当前物理健康的证明。必须实时确认却无法确认时按固定错误合同返回未知/不可用。
- 证明自己维护的视图、缓存失效及结果投影与权威提交对应，不直接假定“所有副本一致”；仍不承诺分区下全球实时健康、跨机同一时钟或完整跨页快照。

最小正常轨迹：续期耐久落实并确认 → 发起详情查询 → 返回该续期或后续合法决定的期限。禁止轨迹：已经确认续期，随后另一入口从旧缓存返回原期限。工程冻结输入/错误及观察点；形式化证明所有允许交错，不只证明这一例。[E2B runtime #2217](https://github.com/e2b-dev/runtime/issues/2217) 提供多入口期限不一致的用户报告，不能据此认定其具体根因已证实。

## E 数据完整性的精确定义

### E1 先定义观察位置

对一次传输 `x` 和某个方向，定义：

- `Source(x)`：按协议解释后的源端有效载荷，不含传输编码的长度头。
- `Read(x,t)`：网关截至 `t` 已成功读取的有效载荷字节序列。
- `Written(x,t)`：网关截至 `t` 已成功交给目标连接的字节序列。
- `Observed(x,t)`：目标协议接收方已交付给调用者的字节序列。

`Written` 不等于用户已经读到：套接字写入成功可能只是进入缓冲区。需要端到端交付结论时，定理必须量化接收方观察或依赖相应接收协议合同。

这些完整字节序列是证明用历史；真实网关不需要把它们全部缓存在内存。实现状态只保存有界缓冲、计数、解析进度和连接身份，由表示关系连接到历史。否则为证明“内存有界”而先在实现中收集整个输出，会与目标矛盾。

记 `a ⪯ b` 表示 `a` 是 `b` 的前缀。对不修改有效载荷的方向，所有中间状态要求：

```text
Written(x,t) ⪯ Read(x,t) ⪯ Source(x)
Observed(x,t) ⪯ Written(x,t)
```

对流式源，`Source(x)` 表示该次执行中实际由源产生的序列；它不包含源端本来“打算产生”但从未产生的数据。这些前缀关系证明不伪造、不重排、不重复，但**不能单独证明没有截断**。

### E2 完整成功必须是相等而非前缀

定义 `CompleteFrame(x)` 为协议声明的正文完整结束；`NoGatewayFault(x)` 表示未超限、未取消、未超时、未发生读写失败；`BoundTo(x,b)` 表示全过程使用原实例绑定。

需要建立的网关完成定理为：

```text
GatewayCompleted(x)
  ⇒ CompleteFrame(x) ∧ NoGatewayFault(x) ∧ BoundTo(x,b)
     ∧ Written(x,end) = Read(x,end) = Source(x)

ClientObservedCompleted(x) ∧ 接收端协议合同
  ⇒ Observed(x,end) = Source(x)
```

等长不够，还要逐字节相等；内容相等也不够，还要实例身份正确。把甲的完整文件发给乙，不是正确传输。

若上传和下载采用协议解码，则比较解码后的载荷；HTTP 分块重新分组可以改变线上的表示，但不能改变有效载荷、必要尾部字段或业务结束事件。UTF-8 字符可能跨块，应先证明字节正确，再证明增量解码；不能逐块独立解码后丢弃残缺字符。

### E3 HTTP 结束和业务结束不同

| 响应类型 | 完整性的判据 |
|---|---|
| 声明长度为 `n` 的正文 | 按协议接收恰好 `n` 个正文八位字节；提前断开不是完整 |
| 分块正文 | 每块完整，出现合法结束块，并完成尾部和最终分隔；断流不允许补造结束块 |
| 仅靠连接关闭结束 | 单靠连接关闭，无法区分正常结束与中途故障；不能据此证明源端意图的数据全部产生 |
| Connect 流式调用 | 帧头、长度和载荷完整，最终结束帧合法，业务错误按结束帧解释；HTTP 200 本身不表示调用成功 |

这些差异来自协议本身，不是增加重试就能消除。[HTTP/1.1 消息长度与不完整消息](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)、[Connect 流式协议](https://connectrpc.com/docs/protocol/#streaming-rpcs)

Connect 帧为一个标志字节、四字节大端长度及相应载荷；响应必须有最终结束帧。网关若只透明转发，可证明帧字节和传输错误不被改写；固定客户端对结束帧的解释仍属于端到端合同，不能假称网关自己已经验证了退出事件。

因此，无长度、无可信业务结束标记的上游流，最多证明“网关没有丢弃已经收到的数据”。若希望也承诺源端完整性，需要长度、可信完成标记或更强的源端合同；本设计不借此擅自修改现有兼容接口。

### E4 超限和超时必须保留失败

设允许有效载荷上限为 `B`。对正常成功，要求 `|Source| ≤ B`；对超限传输，允许转发一个有界前缀，但必须结束为错误、取消或未知，不能结束为成功。

特别禁止：

- 把原本 100 字节的长度改写成上限 80，再返回 80 字节“完整成功”。
- 到上限后伪造正常流结束，补上空结束块或成功结束帧。
- 已经发出 HTTP 200 后，把后续错误静默吞掉；此时必须由正文或协议错误让客户端观察到失败。
- 为释放并发名额提前结束计费，但连接、缓冲或辅助进程仍然存活。

预算必须注明计量对象：线上的编码字节、解码后字节、单帧大小、累计载荷、同时在途缓冲分别是什么。若不支持压缩则明确拒绝；不能只限制压缩前或压缩后其中一层，却声称两层内存都被限制。

### E5 文件正确性

对覆盖写入请求，令请求字节为 `B`，目标实例和路径为 `(b,p)`，`t_commit` 为 envd 合同中的写入完成点。功能定理应写成：

```text
A_function ∧ 完整上传 ∧ 对 (b,p) 的成功写入确认
∧ 相应期间没有其他写者修改该目标
  ⇒ FileContent(b,p,t_commit) = B ∧ FileLength(b,p,t_commit) = |B|
```

长度条件排除“写入了正确前缀，但旧文件尾巴还在”。空文件同样是合法的 `B = []`。若存在其他写者，只能陈述本次操作在其约定完成点的语义，不能保证稍后的文件内容仍相同。

这不是断电持久性证明，也不是写失败自动回滚证明。上传断开后文件可能已有前缀；结果未知时不自动重新写入。下载也不默认是并发写入下的原子快照：其源序列按 envd 的读取合同定义。

来宾路径不得被当作宿主路径使用。对宿主文件的安全命题是：“客户提交的文件请求只能进入获批实例的文件服务，不能改变宿主文件操作目标”；这与来宾内部是否允许访问 `/etc` 是两件事。

### E6 命令正确性

一次前台命令完成结果定义为：

```text
CommandResult = (原命令身份，标准输出字节，标准错误字节，退出状态)
```

在 `A_function` 下，结果对应原命令，两个输出流各自顺序保持、没有丢字节，而且结束前已交付该协议承诺的输出。除非协议本身记录全局顺序，不额外承诺标准输出和标准错误之间的精确交错。

退出码非零是命令正常结束的一种结果，不必然是网关故障。后台命令返回进程编号只证明启动确认；执行完毕需另一个完成事件。超时、终止或断线可以发生在命令已产生副作用之后，不能据错误自动重发命令，也不能把“等待结束”当作“进程已被确认杀死”。

### E6.1 命令句柄、终止范围和 envd 重启

本条细化 E6、S1/S4/S9、F2 与恢复合同；不把整个 envd 或 SDK 实现加入自有证明范围。

- 固定 SDK/envd 合同必须分别说明：命令主进程退出/被终止、进程组或后代进程停止、整个 VM 被停止。三者不能互相代替；不默认单命令超时/kill 会杀死全部后代，也不因此新增更强的进程组终止功能。
- Start/Connect 的命令身份和句柄绑定原实例及 envd 的有效执行会话；来宾 PID 只是该合同内的句柄，不是永久身份。Connect 返回哪些历史/新增输出、何时算结束须固定。重连或等待期限不得被当成重置原执行期限，也不得自动重新执行有副作用命令。
- envd 重启可能丢失命令登记而 VM/来宾进程仍在。此时按固定协议报告不可重连/未知，不仅凭相同 PID 接管旧命令；空进程列表不能证明来宾全部进程停止。控制器保留原 VM 身份/绑定/占用，宿主停止与精确清理不以 envd 正常响应为前置。
- 自有入口/路由/转发/撤销和失败处理必须证明；原命令的真实输出、端点完成事件及承诺的回调排空依赖明确的功能端点合同并做兼容测试。不能把端点故障伪装为正常完成，也不能声称已证明 SDK 客户端全部回调或来宾业务结果。

最小正常轨迹包含原命令开始、重连及合法完成；禁止轨迹包含“等待超时就报告已杀死全部后代”和“envd 登记丢失后仅凭 PID 自动重执行/接管”。使用受控端点故障先检查自有处理；真实端点测试只核对已冻结合同，不复现所有上游缺陷。[E2B #1031 的子进程案例](https://github.com/e2b-dev/E2B/issues/1031#issuecomment-5581469733)、[runtime #3650 的 envd 失效报告](https://github.com/e2b-dev/runtime/issues/3650) 是不同版本的边界线索，不代表当前我方环境已复现。

### E7 数据转发也有可执行的小状态机

每个方向定义实际状态：

```text
StreamState = (原绑定，许可阶段，源结束状态，目标写入状态，
               已读计数 nr，已写计数 nw，有界待写缓冲 q，协议进度，期限)
```

在非错误中间状态，需要 `0 ≤ nw ≤ nr`、`|q| ≤ M`，并且逻辑上 `Read = Written ++ q`。只有带累计预算的操作才另要求 `nr ≤ B`：文件、一元回复和宿主辅助输出各有 `B`；用户命令 Start/Connect 输出没有累计 `B`。`M` 是在途缓冲上限，不由执行期限替代；多级队列的 `q` 是其有序组合，`M` 须覆盖各级及明确的库/内核缓冲前提。证明侧计数可用自然数，不能要求实现保存全历史或使用会溢出的无界累计机器计数。

| 输入事件 | 接受条件 | 更新 |
|---|---|---|
| `ReadChunk(bytes)` | 原许可允许继续、源未结束；需要的机器计数可表示；缓冲预算及本操作适用的累计预算足够 | 在 `q` 末尾追加原字节，增加 `nr`；不能跳过已有待写字节 |
| `WriteAccepted(n)` | 底层确认接受 `q` 的前 `n` 字节，且 `0 ≤ n ≤ |q|` | 从 `q` 移除恰好这段，`nw` 增加 `n`；短写后继续处理剩余部分 |
| `SourceEnd(evidence)` | 该方法和传输编码的完整结束判据成立 | 标记源完整结束；`q` 非空时仍需排空，不能立即完成 |
| `BudgetExceeded / ReadError / WriteError / Deadline / Revoke` | 事件真实发生，原请求身份匹配 | 记录相应失败或取消；不补造源结束；部分副作用仍保留其未知性 |
| `Finish` | 源完整结束、`q` 为空、无错误、需要的业务结束证据成立 | 产生相应层次的完成事件，最后释放在途登记 |

流完成与整个连接、辅助进程排空分开记账；双向流一侧正常结束只关闭该方向，不提前截断另一侧响应。若解析库或套接字库还有内部缓冲，资源证明必须将它们的固定合同上界计入 `M` 或另一项预算，不能因为不在自定义结构体里就忽略。

从以上事件证明前缀关系和完成相等，再证明实际异步循环产生同样事件，才是“Rust 网关不会把截断当成功”的完整路径。直接假设网关存在正确的 `Completed` 标记，会把待证明内容放进前提。

## F 故障恢复和资源边界

### F1 提交点决定责任何时成立

本节本地 `Accepted_node(op)` 表示完整输入、计划、预算和期限的本地事务已提交；中心 `Accepted_center(op)` 由 C10 的中心耐久准入定义，两者不能合并为一个跨库提交点。原局部公式中 `Accepted(op)` 按本地责任解释；系统接受与节点责任连接见 F7。对任意宿主派发事件：

```text
Dispatch(x) ⇒ 之前存在 DurableCommitted(x, exact_plan)
```

对创建、销毁等需要持久终局结果的生命周期操作，其完成响应必须满足：

```text
SuccessReply(op,result) ⇒ 之前存在 DurableFinal(op,result)
```

这不要求为每次查询或命令输出建立终局账本。查询响应对应某个允许的已提交视图；续期成功对应期限提交；文件和命令结果遵守附录 E的数据与端点合同，不能把它们误归为控制器持久生命周期结果。

响应丢失不会撤销提交。提交返回错误但结果不明时，状态是“提交前或提交后，尚待核实”，不能立即分配第二组资源。

### F2 必须覆盖的崩溃位置

| 崩溃位置 | 恢复必须允许的真实情况 | 合法推进 |
|---|---|---|
| 意图事务提交前 | 没有接受该操作 | 不派发；按原身份检查是否实际已提交 |
| 提交后、派发前 | 有持久责任，没有物理效果 | 派发原尝试 |
| 宿主登记后、资源创建中 | 有部分目录、磁盘或网络 | 按原登记观察，继续可安全重放的步骤或精确清理 |
| 虚拟机已启动、回执未写入 | 实际运行，账本仍未知 | 观察原虚拟机，确认原结果或停止；不新建替代实例 |
| 回执已存、运行发布前 | 所需事实可能已有持久证据 | 重查发布前提和期限，发布原实例或进入补偿 |
| 终止提交后、停止前 | 新许可关闭，原进程可能仍运行 | 安装终止围栏，排空和停止原资源 |
| 已删除资源、释放记录未提交 | 物理已无，但额度仍占用 | 原身份范围内确认不存在，再提交释放；不误删同名新对象 |
| 检查点或退休处理中 | 旧表示或新表示之一仍有效 | 选择完整有效表示恢复，不拼接两个版本 |

### F3 数据库表示关系

定义：

```text
Decode(检查点, 连续的已提交日志尾部) = K
Cache.version = Commit.version ⇒ Cache.state = Decode(Commit)
```

需要证明日志顺序、缺口检查、模式版本、错误分支、检查点切换和退休保持这一关系。序列化只证明编码可读不够，还要证明它保存的是对应提交的完整状态。

重启不能混用新数据库核心与旧缓存凭据、旧宿主路线或重新解析后的模板别名。全局存储损坏可以导致拒绝启动；单个实例凭据读取失败应只拒绝该实例的数据授权，而不是让其他健康实例统一失效。

### F4 资源不是一个磁盘剩余量数字

用资源向量表示预算：

```text
R = (实例数，处理器额度，宿主内存额度，磁盘未来增长，inode 数，
     宿主位置，控制记录，保留结果，网络连接，辅助进程，传输缓冲)
```

对每类资源 `r`，要求：

```text
Charged(r) + ReservedForUnfinishedWork(r) + ReservedForCleanup(r) ≤ Limit(r)
```

尚未确认清理的资源仍收费。逻辑磁盘的稀疏空洞只减少当下占块，不减少未来写满的责任；不能只按当前已用块数准入。数据库还需计入日志、检查点替换、索引和单事务峰值，而不只是主文件。

来宾内存大小也不等于整个宿主开销；进程、虚拟化线程和日志等需要独立限额或明确的外部上界。Firecracker 官方要求关注日志资源与宿主线程等部署因素。[生产宿主要求](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/prod-host-setup.md)

上式首先是逻辑预算定理。要推出真实峰值受限，还需逐项证明实际占用不超过模型计费，并声明非受管进程不会抢占预留空间的部署条件。资源检查本身不能创造磁盘，也不能保证任意宿主负载下不出现内存不足。

### F4.1 驻留结构和连接的完整计费

本条细化 F4/F6、S8/S14 及 G3 的容量责任，不恢复用户命令累计输出上限。

- 逐项纳入受管常驻结构：零计数键、已结束订阅者、请求/响应关联表、连接池、取消监听、排队/重试任务及库内在途队列。记录的值为零或业务结果已结束，不代表对应键/对象不占空间。
- 对每类结构给出“活跃对象 + 在途对象 + 显式保留窗口/结果 + 固定开销”导出的条数及字节上界，绑定实际分配和回收入口。可能无限增长的 unknown 责任不得丢弃，必须占用有限预算并限制新准入。
- 各类连接/许可按其合同覆盖所负责的完整正文、流、后台执行及实际退出/排空；收到 HTTP 响应头、发送取消或超时不能直接当成释放。自身退出路径须解除订阅和引用；有未确认效果时按合同保留责任。
- 零计数驱逐、池回收和后台任务退休必须与并发引用/计费原子配合，不能拆掉正在使用的计数器或遗失未决关联。模型计费到实际驻留的连接是自有证明义务；分配器、运行库、内核、envd 的剩余开销分别声明版本/配置和外部上界，并由工程测试核对。
- 持续命令输出只约束顺序、单消息/在途缓冲和并发，不约束累计字节；客户端 SDK 累积输出的内存不属于宿主内存定理。有限键数也不能单独推出整个进程内存上界。

最小正常轨迹在固定活跃/在途/保留预算下反复创建、连接、断线、销毁和退休，结束对象与订阅按合同回收。禁止轨迹是活跃计数不变但已结束键/订阅随总请求数无限增加，或只收响应头就退还仍在传输的许可。复用既有长期容量与慢流样例，不扩展为所有库的穷举压力测试。[runtime #3448](https://github.com/e2b-dev/runtime/issues/3448)、[E2B #1666](https://github.com/e2b-dev/E2B/issues/1666) 提供驻留键与许可生命周期的审查线索。

### F5 位置复用的前提

定义原绑定 `b` 的释放条件：

```text
Quiescent(b) := 原虚拟机和受管辅助进程均停止
  ∧ 无在途旧工作能重新创建原资源
  ∧ 无已登记数据连接或许可使用原位置
  ∧ 原网络与文件资源已精确清理
  ∧ 无阻止释放的模板、验证或维护引用
```

位置从释放中变成可复用，要求 `Quiescent(b)` 的可靠证据；直到新绑定提交之前，还必须保持该条件。随后新虚拟机身份不同于原身份，并匹配该位置记录的上次绑定。

`ConfirmRelease` 这样的纯输入本身不是物理释放证据。调用它的适配器必须证明上述前提，且处理核对与提交之间的竞争。

阻止释放的引用也需要有无环的解除条件。例如验证或构建引用若依赖逻辑终态清理完成即可结算，就不能再要求先物理 `Free` 才解除，否则“引用阻止 Free，Free 又阻止解除引用”会使最终完成性为假。这里验证控制核心对引用的使用与释放顺序，不将整个模板管理子系统纳入证明范围。

### F6 长期运行的真实承诺

历史退休保存足够的结果和高水位，使旧请求不能复活。结果保留期结束后，允许返回“结果已过期”等合同规定结果，而不是无限保存每次操作。

有界编号与有界记录下可以证明“耗尽时安全拒绝，仍保留清理能力”；不能证明“永远接受无限个新实例”。最终完成性也不能靠假设资源永不耗尽掩盖自身账本泄漏。

### F7 两层持久化、故障和责任守恒

中心 DecodeCenter(完整 Redis 权威提交)=Cc，节点维持 F3 的检查点/连续尾表示。两者不共享原子事务。中心 CAS 单条更新、编解码、耐久确认和缓存修订需对应 A11；Lua 不被插入不等于多命令出错自动回滚。发生持久化错误后，内存读到原记录不足以确认耐久；按[中心持久化合同](module-contracts.md#中心持久化与恢复)恢复健康并确认包含原责任的耐久提交再派发。

新增故障点：中心提交回复丢失、节点已接受而回执丢失、节点事实已保存而中心未保存、中心已保存而确认丢失、两层退休中断。恢复使用原绑定/参数；失联不迁移/释额，Missing 不自动证明从未执行。

令 ReservationC(b,r) 为中心为绑定 b 保留的责任，ObligationN(b,r) 为节点该绑定可能仍有的占用及未完成/收尾义务。按统一计量证明 ObligationN(b,r) ≤ ReservationC(b,r)，并证明中心总和不超平台/租户/节点预算；两层账表示同一责任，不相加当双份物理资源。实际峰值另连接逻辑预算，未知/补偿不能丢预留。

节点事实退休由中心耐久确认及结果/窗口合同支撑，或保留足够有界退休信息，不能发出后即忘。两端保持高水位、过期窗口和终止记忆，旧请求拒绝；额度由原绑定充分清理证据释放，心跳到期不是证据。Redis/AOF、SQLite/WAL、日志、在途通信和收尾均计预算。

## G 目标性质和成立条件

令 `Reachable(Σ)` 表示从合法初始状态经过允许转换到达。`Always` 表示历史中每一点成立，`Eventually` 表示未来某一点成立。

下表既有本地字段/谓词按对应节点解释，公开入口/中心的对应责任按 D5 与 G3 连接。尤其 S3 的本地终止/围栏不能从中心终止提交直接推出；中心先禁止自身新许可，节点落实后的本地撤销及最终排空分别证明。

| 编号 | 正式性质 | 主要责任 |
|---|---|---|
| S1 身份完整 | `Reachable ⇒` 每个资源记录、索引、计划、尝试与所属实例的类型及身份一致；无冲突绑定 | 规则核心、持久服务 |
| S2 授权正确 | `Grant(u,r,b) ⇒ CanGrant(u,r,Σ,t) ∧ BoundTo(r,b)` | 请求入口、规则核心、网关 |
| S3 终止单调 | `Terminal(s)` 一旦提交，同一身份以后不能再次获得运行授权；旧工作不能越过生效围栏启动 | 规则核心、宿主 |
| S4 证据真实 | 成功工作、运行发布、停止、清理及释放各自蕴含该类事实的精确证据；未知不蕴含不存在 | 宿主、持久服务 |
| S5 结果不可改写 | `Final(k,r)` 与以后同键终局结果 `r'` 同时成立时，`r=r'`；迟到回执不能改变另一尝试 | 规则核心 |
| S6 持久责任 | `Accepted(op) ⇒` 未完成责任、原身份或合法退休结果持续可恢复 | 持久服务 |

| S11 策略落实 | 实际宿主资源与规则对应获批描述；真实出口满足所选策略判定 | 宿主 |

| L2 有条件清理 | 已终止且外部停止清理最终可完成时，原受管资源最终释放 | 持久服务、宿主、网关 |

### G1 保密是两条执行之间的关系

“每次鉴权都检查了”不等于已经证明无泄漏。定义 `Σ1 ≈u Σ2`：用户 `u` 自己可见的状态和允许公开的信息相同，其他租户私有状态可以不同。

在相同用户输入、相同公开资源条件及匹配外部调度下，要求：

```text
Σ1 ≈u Σ2 ⇒ Observations_u(T1) = Observations_u(T2)
```

必须明确哪些信息是公开的，例如共享容量不足可能是可观察结果；否则一边剩余容量足够、一边不足，响应不同就会使过强定理不成立。租户错误信息、列表总数、模板存在性和日志输出均需在规定观察集合中审计；时序和硬件旁路不包含在这个结论里。

### G2 最终完成性的条件不能代替证明

正常创建成功目标为：

```text
AcceptedCreate(op)
∧ 该操作不被取消且未到期
∧ 所需外部动作在允许期限内成功
∧ 已启用内部工作得到公平执行
  ⇒ Eventually RunningResult(op)
```

失败清理目标为：

```text
TerminalIntent(s)
∧ 外部停止、清理和持久写入最终可用
∧ 内部清理步骤得到公平执行
  ⇒ Eventually Quiescent(original_binding(s))
```

公平只表示持续可执行的步骤不会被永远忽略，不表示外部调用一定成功，更不表示一定在截止前完成。还必须证明：后续步骤真的被启用、前置条件在等待中不会被自己破坏、队列不会漏工作、重试预算不会形成循环、清理不会互相等待。

证明可用阶段顺序与剩余工作量的组合下降关系；加入工作可能暂时增加队列长度，因此不能简单声称“队列长度每步下降”。已有覆盖记录中的内部推进义务必须逐一解决，不能改名为“假设公平”后删除。

### G2.1 局部故障域与跨实例推进

本条细化 L1/L2 与 P8 的跨实例推进，不新增固定耗时 SLA 或要求本批完成 #284 的宿主并行重构。

- 冻结请求/通道局部、实例局部、真正共享依赖故障的分类及传播范围。单个坏请求、失效订阅或局部恢复错误不能通过自有错误传播/队列/引用/锁造成其他可独立处理实例无限阻塞；共享 Redis/SQLite 权威损坏则可安全停止相关全局推进。
- 中心决定锁不得跨远程 I/O 持有；本地串行实现仍须在约定期限和公平调度下释放等待/锁并继续处理，而非假定扫描器、锁和清理本身已经正确。永久不返回的外部调用若属于未满足的环境前提，必须明示其影响范围，不能承诺该条件下无限制推进。
- 进展前提只要求相关外部停止/观察/通信/存储最终提供所需结果和声明调度；内部工作启用、预算保持、队列取出、引用释放及无环等待必须实际证明。未知实例保留占用，不为让另一实例推进而误释额。
- 慢流/取消订阅在自己的网关中按预算解除引用并处理其他合格消费者。envd/SDK 的共享流广播和池行为作为细化外部合同及测试条件，不能用它们的局部修复声称整个外部程序已证明，也不能将自有阻塞改名为外部条件。

最小正常轨迹：A 的局部恢复/通道失败 → 按原身份保留或收尾 → 条件满足的 B 继续处理并完成清理。禁止轨迹：A 的错误导致整个恢复扫描永久退出，或一个已失效消费者通过自有结构永久卡住其他消费者。工程复用已有恢复/慢流测试，仅补确实缺失的故障分类样例。[E2B #1587 的弃用流讨论](https://github.com/e2b-dev/E2B/issues/1587#issuecomment-5058786818)、[#1641 的共享客户端池问题](https://github.com/e2b-dev/E2B/issues/1641) 是故障域依据，不是我方 SDK 全量证明任务。

### G3 分布式系统性质

保留 S1–S14、F1/F2、L1/L2，连接其局部版本与以下系统性质；不是只证明两个测试节点。

| 编号 | 系统结论 |
|---|---|
| DS1 唯一绑定 | 每个全局沙箱固定节点/代际与唯一原本地实例；无重试双跑/失联改绑 |
| DS2 全局责任 | 节点原资源及收尾义务由中心预留覆盖；平台/租户/节点预算不超界，未知不解账 |
| DS3 持久派发 | 高级派发有先行中心耐久意图，本地副作用有本地责任；未知提交不造新实例 |
| DS4 重放终止 | 同键同参数复用原结果；异参数/旧代际/过期窗口拒绝；迟到请求不复活终止绑定 |
| DS5 结果证据 | 对外成功有持久结果与真实证据；接受/就绪/停止/清理不同，旧观察不覆盖新事实 |
| DS6 两端隔离 | 身份、固定路由、本地资格与修改范围正确；同用户跨节点/同节点多租户不越权 |
| DS7 恢复退休 | 独立重启不丢另一层责任；确认/退休/窗口合同使旧请求不再次执行 |
| DS8 时间数据 | 原起点、续期和各终止阶段正确；两端中继维持原实例、完整性和有界驻留 |

I_global 是这些结论所需的归纳状态/历史约束，不只是终态检查表；保密仍按 G1 双执行关系，不能用单轨迹安全代替。

DL1/DL2 将 L1/L2 扩展到两端：单有效中心、必要存储/节点最终可执行、通信最终可提供原操作结果、停止/清理可用和声明调度条件下，接受工作最终有合法稳定结果及必要收尾。仍须证明工作被启用/不丢失、预算支持收敛和等待依赖无环；永久分区不保证完成。

## H 模块证明与真实代码对应

### H1 模块之间的证明接口

按保证及其前提划分。每个合同注明输入/输出、修改范围、成功证据、拒绝/未知、崩溃责任、版本和预算；纯比较用函数合同，生命周期用状态转换，通信/流用事件历史，不给每函数另建状态机。

| 模块 | 下游保证 | 不可假设掉的自有逻辑 |
|---|---|---|
| 公开入口 | 完整输入、认证租户、结果/错误/可见投影 | 解析、身份、单位/默认、错误映射 |
| 中心控制 | 唯一固定节点、合法预留、原意图/版本及窗口终止 | 调度、全局检查、有界数值、退休 |
| 中心持久协调 | 原子接受、耐久后派发、原结果与恢复 | CAS/Lua/编码、未知、缓存/outbox、确认/退休顺序 |
| 协议/节点入口 | 编解码保真、认证绑定、原本地映射与拒绝 | 证书映射、版本/窗口、参数比较、持久接收/终止 |
| 本地控制/持久化 | 既有 World 转换、本机责任/寿命/预算/恢复 | 全失败分支、SQLite连接、工作/回执、时钟和退休 |
| 宿主执行 | 原资源、获批配置、真实观察、停止/清理 | 围栏/身份/调用顺序、部分失败及位置复用 |
| 两端网关 | 原实例、忠实转发、显式失败、有界驻留/排空 | 授权登记/撤销、路由、异步转发/半关闭/回收 |

上游输出满足下游前提须由邻接定理或 I_global 提供；双向依赖用初始化和每种步骤共同归纳，不能循环假设“整个系统正确”。实例独立不等于共享额度/登记无交互。

库/引擎/密码算法/系统调用提供最小外部合同；自有封装、组装、锁/事务/回调仍证明对应，不将整个 API/节点当可信函数。模板是 owner 明确排除项，核心使用其合同仍为显式条件。

### H2 Rust 与 Lean 模型的对应

Rust 经 Charon 提取、Aeneas 翻译得到 Lean 中的实现语义；手写 Lean 模型描述允许的行为。二者不是因为都用 Lean 就自动相同。

定义表示关系 `R(r,m)`，其中 `r` 是翻译后的实现状态，`m` 是规约状态。它逐字段说明：有限整数怎样表示自然数、容器怎样表示逻辑映射、缺失值和错误怎样对应、完整尝试键怎样相等、哪些具体缓存由哪个提交派生。

最少需要以下定理：

```text
初始化：RealInit(r) ⇒ 存在 m，ModelInit(m) ∧ R(r,m)

成功：R(r,m) ∧ RunRust(r,input)=Success(out,r')
    ⇒ 存在 m'，ModelStep(m,input,out,m') ∧ R(r',m')

拒绝：R(r,m) ∧ RunRust(r,input)=Reject(e)
    ⇒ ModelReject(m,input,e)，并满足该入口的无副作用条件

完备：R(r,m) ∧ ModelAccepts(m,input)
    ⇒ 实现不会额外拒绝、溢出或在自己的有限处理逻辑中不终止
```

对纯核心可逐处理函数证明一步对应；对持久服务、网关和宿主执行，需要带事件的多步对应。锁获取、缓存查找等内部步可以在抽象模型中不改变业务状态，但不能允许实现永远只走这些步而仍宣称最终完成。

崩溃也属于对应关系：删除易失内存后，由持久状态和真实宿主状态重建的结果仍符合规约。仅证明正常返回路径不够。

外部调用、异步任务和不支持的 Rust 结构需要受审计的接口模型或局部重构；不能手工重写一份更简单的 Lean 函数后，跳过它与实际 Rust 的对应。翻译工具链版本固定，外部合同作为显式参数；不通过新增自定义公理、占位证明或关闭检查来取得通过。

### H2.1 抽取能力与可信链

固定工具链主要支持安全、顺序 Rust 子集，抽取成功不自动覆盖 async/Tokio、锁、数据库/系统调用或终止。不能抽取的部分需可抽取决定、微步骤及真实锁/事务/回调连接；不以手写简化 Lean 程序代替实际对应。

编译器前端、Charon/Aeneas 实际翻译器、Lean 内核、外部库模型分别登记信任角色，不称任意 Rust 全语言无条件无损。手写可计算标准库定义无公理，不等于已证明与真实库一致，需对应论证或显式模型前提。证明绑定源提交、目标平台、features/cfg、生产/抽取编译器、依赖、工具、生成入口和外部模型指纹；生成文件不手改，测试/指纹不替代翻译器正确性证明。

### H3 系统组合的证明接口

1. 纵向精化：各实际模块对应独立合同/模型，覆盖初态、成功、拒绝、未知及恢复；对应业务字段、派生缓存及辅助历史。纯函数一步对应，编排以保持可观察事件的多步对应。
2. 横向组合：上游输出满足下游前提，共同 I_global 保持，共享状态/资源修改范围正确；不能只并列几个局部安全定理。
3. 通信连接：实际端点实现消息身份/版本和重投语义，允许重复/延迟/乱序/丢失；唤醒不替代持久 outbox。
4. 恢复连接：中心、节点、Redis独立中断，保持各自耐久状态及可能发生的物理/网络效果，不一起清空。
5. 系统结论：对任意预算内有限登记节点集合，初始化、所有微步骤与实现精化组合，推出实际可观察行为符合系统规约。允许内部不改变抽象状态的步骤，但无限内部空转由进展证明排除。

```text
外部合同 A ∧ 合法部署 D ∧ 各模块实现精化 R_i
∧ 接口相容/通信连接 ∧ I_global 初始化及保持
  ⇒ 实际组合执行符合声明系统规约及安全/功能性质

上述条件 ∧ 明确通信/存储/调度/收敛条件 ∧ 已证内部推进
  ⇒ 声明的最终完成性
```

安全按任意有限前缀归纳，G1保密另做双执行组合；不由两题 CI 或单机双服务实测推出全体多机执行已证明。每定理列节点/预算参数、输入、故障、外部前提及未覆盖项。

## I 证明交付与代码索引

### I1 先固定定义 再按模块推进

每条定理提交时必须同时具备以下信息：

1. 对应的产品条款、可观察结果及保证类别：控制器自身证明／明确外部条件下的证明／工程测试／当前不承诺。类别不是完成状态，尚未证明的目标仍标为未解。
2. 完整类型、允许输入、初始状态、规则和拒绝顺序。
3. 使用的外部合同编号及部署条件。
4. 实际 Rust 入口和适用提交，以及表示关系涉及的全部字段。
5. 可执行的成功、拒绝、边界和故障样例。
6. Lean 定理及完整检查结果；未覆盖的外部调用和分支明确列出。

证明组织顺序：**轻量整体蓝图 → #292 完成功能拆分/工程验收并冻结真实提交 → 首条跨模块链路闭合 → 每批详细骨架/审查/智能体填证明/验收 → 整体闭合**。整体蓝图先固定最终性质、模块合同、主要依赖和外部条件，不预先铺开所有内部引理；开发期仅做少量代表性抽取/建模试验，功能开发不以前置完成定理为门槛。首条链路覆盖“中心创建→原节点就绪→丢回执→中心重启→原身份恢复→销毁清理”，证明声明子集内所有允许分支/故障交错，而非一次测试轨迹；模型性质、指定 Rust 对应和模块组合均须连接。首条链路通过不代表所有接口、保密、长期容量或全系统完成性已验证。后续按 P1–P8 逐批展开并复用公共引理，证明重构不得变更业务语义，受影响工程回归仍须通过。

详细阶段、首批闭合判据、显式未解条件和智能体边界见[证明工作流](proof-workflow.md)，任务进度由 [#101](https://github.com/ningZhang-cs/sandproof/issues/101) 跟踪；本页不复制进度表。骨架/类型检查、有条件的组合定理、指定实现的闭合证明分别报告；禁止占位证明造通过或循环假设，未解自有条件必须继续实例化，不能转入外部可信边界。

### I2 必须独立命名的判定函数

为确保规约能够落实到实际代码，至少建立以下可执行定义及相应的判定正确性定理：

| 定义 | 主要输入 | 输出 |
|---|---|---|
| `normalizeRequest` | 方法、认证上下文、原始字段 | 完整请求或精确拒绝 |
| `checkIdentityAndPlan` | 状态、原尝试、计划 | 身份与资源匹配结果 |
| `checkPublication` | 状态、回执、宿主证据、期限 | 运行或终止是否可发布 |
| `checkObservation` | 原登记、实际观察、保护条件 | 已存在、不存在、未知 |
| `checkRelease` | 原绑定、工作、连接、资源、引用 | 是否可安全释放 |
| `computeLifetime` | 接口种类、原期限、当前时间、参数 | 新期限或拒绝 |
| `checkCapacity` | 活跃责任、候选计划、峰值与清理预算 | 准入或明确超限 |
| `classifyTransferEnd` | 已读写字节、协议状态、错误、业务结束 | 完整、失败、取消、未知 |
| `projectVisiblePage` | 租户、状态、查询、时间、游标 | 页面及允许公开的统计 |

这里是证明接口，不要求生产代码使用这些英文函数名。每个定义都要连接到实际调用路径，不能成为一份没有被服务使用的“验证专用实现”。

### I3 一条性质应有正例和反例

以“没有截断”为例：100 字节源在各类分块下完整通过应成功；第 80 字节断开应失败；上限 80 时不得改写长度变成成功；零字节源应完整成功；上传完成但写入回执丢失应为未知；内容正确但实例身份不符必须拒绝。

这些样例帮助检查规约有没有写错，不能替代对任意字节序列和所有允许交错的证明。反过来，Lean 证明也不能替代 Linux/KVM 实测对部署前提、系统调用合同和实际配置的核对。

### I4 实现入口与覆盖记录

本页的 Rust 链接用于定位已有本地类型和处理函数，不将移动的源码当作固定证明基线。实际入口、抽取范围、精确提交、工具/平台配置及各批结果统一见[证明覆盖](proof-coverage.md)。中心、Redis 适配、内部协议、节点入口、两端网关及组装连接须在功能冻结时逐项登记；已有本地成果按其版本复用，不自动扩展到新模块。

最终交付分别报告：模型性质成立、指定 Rust 实现对应模型、在列明外部合同下组合系统性质成立。声明第三类结论时同时列出输入范围、故障、部署条件和未验证依赖；只有目标范围内的自有义务闭合，才可称为“在边界内完成形式化验证的沙箱控制器”。
