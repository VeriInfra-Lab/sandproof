# 最终完成性与长期容量：第一批复核

日期：2026-09-22。本批不改 Rust 运行行为，不接数据库或外部执行器，不删除历史记录。

## 本批完成的证明

新增 `SandboxModel/WorkflowReceiptProgress.lean`，证明当前尝试的有效回执
如何减少既有完成性证明中的剩余工作量，并连接模型的可执行回执处理函数。

- 当前逻辑命令尚无终局结果、属于本次操作，而且当前尝试已经派发或结果未知时，
  成功回执和明确失败回执都会严格减少该命令的剩余工作量。
- 其他命令的剩余工作量不变；本次操作预期命令清单不变。
- 创建、暂停、恢复的正常阶段中，资源阶段部分不变，因此整个操作的剩余工作量严格减少。
- 处理函数仍要求回执证据合法；不是收到一条消息就认定资源执行成功。
- 旧尝试的迟到回执不减少同一命令当前尝试的剩余工作量。这不等于迟到回执不写状态。

这些定理针对当前尝试及明确列出的正常阶段。销毁和失败补偿的阶段计数还包含
停止回执检查，需要另证，不能直接套用“阶段不变”。本批也没有证明每条回执
一定到达，或者未来收到回执时这些条件必然仍成立。

## 完成性结构中仍需处理的义务

`WorkflowLiveness.lean` 的三个内部义务仍未全部消除：

1. `ReservationGuardsPersistUnderNoRankDrop`：等待期间资源预留条件仍然有效。
2. `WorkflowProtocolClosure.select`：每个未完成状态都能选出能推进本次操作的工作。
3. `WorkflowServiceProgress.residual`：尚未归入已证明控制器动作的分支，仍要求调用者提供严格减少证明。

现有选择接口要求立即给出一个持续可执行的控制器工作项。回执和工作执行不属于
`ControllerScheduledWork`；只等待外部回执的状态不能简单地用控制器公平调度解决。
后续组合应显式区分“控制器可推进”和“等待外部响应”，并证明等待期间的条件保持、
当前尝试身份及跨步骤的工作量关系。本批未修改该接口，也没有据此宣称现有定理错误；
它们仍是带有这些前提的条件化定理。

外部最终响应允许成功或明确失败，不等于每个操作最终成功。失败路径仍需要
重试上限、补偿和资源关闭的证明。最终结论应是有终局结果，而不是永不失败。

## 容量核查：以实际实现为准

| 现有事实 | 对后续设计的影响 |
|---|---|
| `request.rs` 对部分递增编号显式检查上限 | 必须区分安全拒绝与已接收操作的完成；不能靠无界自然数模型略过耗尽 |
| `transition.rs` 的失败补偿沿用当前围栏编号，但会安排收尾命令 | 不应凭猜测为补偿额外预留一个围栏编号；需要计入命令与尝试记录预算 |
| `store.rs` 更新已有键，否则追加向量；没有可配置的存储限额 | 现有代码尚未实现“预算不足就拒绝新操作”的准入机制 |
| `worker.rs` 的回收更新资源状态，保留记录与索引 | 资源已关闭不等于历史存储已释放 |
| `HandlerMachineHeadroom` 要求每次调用具有机器余量 | 是当前定理的充分前提，不是已证明永久成立的性质，也不全是运行代码的拒绝条件 |
| `VecHeadroom` 检查机器长度范围，不是实际内存可分配量 | 不能据此声称已经处理宿主内存耗尽 |

下一批容量设计需要覆盖资源表、操作账本、计划、逻辑命令、每次尝试及各索引。
接收操作时不能只计算当下入队数量，还须为后续安排、有限重试及失败收尾预留空间；
并证明其他新请求不会花掉这些空间。预算释放不能把仍保留的历史记录当成已删除。
具体限额和最坏增量尚未确定，本批不添加脱离实际状态的预算模型来充当完成证明。

在不做历史归档的当前范围内，合理目标是：容量不足时安全拒绝新工作，已接收工作
在约定的外部响应与公平条件下仍可完成。不是固定内存无限接收请求，也不是
已实现的服务级内存保障。历史删除、编号复用和生产持久化继续留在后续阶段。
