# 完整沙箱生命周期控制器：系统实现与形式化验证计划

**状态：已讨论确认的正式计划。** 下列实现与验收任务尚待逐项完成；确认计划不代表任何新增系统能力或证明已经完成。

## 1. 目标与已确认范围

交付一个独立控制面、直接管理 Firecracker 的完整沙箱服务，同时产出对安全关键实现的形式化证明和可复现的研究评估。

| 维度 | 首个研究版本 |
|---|---|
| 部署 | 单台 Linux/KVM 宿主机，一个 controller 与一个 worker，支持多用户、多沙箱并发 |
| 生命周期 | create / exec / pause / resume / kill，文件输入输出、受控网络、资源管理和失败补偿 |
| 故障 | controller/worker 进程崩溃重启，消息重复、乱序或迟到，超时、丢回执及外部动作部分完成 |
| 实现路线 | 以现有 Rust 纯控制核心为基础，将持久化、worker、执行和恢复机制接入统一协议；复用 Firecracker/jailer |
| 研究目标 | 生命周期安全、实际 Rust 与 Lean 的对应、持久化与恢复协议，以及容量支撑的条件化完成性 |
| 后续扩展 | 多节点调度、跨节点迁移、故障接管和控制器高可用不进入首个研究版本 |

单节点指一台承载多个 Firecracker 虚拟机的宿主机，不限制为单用户或单沙箱。阶段性先打通 create/kill，是验证关键假设的顺序；最终交付保留完整暂停恢复能力。

## 2. 失败语义

采用**安全失败关闭**，作为系统和证明的共同合同：

- 准入检查拒绝请求时保持原状态，不产生未提交副作用。
- 已接受操作发生部分失败、无法安全继续时，允许终止沙箱、执行清理并返回明确失败。包括某些 pause/resume 失败可能导致沙箱终止；第一版不承诺任意中途失败均可无损回滚并继续运行。
- 超时表示结果未知，不能解释为“动作未执行”。通过持久记录、精确资源身份和真实观察对账，再决定重放、继续或安全收尾。
- 接受 kill 请求不等于已经停止虚拟机。无法确认停止时，不能发布销毁完成；失败补偿也必须满足其资源关闭和发布条件。
- 外部组件永久不可用、资源永久无法停止时，不承诺无条件完成，仍须保持安全并准确报告未完成/未知状态。

## 3. 证明目标与边界

### 目标结论

从满足表示关系的合法初态出发，在明确故障模型与底层合同成立时，真实实现的任意有限执行前缀都对应合法协议历史并保持安全。进一步，在公平调度、恢复后足够的运行时间、持久化可用及必要外部响应/安全收尾条件下，每个已接受操作最终得到永久稳定的成功或失败结果，符合清理条件的非当前资源最终被回收。

具体分别验收：

1. 同一沙箱不双跑，资源不跨沙箱错绑，旧 generation 不能重新获得权限。
2. Running/Paused/Destroyed 发布满足真实资源、权限和精确回执条件；迟到 cleanup 不回收当前资源。
3. operation/effect 幂等、未知结果处理、旧尝试隔离及终局结果稳定。
4. 决策与 outbox 原子持久化，commit-before-dispatch，崩溃后的重放与资源对账符合协议。
5. 已接受操作具有后续执行、有限重试和失败收尾的预留预算，其他请求不能消耗该预算。
6. 工作流完成性和最终清理建立在具体实现机制上，不把尚未证明的内部进展义务包装为环境假设。

### 信任边界

Lean 是唯一协议规范来源；实际 Rust 通过固定版本的 Charon/Aeneas 抽取，与规范证明对应。安全关键的自有权限判断、持久化决策、worker 身份检查、对账和恢复调度不能整体放入“adapter 正确”的假设。

Linux/KVM、Firecracker/jailer、存储引擎及文件/快照/网络原语的内部正确性，通过逐项列明的合同连接，并有固定版本审查和故障实验支撑；不宣称证明内核或虚拟化逃逸不存在。完整 POSIX/ACL、文件内容语义、动态 DNS/SNI、共享卷、snapshot fork 和恶意宿主不进入首版证明范围。

进程崩溃测试不能推出宿主掉电安全。第一阶段明确持久化故障域；若进一步声明宿主重启或掉电保证，须增加相应存储合同与实验。逻辑预算和整数容量也不等于宿主实际内存永不耗尽。

## 5. 五个实施阶段

### 阶段一：建立可信基线

**系统交付**：固定开发/运行环境、工具链和接口合同，复现已有成果。

- [ ] 固定 Linux/KVM、Firecracker/jailer、kernel/rootfs、Rust/Charon/Aeneas/Lean 的版本与指纹，记录运行配置。
- [ ] 运行 `scripts/verify-controller.sh`，保存完整日志和生成文件指纹，得到可重复的现有验证基线。
- [ ] 统一 README、研究计划、refinement 计划、新运行层定位与证明覆盖文档。
- [ ] 明确生命周期返回语义、可信调用者身份、持久化故障域、网络撤权对新/已有连接的语义，以及逐接口的外部合同。
- [ ] 建立“性质 → 模型/定理 → Rust 入口 → 外部原语 → 验收证据 → 剩余义务”清单，检查前提可满足。

**验收门槛**：已有成果可复现；新增目标、已证明结论和环境假设分开记录。不能用局部构建或测试数量替代全输入证明覆盖。

### 阶段二：打通真实故障恢复

**系统交付**：持久化、worker、真实 Firecracker 启停，以及 create×kill、丢回执和进程崩溃恢复。

- [ ] 选择单节点事务存储并记录合同依据，实现 sandbox/operation/effect-outbox 的原子持久化与提交后派发。
- [ ] 实现受 jailer 管理的 VM 启停、worker 资源登记和 sid/epoch/generation/effect/resource 身份观察，复用现有纯核心作决策。
- [ ] 在提交前后、派发前后、VM 已启动但回执未记录、kill 已接受但 stop 未完成、controller/worker 重启等位置建立确定性 failpoint。
- [ ] 检验在途启动与 terminal fence：安装 fence 后如何阻止旧执行权生效，或如何处理已经发生的副作用；只丢弃迟到 callback 不算完成撤权。
- [ ] 根据实机结果细化 durable/volatile/transport/observed-resource 状态、部分完成和 reconciliation，保留唯一规范，不维护第二份近似业务状态机。
- [ ] 将自有恢复和执行资格决策纳入实际 Rust 对应证明；对每个 I/O 原语列出真实生效/提交点和剩余依赖，检查拒绝分支及完整后继状态。

**首个关键验收关卡**：真实启动、停止、fence 和恢复行为能否兑现协议合同。每个关键崩溃窗口均有可执行的恢复路径与对应证据；安全关键自有决策不能依赖笼统的“shell 会正确恢复”假设。

如果真实行为超出现有模型，先形成可复现反例、修改协议/模型并重验受影响证明，再扩展功能。此阶段是可行性评估点；实验通过本身不等于部署链已经全部证明。

### 阶段三：完整生命周期系统

**系统交付**：暂停、快照、恢复、执行、文件与网络管理、多沙箱并发，以及安全失败关闭补偿。

- [ ] 实现 freeze → snapshot seal → durable manifest commit → stop → Paused 的完整路径，明确内存、磁盘、workspace 和 manifest 的关系。
- [ ] 实现精确 manifest 选择、restore、当前策略应用、activate 与 Running 发布；恢复后的权限来自当前控制记录。
- [ ] 接入受管执行、文件输入输出、静态网络策略与网络槽、精确资源 cleanup，逐项复核并复用现有运行层。
- [ ] 完成可使用的服务接口与操作查询/重试行为，使调用者可以观察 pending、unknown、补偿和终局结果。
- [ ] 覆盖 pause×kill、resume×kill、resume×resume、exec×pause/kill、旧策略命令以及旧 cleanup 与新 generation 并发的故障场景。
- [ ] 每新增一条运行路径，同步补充唯一模型、实际 Rust 对应证明、拒绝分支覆盖及故障回归。

**验收门槛**：真实正常生命周期和失败补偿均可运行；稳定状态发布有精确身份与真实资源证据；多沙箱之间不发生错误归属；新增输入进入统一对应证明。

### 阶段四：完成性与容量保障

**系统交付**：准入预算、持久资源预留、有限重试与安全失败清理。

- [ ] 依据实际操作、最大重试次数和补偿路径计算增量预算，覆盖资源、operation、plan、effect 尝试、账本与索引。
- [ ] 接受操作时持久预留后续执行和收尾空间；容量不足时安全拒绝新工作，其他请求不能花掉已预留预算。
- [ ] 证明预算初始与逐步保持性，将现有 `HandlerMachineHeadroom` 和输入容量前提连接到实现；明确编号耗尽、历史记录持续占用与宿主资源耗尽的行为。
- [ ] 区分控制器可推进与等待外部结果，闭合预留条件保持、工作项选择、真实 worker 动作、当前尝试回执、重试耗尽和发布的进度组合。
- [ ] 消除 `WorkflowProtocolClosure.select`、`ReservationGuardsPersistUnderNoRankDrop`、`WorkflowServiceProgress.residual` 等内部未证义务，或以已证明且对应实际机制的结构替代。
- [ ] 对所有已接受操作（含被 kill 取代的操作）证明最终结果稳定；分别证明条件化终结与符合条件的非当前资源最终回收。

**验收门槛**：每步容量不再依赖调用者无依据地提供；完成性只保留明确的调度、恢复、存储及外部响应/安全收尾条件，不把核心进展结论当成前提。外部条件不成立时保持安全，准确报告未完成状态。

### 阶段五：研究评估与发布

**系统交付**：可部署服务、使用接口说明、固定配置和独立复现环境。

- [ ] 在多沙箱负载下运行确定性 failpoint 矩阵、固定 seed 的随机交错和恢复回归，将失败历史最小化并持久保存。
- [ ] 为关键性质安排 guard mutant，验证检测工具对目标错误有敏感性；缺少关键观察时报告 Inconclusive，现有 checker 接受不等于完整实现已经证明符合规范。
- [ ] 评估正常操作、快照、故障恢复的延迟和吞吐，以及持久化写放大、资源残留、账本增长与证明维护成本。
- [ ] 对照相关工作明确研究贡献与差异；不预先声称“首个”，不将历史 E2B harness 行为重新表述为已确认系统漏洞。
- [ ] 发布源码/工具链/镜像指纹、原始因果历史、failpoint/seed、配置、证明覆盖表、完整验收日志及复现命令。
- [ ] 在另一台符合要求的 Linux/KVM 主机复现声明的证明和实验，形成系统使用文档与研究报告。

**验收门槛**：实际公开输入、恢复路径和关键性质均可追溯到证据；报告分别列明机器证明、底层合同、仅有实验支持和未完成内容。有限实验不能代替任意历史的证明。

## 6. 推进方式与工期

阶段顺序为：**可信基线 → 真实故障恢复 → 完整生命周期 → 完成性与容量 → 研究评估与发布**。

故障日志、覆盖记账和回归测试从阶段二开始建设；容量约束应提前影响状态设计，阶段四完成总体机制与证明，不能等到最后才发现实现无法支持预留。局部进度引理可提前开展，整体完成性须对应稳定后的真实运行路径。

每个后续实现 issue 应写清修改的合同/状态、代码范围、关联定理、故障案例、验收证据和剩余假设，并回链本总计划。需要按实际功能族拆分工作，不以代码量或已编译模块数量衡量完成度。

**暂不承诺总工期。** 完成阶段二后，根据真实模型改动、接口可行性和证明成本重新估算，必要时调整后续任务划分；范围或安全承诺发生实质变化时另行讨论。

## 7. 总完成标准

- [ ] 用户可在单节点、多沙箱环境使用完整生命周期、执行和文件/网络接口，故障状态与失败语义清晰。
- [ ] 安全关键的自有控制、worker 和恢复决策具备实现对应证明；真实部署路径的其余原语及信任边界逐项公开。
- [ ] 安全性质覆盖声明故障模型下的任意有限合法历史；条件化完成性、结果稳定及最终清理义务闭合。
- [ ] 容量前提由真实准入/预留机制和保持性证明支撑，资源耗尽边界明确。
- [ ] Rust 测试、静态检查、重新抽取一致性、全部 Lean 模块及定理依赖审计通过，不以 `sorry`、`admit` 或自定义公理绕过。
- [ ] 故障实验、性能评估、相关工作对比、部署文档和独立复现材料齐全。

最终系统验证结论必须与已覆盖的真实执行路径和明确依赖相符。纯核心定理不能自动覆盖新增运行层，测试通过也不能替代实现证明。
