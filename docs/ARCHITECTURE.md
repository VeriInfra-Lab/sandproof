# Sandproof 系统架构

[文档目录](README.md) · [项目蓝图](project-blueprint.md) · [模块合同](module-contracts.md) · [V1 验收清单](testing-plan.md)

本文解释系统由哪些部分组成、一次请求如何运行、数据存在哪里，以及它们与 E2B 的对应关系。章节按 E2B 的架构文档组织，但不是 E2B 的逐句翻译，也不把 E2B 的全部功能纳入我们的目标。

目标结构为中心/宿主双服务与有限静态节点。第 2 节给出目标连接；第 3 节标明已有本地实现和待实现中心职责，不能把目标图当部署结果。各项实测绑定 issue/PR 的精确提交、配置和摘要；验收标准见[测试清单](testing-plan.md)，实际证明结论见[证明覆盖](proof-coverage.md)，证明模型和组合方法见[验证设计](formal-verification-design.md)。本页只维护组件关系、存储用途和运行路径。

E2B 对照来源是 [runtime 的 ARCHITECTURE.md](https://github.com/e2b-dev/runtime/blob/132dadd2ef55bbac301528500e8a4538caf4b163/docs/ARCHITECTURE.md)，固定在 `132dadd2ef55bbac301528500e8a4538caf4b163`。这只是架构阅读参考，**不升级我们的兼容基线**：SDK、envd、Harbor 和 Firecracker 的采用版本仍以[蓝图](project-blueprint.md)及测试锁定记录为准。

## 1. 这个仓库实现什么

Sandproof 要交付一个统一中心入口、多个静态登记宿主的多用户沙箱服务：用户通过约定的 E2B 客户端调用，创建一台隔离的 Linux 虚拟机，在里面反复执行命令和读写文件，最后主动销毁或由系统到期销毁。控制器负责检查权限、保存决定、驱动真实资源，并在自身出错重启后继续核对和收尾。

它不只是“判断某个状态是否合法”的演示程序，也不自行实现一套虚拟机。我们编写控制器、宿主执行层和兼容入口；复用 Firecracker/jailer、Linux/KVM，以及固定版本的 E2B envd。

两项约束限定当前交付规模：

1. **轻中心、重宿主。** 中心只决定全局归属、固定节点、额度、意图和路由；宿主自主完成本地生命周期、恢复与清理，不由中心远程调用 PrepareVm 等子步骤。
2. **私有系统盘、冷启动、固定绑定。** 不保存运行中内存，不做快照恢复、自动迁移或失联后异地重建；中心多活和 Redis 自动切换也不包含。

中心需要权威 Redis，宿主继续使用本地 SQLite 和原资源登记；模板产物由受保护只读服务分发。不需要 PostgreSQL、ClickHouse、云对象存储和监控平台作为前置。首次工程交付在一台物理 KVM 主机上部署中心、Redis 与一个真实宿主服务，经双向认证 HTTPS 通信；多台真机验收见关联后续任务。

### V1 做完后，用户能做什么

下表是[蓝图 F01–F10](project-blueprint.md)的架构导读，不是另一份验收标准，也不表示这些能力已经全部完成。

| 功能 | 用户最终能做什么 | 对应实现路线 |
|---|---|---|
| F01：基本生命周期 | 创建、连接运行中的同一实例、查询、列出、销毁自己的沙箱 | 兼容 API → 持久控制服务 → 核心决定 → 节点执行 → 真实观察后发布结果 |
| F02：寿命 | 设置期限、续期，到期自动销毁 | 中心固定续期意图，节点持久应用；运行起点来自节点首次就绪；节点独立执行到期 |
| F03：命令 | 多次执行、指定工作目录/环境/用户、后台运行、取输出、等待和终止 | 经过授权的网关连接来宾 envd，复用其进程协议；控制超时、流量和未知结果 |
| F04：文件 | 在运行期间读写、上传下载、列目录和建目录 | 网关检查访问资格，envd 操作该虚拟机内的文件；请求限额由入口执行 |
| F05：独立系统 | 安装依赖、修改自己的系统目录，不污染其他沙箱 | 每个实例独立可写 ext4 系统盘；基础镜像不交给来宾直接写，不挂载宿主工作目录 |
| F06：通用模板 | 提交 Dockerfile+所需文件或公开 OCI 镜像，选择有界资源配置，再按模板创建实例 | 自助构建、独立构建池、发布登记、运行绑定与 Harbor 通用适配已接通；须显式部署，自有构建入口不等同于原 E2B 模板 API |
| F07：权限与资源 | 多用户互不越权，资源不足时拒绝新申请且保留清理余量 | 中心全局预留覆盖节点潜在占用；两端鉴权、实例令牌、本机准入及真实资源限制 |
| F08：受控网络 | 默认允许受平台限制的公网出站，或按 SDK 选择禁网、静态 IPv4 规则 | 宿主网络空间、TAP 和防火墙强制执行；公网需部署显式开启，目前仅选定测试网络场景通过 |
| F09：失败恢复 | 服务中断重启后，不盲目重复创建、不误杀别人的实例、能继续核对和清理 | 已提交动作记录 + 精确宿主资源身份 + 只读观察 + 恢复决策 |
| F10：可复现评测 | 对固定任务，用同一接入比较 Sandproof 和 E2B 的功能表现 | 锁定 SDK/Harbor/任务/镜像；先跑标准解答，再做相同智能体配置的对照 |

“兼容”只覆盖约定子集，不保证 E2B 的全部接口、性能或云平台能力相同。暂停/恢复、快照产品、fork、共享卷、自动迁移、高可用、任意公网服务端口发布、桌面和 GPU 不属于当前交付；已有模型包含相关步骤不代表它们已启用或获真实实现证明。

## 2. 系统全貌

### 2.1 目标连接（待实现）

```text
用户 / 固定 E2B SDK / Harbor 通用适配
                    │ 统一公开入口
              中心服务 ↔ 权威 Redis
          鉴权、准入、固定绑定、意图、查询、路由
                    │ 版本化 HTTPS / 双向证书验证
           ┌────────┴────────┐
           ▼                 ▼
       宿主节点 A         宿主节点 B …（有限静态登记）
       本地控制器         本地控制器
       ↔ SQLite           ↔ SQLite
       执行/观察/恢复     执行/观察/恢复
       ↕ 资源登记         ↕ 资源登记
       Firecracker VMs    Firecracker VMs
       Linux/envd/用户    Linux/envd/用户

模板构建/目录 → 受保护 HTTPS 只读产物服务 → 节点校验/缓存
                                                        → 私有实例盘
```

同一节点可运行不同用户的沙箱；同一用户的不同沙箱可跨节点，同一沙箱不跨节点运行。节点之间不需要点对点通信。首次真实部署只包含一个物理宿主，中心、Redis 和节点仍按这套网络与鉴权合同连接，不省略持久化或证书检查。

### 2.2 当前本地实现

当前 `sandproof-server` 在单宿主组装兼容 API、`ControllerApplication`、SQLite、本地纯核心、节点适配器及运行工具。管理路径为“API → 本地控制/事务 → 原工作 → 宿主证据 → 发布”；数据路径为“网关 → 本地资格 → 固定实例中继 → envd”。中心/Redis、内部高级操作和第二层网关尚未交付。

数据请求不把命令正文写入生命周期状态机，也不另行创建 VM。目标中心只协调高级生命周期操作；下列现有本地模块保留唯一的执行算法。

E2B 的 `runtime` 仓库包含整套后端，不只是控制 Firecracker 的中间层。本仓库 `sandbox-runtime` 仅负责底层宿主运行，不能因名字相似视为同一范围。

## 3. 组件与职责

### 3.1 已实现：本地兼容入口和组装服务

[sandbox-api](../sandbox-api/src/lib.rs)负责 HTTP 请求、凭据解析、租户识别和 E2B 响应映射；其中 [ManagedPort](../sandbox-api/src/managed.rs)是薄适配器，把 SDK 输入转换为普通业务命令，并把应用结果映射为 HTTP 字段、时间字符串和分页令牌。它不能绕过控制核心，直接把沙箱标成运行成功。

宿主与数据连接合同由控制服务的 [application](../controller-service/src/application/mod.rs) 拥有，业务错误在 HTTP 边界转换。网关只依赖 `DataAccessPort`：接收原实例的访问许可，提交已准备好的请求，再取得已登记的中继进程；不依赖具体节点、不拼接网络空间名称，也没有自行执行 Linux 命令的后备路径。撤销通知、响应与中继的排空持有者，以及取消后的精确子进程回收仍保持原责任。创建、销毁、恢复、到期清理、维护和数据资格协调已移入 [ControllerApplication](../controller-service/src/application/coordinator.rs)，同一应用对象由 API、网关和后台扫描共享，只有一把管理锁。生命周期与模板/私有构建编排按职责分文件，模板证明排除范围不变。应用结果保留数值时间和归属，不携带 SDK 序列化字段；可信时钟在各个原检查点重新取值，可注入时钟只用于可信组装及确定性测试。宿主能力按工作执行、恢复观察、物理位置、数据中继、容量就绪、来宾配置和模板校验分成小端口，证据类型单独共享；恢复端口不要求执行能力。完整应用的 ControllerHost 仅为组装约束，不另建代理或锁。具体实现由节点层的 [NodeHost](../sandbox-node/src/adapter.rs)提供，物理配置租约及原测试由 [physical_profile](../sandbox-node/src/physical_profile.rs)拥有。可信组装传入内部中继程序路径，节点仍按精确实例登记后放行，不从用户请求选择程序。

[sandbox-server](../sandbox-server/src/main.rs)把各模块组装成 Linux 常驻进程。`main.rs` 只选择平台入口或内部字节中继；正式服务的唯一启动顺序由 [linux/startup.rs](../sandbox-server/src/linux/startup.rs)组装，不在旧入口保留转发层。启动相关职责分成以下模块：

| 模块 | 职责 |
|---|---|
| [linux/config.rs](../sandbox-server/src/linux/config.rs) | 解析部署配置，校验完整容量、寿命和接口预算，构造节点与管理配置；不启动宿主动作 |
| [linux/preflight.rs](../sandbox-server/src/linux/preflight.rs) | 检查受保护路径、当前数据库格式与配置、物理存储覆盖；显式取得物理配置租约 |
| [linux/reconcile.rs](../sandbox-server/src/linux/reconcile.rs) | 核对控制库与宿主身份，启动前恢复，并运行恢复、到期与维护扫描 |
| [linux/startup.rs](../sandbox-server/src/linux/startup.rs) | 按顺序连接上述职责，构造管理 API 和数据网关，最后监听 |

先静态校验和只读数据库预检，再取得物理配置租约、初始化节点、开库事务重检、核对宿主库存和恢复，最后监听并启动周期扫描。拆分没有把恢复提前或延后，也没有增加第二套生命周期判断。当前入口要求绑定回环地址；对外部署需要可信的 TLS 前置入口，不应直接把高权限内部监听暴露到公网。

正式部署必须提供完整的 `bounded_host`、`maintenance.capacity`、`data_transfer` 和物理存储配置，不允许缺项时回退到旧模式。它们是部署预算，不是 E2B 客户端创建参数；SDK 的默认寿命和可选请求字段保持原合同。模板登记、预制目录及私有构建池等未启用能力仍可省略，不能把“功能未启用”误解为另一种控制器模式；精确配置规则见[模块合同](module-contracts.md)。

应用层提供默认关闭的 `contention-diagnostics` 编译开关，局部记录同一线程的锁等待/持有与请求耗时；显式选择的宿主端口调用单独计时。它不增加另一把控制锁、部署模式、HTTP 监控接口或可观测存储，不记录凭据/实例标识，不能作为授权依据。受控慢宿主与有限历史的诊断入口及结论边界见[验收清单](testing-plan.md)。

当前继续采用上述串行协调；分离短持久决定与慢宿主执行、支持不同沙箱有限并行的优化归入 [P2 待办 #284](https://github.com/ningZhang-cs/sandproof/issues/284)，不混入本次模块重构。当前真实函数的验证接口及固定工具链抽取评估统一见[证明覆盖](proof-coverage.md#当前串行实现的模块交接)，不是新增证明或另一份业务规范。

HTTP 管理、数据鉴权/派发与后台协调另共享有限请求准入，超额在派发阻塞任务前拒绝，并保留控制与后台名额；它没有把串行状态机改成并行执行。配置、取消后的名额归属及 TLS 前端的连接/请求读取边界统一见[请求派发预算](module-contracts.md#请求派发预算290-r1)。

这部分对应 E2B 的 API，以及单机下简化的服务组装。我们没有团队管理后台、计费、OIDC 平台或跨节点放置算法。

当前默认创建入口仍为 `base`；部署显式配置可信预制目录或正式发布登记时，可按归属选择不同模板，响应报告准入时固定的不可变编号与资源形状，见[模块合同](module-contracts.md)。自助构建扩展接通提交/状态/日志，并在发布检查后返回模板编号；未知名称不映射为 base。显式禁网默认可用，公网/静态 IPv4 需部署开启并满足宿主与镜像条件。创建级环境变量和元数据与单条命令参数是不同接口；支持、差异和拒绝项以[兼容合同](../tests/compat/contract.json)及实机证据为准。

### 3.2 已实现：本地控制核心与持久服务

[controller-core](../controller-core/src/lib.rs)是纯 Rust 状态处理代码：读取当前状态和输入，判断接受或拒绝，给出后继状态及后续动作。这里不执行 SQL、不发网络请求、不启动进程，是既有 Lean 对应证明主要覆盖的部分。

[controller-service](../controller-service/src/lib.rs)负责把这些决定变成可靠执行流程：

同一库的 [host_contract](../controller-service/src/host_contract.rs) 与宿主端口不依赖数据库；节点关闭该依赖的默认特性后，只编译这些共享合同、模板描述及原有候选见证核验。正式服务启用默认的 `durable` 特性，仍使用唯一的 SQLite 协调算法。这是编译依赖边界，不是两种控制器或绕过持久化的运行模式；没有数据库特性时不导出开库和协调器。已有路径重导出同一声明，避免复制类型或证明专用实现。

- 保存已接受输入、操作、编号映射、待执行动作和回执。
- 先提交决定，再派发外部动作；没有提交的动作不能先执行。
- 用事务协调寿命、配额、重试和清理预算。
- 重启时重放已接受输入，并利用宿主证据解决未知结果。

业务状态只有一个来源。数据库查询视图不是第二套状态机，节点执行器也无权自行宣布沙箱“已创建”或“已销毁”。当前采用单控制进程、串行管理写入口的保守方案，优先明确失败语义，不承诺集群吞吐。

### 3.3 节点执行适配器与运行工具

[sandbox-node](../sandbox-node/src/linux.rs)把控制动作映射为真实宿主操作，检查用户、实例、操作代数和资源绑定，返回可核对的观察结果。例如：登记的那个进程是否还活着、网络规则是否仍正确、私有磁盘是否属于本实例。

节点按身份、凭据、只读盘点/观察、执行、恢复和传输分模块。[纯判断](../sandbox-node/src/linux/decisions.rs)只比较传入值；原操作、归属和物理位置检查，以及读取与执行顺序仍由节点负责。精确退休/释放留在位置模块，不能凭纯判断返回 true 就删除资源。同步助手进程统一使用运行层的 `OwnedChild`，并行处理 stdin/stdout/stderr、执行分层期限与有限回收；退出未确认仍占用额度，具体合同见[宿主同步辅助命令](module-contracts.md#宿主同步辅助命令)。后台中继仍使用原有持久身份和独立回收机制。

这里的“代数”就是区分新旧操作或实例的版本编号；“围栏”是执行前必须检查的版本/终止标记。它们用于阻止迟到的旧命令重新启动已经撤销的资源，不是来宾里的一堵防火墙。

[sandbox-runtime](../sandbox-runtime/README.md)完成更底层的工作：准备私有磁盘、网络空间和 TAP；通过 jailer 启动 Firecracker；记录 PID 与启动时间；观察、停止和精确清理资源。启动前先登记身份并设置放行门控，避免出现“虚拟机已经启动，但没有留下能够认领它的记录”。

重启盘点使用不含沙箱令牌的窄只读观察器，输入来自控制库的原创建参数和物理位置；它没有启动、停止或清理接口。资源完整核验后，可将有可信原绑定的凭据故障限制在所属沙箱，不因一个坏凭据停止其他健康沙箱；这不放宽资源身份或共享状态检查，具体拒绝与未知语义见[模块合同](module-contracts.md)。

两者承担目标宿主节点的本地执行部分，对应 E2B orchestrator 的一部分。内部服务入口仍待实现；快照、分布式缓存、内存按需加载、共享卷和动态节点池不包含。

### 3.4 命令与文件网关、来宾 envd

[网关](../sandbox-server/src/gateway.rs)只转发允许的接口。每次请求检查当前实例访问资格和令牌，再连接固定实例的 envd；客户端不能提供任意宿主目标地址。envd 的初始化等控制接口不作为公共数据接口开放。

envd 是运行在虚拟机内的服务，负责启动用户进程、收集输出、传递信号及文件操作。我们复用固定版本，不在 V1 重新实现这一整套进程/文件协议；也不因此把 envd 视为已被我们的 Lean 证明覆盖。

用户命令持续输出不设累计字节上限，靠在途缓冲、并发、背压及撤销维持宿主边界；宿主同步工具则使用独立的输入/输出与交换/回收预算。两者不能混为一谈，执行期限也不等于输出大小限制。具体参数、失败语义与外部前提统一见[模块合同](module-contracts.md)，新增适配层的待证明连接见[证明覆盖](proof-coverage.md)。

来宾及来宾 root 不可信。envd 的“成功”回复不能单独证明宿主隔离有效、Firecracker 已停止或宿主资源已经清理。文件访问权限在本版本主要是“谁能对哪个实例执行哪种操作”；实例内部的用户和文件权限由来宾 Linux 处理，**不是我们已经证明了一套逐文件夹 POSIX/ACL 权限系统**。

### 3.5 模板与评测接入

Python 的受保护配置读取、数据通道额度和跨池 UID/地址检查统一在 [template_build_config](../tools/template_build_config.py)。构建服务、配置生成器和验收入口调用同一实现；基础配置不导入 HTTP 服务。服务启用时的完整组装与物理租约检查仍由服务入口负责，直接脚本和模块调用均保留，不增加旧模式别名。

物理配置校验现在对缺失、空值和不完整的共享配置统一拒绝，不再返回“无配置但成功”；验收策略先验证完整候选，再更新调用方的设置，拒绝不会留下半应用的设置。节点的 envd 令牌摘要直接使用既有 Rust SHA-512 库，保持原 128 个小写十六进制字符的格式，不再启动额外宿主工具。

当前已有固定 `base`、[测试来宾构建工具](../tools/build_ci_guest.py)、显式可信预制多模板运行基础、隔离候选工作器和正式发布登记。[自助构建服务](../tools/template_build_service.py)接收用户 Dockerfile+上下文或公开 OCI，提供状态/有限日志/原因；独立构建池用标准 BuildKit 构建 Dockerfile，用固定 regctl 直接导入公开镜像，经转换和原构建 VM 回收后交给运行池发布。候选须经真实启动及管理通道检查，临时 VM 精确回收后才发布。Harbor 的[通用入口](../benchmarks/run_generic.py)已接上自有构建服务与原解答/评分，实际任务验收与来源差异见[评测说明](../benchmarks/README.md)；不声称原 E2B 模板 API 完全兼容。接口、部署配置与失败合同统一见[模块合同](module-contracts.md)。

运行路径是：用户 Dockerfile+上下文或公开 OCI 镜像 → 隔离构建/转换 → 启动检查 → 发布不可变模板 → 鉴权与资源准入 → 创建私有沙箱。复用 BuildKit、regctl 和 umoci。[#123](https://github.com/ningZhang-cs/sandproof/issues/123) 负责构建编排、转换和用户模板入口，[#6](https://github.com/ningZhang-cs/sandproof/issues/6) 负责启动产物及多模板私有系统盘，[#13](https://github.com/ningZhang-cs/sandproof/issues/13) 将原题环境接入同一通用流程，随后运行原解答、原评分并销毁。默认 base 保留为便捷模板，不能把所有名称映射到它。

软件内容、资源形状、模板修订与运行实例分别记录。用户构建/注册时选择有界 CPU/内存/磁盘配置，创建时选择模板，不虚构固定 SDK create 未提供的资源字段；别名只在准入解析一次，运行和恢复绑定原修订。首版支持 Linux x86_64 Debian/Ubuntu 兼容环境，冷启动即可。构建环境不得接触生产数据库/管理凭据或宿主 Docker socket，预算与运行实例分离；输入/镜像层的路径、用户/目录/环境和启动语义按[模块合同](module-contracts.md)检查，失败不发布就绪。

Harbor 是客户端和评测执行框架，不是控制器内部的调度器。任务初始化、命令、文件与评分链都必须真正通过；适配后运行的结果应标为“Harbor 经适配运行”，不能冒称原 E2B 模板链兼容。

### 3.6 待实现：中心服务与节点内部入口

中心复用公开协议解析和错误映射，但业务端口接向中心纯控制核心与 Redis 适配。它持有用户公开凭据、全局身份和额度、固定节点、可靠待发送集合及已确认节点事实；内存查询/路由是绑定提交修订的派生视图，不是第二份权威。

节点内部入口验证中心证书和完整部署/节点代际/租户/实例/操作/版本，持久绑定原本地身份，然后调用现有应用。中心不持有宿主权限，节点不直接读取 Redis 账本，不向节点复制全量用户 API 密钥。控制请求使用高级创建、续期、销毁和查询，不增加任意宿主命令或路径接口。

中心和节点两端网关都保留访问资格、预算、终止及排空责任。超时、分区和回执丢失保留原节点与预留；返回真实事实后按身份/版本耐久应用，再确认节点可以按窗口与保留规则退休。详细字段和成功/拒绝/未知见[模块合同](module-contracts.md#中心与宿主的高级操作合同)。

## 4. 存储：哪些必须有，哪些不用做

### 4.1 本项目的数据分别存什么

| 存储 | 保存内容 | 为什么需要 | 当前实现或计划 |
|---|---|---|---|
| 中心协调账本 | 全局归属、固定节点、意图/版本、预留、未决操作、待发送集合、已确认事实与有限结果 | 中心重启恢复原责任，未知不重新分配或释额 | 待实现：独立权威 Redis、有界控制块、CAS 与耐久提交；不使用 TTL 删除未决责任 |
| 本地控制数据库 | 已接受输入、操作、动作派发状态、回执、编号映射、截止时间和预算记录 | 节点自主恢复，知道原本地操作进度 | 已实现：本地 SQLite、WAL、同步写与检查点；中心加入后保留 |
| 宿主资源登记 | 资源归属、代数/围栏、进程身份、网络创建意图、资源绑定及实例凭据 | 认出真实资源；区分旧资源、新资源和结果未知；避免误杀 | 已实现：受保护的节点状态目录和运行器登记文件；必须与数据库核对 |
| 基础镜像与内核 | 启动 Linux 所需的受保护产物、版本及摘要 | 固定实例启动输入；基础镜像不能被某个租户修改 | 受保护本地文件；可显式提供按模板绑定的长度/摘要/资源描述，动态依赖未锁定时不承诺完整可复现 |
| 模板构建与目录 | 构建状态/日志、归属、别名→修订映射及产物清单 | 创建一次固定正确授权的修订 | 已有自助构建与正式登记；待接中心目录和受保护 HTTPS 只读产物分发，Redis 只存描述；节点校验并有界缓存 |
| 每实例系统盘 | 用户进程、安装依赖和文件操作产生的数据 | 保证运行期间可写且实例间不共享修改 | 已实现：每 VM 完整复制的私有 ext4 文件；不是共享卷或快照服务 |
| 运行诊断 | 服务错误和恢复异常 | 查明失败原因，不作为唯一安全证据 | 基础 stderr 诊断；完整容量部署显式丢弃 VM 控制台输出，不默认保留无界日志；没有集中检索和指标平台 |
| 测试证据 | 精确提交、版本指纹、探针结果、故障点、残留检查 | 复现实验，区分通过、失败、未运行和未覆盖 | 测试输出及忽略的 `artifacts/`；专用两题晋升已接通，完整系统矩阵仍由 #14 跟踪 |

SQLite 和宿主登记不是两个各自决定业务状态的控制器。前者记录控制决定，后者记录真实执行身份和证据；两者不一致时要进入核对流程，不能任选一边当成功。

正式控制服务采用完整容量配置和格式 5 检查点＋连续输入尾恢复；公开模板构建的 Python `BuildStore` 则使用独立的格式 4 状态库，两者不是同一种数据库格式。永久逻辑身份不会回绕，物理位置在精确释放后才能复用。当前格式、相同持久配置的非空数据库支持正常重启；旧格式、不完整配置或损坏记录明确拒绝，不自动升级、补造或降级到无维护、无请求窗口路径。完整配置先校验、只读预检，随后取得宿主租约、开库重检、恢复，最后监听；格式与配置细节见[模块合同](module-contracts.md)。这些机制与有限实机测试不等于已经证明无限期运行；证明范围仍单独记录。

### 4.2 “资源观察”不等于“可观测性平台”

这两个词容易混淆：

- **安全所需的资源观察**：例如确认原 PID 对应的同一个进程已退出、检查真实网络规则、发现遗留磁盘。它直接影响是否允许发布成功、释放预算或重试，是 #10/#11 的核心，不能后置掉。
- **运维可观测性**：例如请求耗时曲线、日志搜索、CPU 历史图和告警面板。V1 需要基本诊断和证据，但不要求建设独立的数据分析平台。

所以，对“是否要做可观测性的存储”的回答是：**需要保存必要记录和证据，不需要为 V1 专门部署 ClickHouse、时序数据库或集中日志集群。** E2B 的集中可观测性还服务于云规模运营和产品查询，不是 Firecracker 启动沙箱的必需组成。

轻量处理也不能等于完全不管日志。部署仍要限制读取权限、避免输出凭据和用户敏感内容，并安排日志大小与保留策略；当前基础日志不代表这些运维工作已经全部完成。控制器不能用“日志里有一行启动成功”代替真实资源观察。

### 4.3 中心 Redis、本地 SQLite 与模板产物

Redis 保存中心全局协调责任；SQLite 保存各节点本地控制进度，两者不互相替换、不共享原子事务。首版使用有界权威控制块，CAS 的全部检查先于单条提交写入，确认耐久后才能派发；写入结果未知时查询原操作，不按新实例重试。AOF、内存与重写预算、单有效写者以及错误恢复合同见[中心持久化与恢复](module-contracts.md#中心持久化与恢复)。

模板产物保持不可变，首次在节点受控下载并校验后缓存，运行盘单独可写。中心统一目录和别名，不要求 Redis 保存磁盘，也不要求每次分配重新下载。受保护 HTTPS 产物服务足够承担当前分发合同，云对象存储可以后替换实现；不引入快照存储链。

## 5. 主要运行流程

5.1–5.5 描述已实现的本地算法；目标全局连接见 5.6。公开兼容语义保持不变，新增中心不能用旧本地实测代替双服务验收。

### 5.1 创建沙箱

1. API 验证用户，检查模板、参数、权限、寿命和资源准入；启用模板目录/登记时解析并持久绑定不可变修订与资源形状，未启用仍只接受 base。
2. 控制服务把接受决定和待执行工作提交到 SQLite，建立实例身份及受保护凭据。
3. 控制核心安排围栏、资源预留和准备动作；节点登记精确资源身份。
4. 宿主先建立默认拒绝的隔离网络，再准备独立磁盘，通过 jailer 冷启动 Firecracker。
5. 节点检查真实 VM、网络和磁盘，完成 envd 健康检查及鉴权初始化，返回对应动作的观察。
6. 控制服务提交回执，核心满足发布条件后才进入运行状态，API 才返回可用实例。

这是多个提交与外部动作组成的流程，不是一个能同时原子控制 SQLite 和 Linux 的“大事务”。任一步中断都可能留下部分资源，所以必须记录身份并处理未知结果。Firecracker 进程启动了，不等于沙箱已经可交给用户。

### 5.2 执行命令和传输文件

请求到达网关 → 检查令牌、实例归属、阶段和寿命 → 选择固定 VM → 转发允许的 envd 接口 → 返回输出或文件。

当前中继进入该实例网络空间，访问固定来宾管理地址；不依赖 Redis 找节点，也不提供任意端口代理。请求体、文件和一元回复保留大小限制；命令持续输出不设累计字节上限，使用有界在途缓冲、背压和撤销，见[数据通道合同](module-contracts.md#数据通道c--ab--来宾)。用户命令可能有副作用，因此连接断开只表示没有拿到确定结果，不能自动重新运行同一条命令。

内部只保留 `relay` 入口及唯一的有界缓冲转发实现，不再保留无实际差别的 `relay-bounded` 别名或模式参数。宿主仍先取得许可、登记精确进程后放行；半关闭、撤销与排空责任不变。这是受管内部协议整理，不增加不受管中继路径。

用户在虚拟机内改 `/etc`、安装软件或使用绝对路径，与访问宿主的同名路径是两回事。V1 的隔离依靠独立虚拟机/磁盘和受限宿主接口，不通过把所有文件强塞进一个工作目录来假装兼容 E2B。

### 5.3 连接、续期和到期销毁

连接只返回同一个运行实例，并按合同延长寿命；不会创建第二个实例。显式设置超时以服务端时间重算截止时间。到期扫描在提交销毁前重新检查截止时间，避免旧扫描结果误杀已经续期的实例。

当前常驻服务已接入时钟和周期扫描。定时扫描不是硬实时承诺；如果宿主结果未知，服务必须先核对，不能为了赶期限而猜测旧实例已经停止。

### 5.4 主动销毁与资源清理

接受销毁 → 撤销后续访问/执行资格并推进终止围栏 → 对精确绑定的 VM 执行停止 → 观察确认停止 → 发布销毁状态 → 回收对应磁盘和网络 → 确认回收后释放预算。

“已销毁”与“所有清理工作结束”要区分：前者不能早于真实停止证据，后者决定残留资源和预算是否已释放。保留的身份记录、故障证据也不等于还有一台可执行 VM；不承诺磁盘介质的物理安全擦除。

### 5.5 服务重启和丢失回执

以“VM 已启动，但回执尚未写入数据库，服务就退出”为例：

1. 数据库显示动作已派发但无最终结果，因此标记为未知，而不是重新创建。
2. 重启服务读取节点登记，并核对用户、沙箱、代数、VM 编号、PID/启动时间和网络身份。
3. 有充分证据时补交观察，继续原操作；只准备了一部分且能确认未运行时，按精确身份回收。
4. 资源仍活着但证据不足、身份不符或无法读取时，保留未知并拒绝相关后续动作，不按进程名或目录名前缀批量清理。

恢复依靠原数据库、资源登记和真实观察，不重建用户程序的内存或命令历史。已交付恢复用例与适用提交见 [#11](https://github.com/ningZhang-cs/sandproof/issues/11) 及[测试清单](testing-plan.md)，不是所有可能故障的验收声明。中心/节点/Redis 独立重启、消息丢失与分区是双服务的待验收合同；宿主掉电后的运行内存恢复、整盘丢失、任意备份回滚和恶意管理员不包含。

### 5.6 待实现：中心到节点的完整链

中心持久接受创建并保留身份/固定节点/额度 → 派发原高级请求 → 节点持久接受及映射 → 原本地启动/就绪 → 节点保存事实 → 中心耐久应用 → 对外成功。中心保存后发送接收确认，节点只能在责任、窗口、保留与引用条件满足时退休。

丢回执或中心重启不重启原 VM；中心查询原节点或重发同身份同参数。销毁先提交中心终止意图、拒绝新中心资格，节点收到后持久落实围栏与本地撤销，再真实停止和清理。公开 kill 成功至少有原 VM 停止证据；额度在精确清理后释放。分区不承诺中心提交瞬间停止来宾，本机到期独立执行。两端各自未知状态是合法状态，不要求进度始终相等。

## 6. 网络与权限边界

隔离测试机可为通用 Harbor 链显式启用[本轮代理出口](../tools/benchmark_proxy.py)：构建池和运行池原防火墙先检查权限，已获准的公网 IPv4 再经独立 TUN 服务连接宿主回环 SOCKS 代理。它不改宿主默认路由、不向来宾暴露宿主端口、不复制 VPN 凭据，也不劫持 DNS 或修改题目。只有本轮两池的出口接口被选择；代理故障保留不可达后备路由，不自动退回直连。此项是可信测试部署的传输配置，不是新授权机制、普通 CI 网关或已验证的生产代理系统；第三方代理与外网仍在证明边界外。

Firecracker 提供虚拟网卡及其宿主 TAP 接口，**不替我们做出站访问过滤**；过滤由宿主实现。这也是 [Firecracker 官方设计](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/design.md#threat-containment)明确区分的职责。

| 层次 | 负责什么 | 不应依赖什么 |
|---|---|---|
| 管理 API | 识别用户，拒绝越权生命周期请求 | 客户端自报的用户身份 |
| 核心与持久服务 | 当前访问资格、代数、配额、决定和恢复 | 仅凭 HTTP 成功就修改业务状态 |
| 宿主执行和防火墙 | 精确资源绑定、真实停止、来宾出站边界 | 来宾 root 不会改配置或不会恶意联网 |
| Firecracker/jailer + Linux/KVM | 虚拟化和宿主进程隔离机制 | 我们的状态机定理能替代底层隔离正确性 |
| 来宾 Linux/envd | 来宾内进程和文件操作 | 来宾自报信息足以证明宿主安全 |

当前服务默认只启用显式禁网：每 VM 私有网络空间，默认拒绝来宾主动出站，保留宿主发起的管理连接及其回复。部署显式开启后，可为每 VM 安装独立 IPv4 出口；其宿主 INPUT/FORWARD/NAT、来宾闸门及资源身份均须观察成功，才能发布运行。已有禁网模式的来宾 root 改写解析配置、DNS 和 IPv6 探针，以及公网/静态模式的选定真实 VM 流量测试；具体覆盖以[验收清单](testing-plan.md)为准。

公网与静态 IPv4 规则已按固定 SDK 创建字段接入，并在测试专用外部网络空间验证选定允许与拒绝路径；这不表示真实互联网、DNS 或所有故障/并发路径已验收。它们在平台隔离底线内表达每个沙箱的授权，不靠来宾自行遵守。

IPv6 的细粒度放行、通用域名授权、受控 DNS 解析服务和运行中动态修改规则先不纳入 V1。**功能可以后置，阻止旁路不能后置**：未支持的 IPv6 不能意外出站，禁网不能经宿主 DNS 代理通向外网，静态 IPv4 也不自动放行公共 DNS。仅固定解析器 IP，并不能限制查询内容或防止通过域名携带数据。网络模式和优先级的精确定义仍归[模块合同](module-contracts.md)及兼容清单维护。

## 7. 与 E2B 架构逐项对照

| E2B 架构中的部分 | Sandproof V1 的对应部分 | 保留或简化的原因 |
|---|---|---|
| API：生命周期、认证、配额、节点选择 | 待实现中心入口/核心/Redis；复用现有 API 解析 | 全局准入及静态节点选择；不复制本地工作算法 |
| orchestrator：每节点运行管理 | `sandbox-node` + `sandbox-runtime` | 保留实际启停、隔离、观察、清理；不复制全部运行平台 |
| client-proxy + 节点 proxy | 现有本地网关＋待实现中心网关 | 中心固定路由，节点当前资格再次核对；两端预算和撤销 |
| envd | 复用固定版本 envd | 保留客户端协议，避免重写进程/文件服务 |
| PostgreSQL + Redis 的不同业务职责 | 待实现中心 Redis；已有节点 SQLite 与资源登记 | 权威职责不同，只有一个有效中心写者；不逐一复制 E2B 数据库布局 |
| 模板快照、内存按需加载、磁盘写时复制 | 本地镜像 + 每实例完整盘副本 + 冷启动 | 接受启动和磁盘成本，避免把快照性能工程引入 V1 |
| template-manager | 已实现预制目录、自助构建/转换/登记与运行绑定 | 复用开源工具，保留自助入口、不可变产物与启动检查，后置完整平台和快照加速；不假称完整原模板 API 兼容 |
| GCS/S3 中的模板/快照产物 | 不可变产物＋待实现 HTTPS 分发/节点缓存 | 不强制云对象存储，不保存运行内存快照 |
| ClickHouse / OTel / 集中日志 | 基础诊断、持久恢复记录、实机测试证据 | 保留安全必需观察，后置大规模运维分析平台 |
| pause/resume、自动唤醒、checkpoint | V1 明确不支持 | 后续阶段另做状态、存储、恢复与验收 |
| dashboard、共享卷、集群伸缩等 | 当前交付不实现 | 固定核心子集、静态登记和有界规模 |

这些简化不表示 E2B 的相应设计没有必要，而是两者规模和目标不同。也不能仅凭我们有状态机证明，就推断实际网络、存储或崩溃恢复一定比 E2B 更安全；每一项承诺仍需具体实现、测试及对应证明。

## 8. 部署与开发形态

本机 macOS 可开发控制、存储、API 和协议测试；真实沙箱运行需要固定的 Linux/KVM 主机。目前 `sandproof-server` 以高权限执行宿主操作，jailer 再将 VM 进程降到独立非特权身份。配置、凭据、数据库、节点状态和可执行文件都必须位于可信且受保护的路径。

当前本地部署由一个常驻服务、本地 SQLite、受保护模板/实例盘和 Firecracker 进程组成。目标首次工程部署在一台 KVM 主机上另行运行中心和权威 Redis，中心与节点账号、目录、端口和配置分离；中心不需要宿主高权限。双向证书、可信端点及单有效中心写入者必须保持，即使同机。多物理节点验收另行推进；不要求 Kubernetes、Nomad、Redis 集群或云对象存储，也没有自动部署流水线。

这仍不是一份“照做即可上线”的生产运维手册。监护重启、TLS 配置、日志保留、备份和完整恢复演练须随部署验收落实。专用 App 的两题 KVM 晋升检查已接通，完整故障与资源压力矩阵仍由 [#14](https://github.com/ningZhang-cs/sandproof/issues/14) 跟踪；两者不等同。高权限执行的信任边界见[CI 运行环境](ci.md)，晋升规则只在[开发指南](../CONTRIBUTING.md)维护，不能让任意外部 PR 在测试宿主执行。

## 9. 测试与证明如何落到这套架构

功能验收分层：纯核心/存储/API 测试、模块组合与故障注入、Linux/KVM 实机、固定 SDK 兼容，以及 Harbor/Terminal-Bench 回归。它们覆盖不同合同，不是一条每批都要从头跑全集的流水线；后续重构重跑受影响层次，不能只靠证明编译判断服务仍可用。完整场景和判据只在[V1 验收清单](testing-plan.md)维护：冻结的 2.0 是当前兼容回归；专用两题是预装环境的稳定晋升子集，不验收本轮模板构建；2.1 已有独立锁与工具入口，原环境/原解答/原评分 89 题全量仍为发布前待办。版本锁和运行方法见[评测说明](../benchmarks/README.md)；旧成绩不自动成为新版本证据。

本地服务已有选定 SDK、网络流量、启停丢回执、多模板隔离、自助构建及通用任务链的分批实机证据；实际交付和未运行项由对应 issue/PR 的精确提交与配置判断。历史结果不自动覆盖新候选；中心/节点网络、Redis 和独立故障验收仍待 #292 交付，完整 2.1 原题验收为发布前待办，不将两题晋升当整套系统矩阵。

形式化目标按[验证设计](formal-verification-design.md)分为模块模型性质、真实 Rust 精化和系统组合。先完成 #292 功能/故障/实机交付并冻结组合提交，再闭合“中心创建→原节点就绪→丢回执→中心重启→原身份恢复→销毁清理”，随后按批扩展查询、两端网关、容量、保密及条件完成性。Charon/Aeneas 的固定支持子集、最小外部原语、真实事务/锁/异步连接分别审计，不能将全部自有适配当可信黑箱。

既有纯核心的证明不自动覆盖新增 SQLite、HTTP 网关、节点执行代码或整个 envd；Redis/SQLite 引擎、操作系统、Firecracker/jailer、硬件及原语的信任假设必须单列。我们追求“声明边界内的完整验证”，不是把难证明的自己编写的安全逻辑全部划到边界外，也不是证明底层虚拟化永远没有漏洞。

owner 明确排除的模板子系统是例外：构建器、Dockerfile/OCI 处理、镜像转换和自有构建编排/模板登记/发布整体不做形式化证明，以测试和运行检查验收。核心以正确授权、不可变修订、准确摘要/资源清单及可启动描述为显式外部前提；这些前提没有被证明。核心自身的实例绑定、准入、生命周期、访问撤销、恢复及精确清理仍保留证明目标，不能宣传镜像供应链或整套平台已验证，详见[覆盖记录](proof-coverage.md)。

| `SandboxModel/`、`verification/` | Lean 规范、Rust 翻译产物和对应证明 |
