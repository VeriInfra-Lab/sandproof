# 证明开发工作流

[文档目录](README.md) · [通用开发规则](../CONTRIBUTING.md) · [工具链](../verification/README.zh-CN.md) · [验证设计](formal-verification-design.md)

本文用于证明开发批次。当前 V1 功能开发按[项目蓝图](project-blueprint.md)
与[测试计划](testing-plan.md)推进，不要求新增功能逐项先完成证明。
既有证明的适用版本和后续缺口必须准确记录；进入证明批次时仍执行下述完整验收。

## 证明批次的组织顺序

目标与任务以[验证总览](formal-verification-design.md)链接的新 V0–V9 为准；实际结论只写[覆盖记录](proof-coverage.md)。第一阶段是完整生命周期闭环，未实现状态不标已证，未采用接口不先造通用库。

| 工作 | 完成条件 |
|---|---|
| 合同/可行性 | V0 最小公共接口与 V9 不变量；核对原工具支持、真实 snapshot/guest 前提和新故障规则 |
| 真实穿透 | create→运行态修改→unload→manager 重启→resume→继续修改→destroy；实际状态与资源见证 |
| 三个证明切片 | 暂停交接、唯一恢复、材料回收逐片同步业务实现、真实生成体对应、边界连接及故障测试 |
| 系统闭合 | LC-G1–6、LC-P1–14、LC-I1–10 和实机矩阵；包括正常接受和实际 driver 的条件进展 |

旧 create→丢回执→恢复→销毁首链保留为基础，不能代替新闭环。所有允许微步骤中的崩溃、未知提交、部分效果、迟到/重复/乱序消息、取消和终止竞争都需要进入所属模型；不是只证明一次顺序演示。普通检查在独立测试环境，形式化任务在证明环境，沿用下文完整入口和证据复用规则，不同批次/配置结果不能拼接。

设计文档变更不自行刷新冻结记录。若影响已登记证明输入摘要，先把旧结果限定于原候选；后续证明批次检查语义/抽取及完整验收后才能更新对应冻结记录。文档通过不等于新增生命周期定理通过，也不能改弱门槛使旧证据自动适用。

### 模块任务的开工与依赖审查

每个模块issue引用所属详细计划，不复制一套规格；按 [V0开工与完成条件](formal/00-foundations.md#5-开工与完成条件) 填写本批实际入口/输入、故障、表示关系、定理/性质ID、提供方、精确版本和未覆盖项。LC-P1–14 和 LC-I1–10 的提供者在 V9 维护。

先固定本切片所需 V0 公共合同与 V9 最小系统不变量；中心、本地控制/执行、公开/数据三线按最小合同交付第一链路，V9持续核对邻接前提。不是先把所有叶子模块证明完再组合；同一crate的共享事务/状态须明确负责人和共同不变量，不各造一份模型。

抽取/异步/Lua 等可行性试验须报告实际支持范围、剩余桥接及失败原因。已存在的稳定同步函数可以按精确提交、调用闭包、输入域和合同独立开工；不要求先完成全部 V0、Resume/GC 或晋升 E2E。函数尚未实现或接口未确定的任务只能先做规格，不认领实现证明。

每个并行包先检查原冻结输入差异、实际抽取能力与前提提供者，再证明真实生成体；输入变化不能只换摘要。各包独占模块证明、薄调用根及私有构建目录，公共生成物、根导入、依赖表、冻结清单和覆盖记录由同一集成负责人协调，不并发刷新。issue 无负责人时保持待认领，不虚构 Ready 或 assignee。

每次交付分别报告以下事实，不合并成一个“完成”：

- 功能实现：原生产入口、持久状态和驱动已接通。
- 工程验收：某精确候选的普通/组件/实机判据已通过，写清实际执行与证据复用范围。
- 局部证明：模型定理报告其内核检查和输入域；若声明实际实现对应，另列真实生成体、表示关系及对应定理，不能把条件模型当作 Rust 对应。
- 公共证明接线：原生 case、正式任务、Lake/实际文件和总审计已登记，并取得对应范围的完整结果。
- 系统组合：各自有条件已由实际提供方落实，满足 V9 的目标与验收；发布晋升另按开发指南。

功能与有限工程验收已有结果时，后续待办应写“实现对应/组合未证”或具体未覆盖场景，
不能重新标成“尚未开发”。历史冻结/路径失败保留原版本；后来已经修复的失败不继续
列为当前阻断。可以继续有明确边界的局部工作，但不能跳过原完整入口来声明整套通过。
实际状态仅在覆盖记录维护；工程合入、局部定理和一次普通入口通过都不自动完成公共
证明接线或系统组合。发布仍满足开发指南的普通检查与 E2E，不因证明切片可开工而豁免。

### 骨架与未解义务

每批骨架只展开所需类型、定理、表示关系、不变量与辅助引理。每个未解任务写明产品条款、输入/故障、前提提供方、依赖、实际入口/版本、负责人和诊断，区分：

1. 计划或形式化声明：类型已定，仍未证明。
2. 有条件组合定理：已证明模块/连接条件成立可推出系统性质；尚未落实的自有条件显式保留。
3. 指定实现的有条件闭合：边界内业务条件由适用版本证明实例化，仅留下依赖登记中的外部合同、获批可信适配与部署条件。结论必须带这些条件，不能称适配代码也已机器证明。

类型检查不等于证明；未解条件不能藏入自定义公理、目标本身或不可满足的前提。检查合法初态和条件可实现性，双向依赖用共同不变量初始化/逐步保持，禁止循环假设。正式证明库不用 `sorry/admit` 或绕过内核检查；临时目标与探索只放隔离环境或任务记录，不导入成已证成果。

获批合同作为显式参数/前提接入有条件定理，不通过添加自定义公理取得无条件结论。每项条件标明外部依赖、可信适配或待证业务提供方；审查/测试只支持相应可信条件的采用，不冒充该条件的机器证明。

智能体可读取目标、隔离尝试、检索/复用引理、填写证明与报告反例，不自行改弱业务性质、写生成产物、扩大可信边界或改变工具版本。当前已获批的薄适配范围以[依赖登记](formal/dependencies.md)为唯一明细，按符号登记不是继续扩大到整个业务服务的许可。难点区分已证、正式反例、缺条件/引理、工具障碍、未解决；搜索失败不等于命题为假。中间引理可重写，超出已登记范围的新假设或业务目标变化须独立审查。

## 环境与接入

- 保持 `lean-toolchain` 和 `lake-manifest.json` 固定，不为工具接入升级证明依赖。
- 本地工具使用 `.tools/lean-mcp` 专用环境，直接依赖版本记录在
  `tools/lean-mcp-requirements.txt`。
- `scripts/lean-mcp-server.sh` 启动真实的 lean-lsp-mcp，仅走本机标准输入输出。
  已关闭外部搜索和工具内的构建入口；完整验收仍由项目原有脚本负责。
- Codex 注册名为 `sandbox-lean`。注册成功不代表当前会话已经重新加载工具。
  在客户端重新加载前，可以通过
  `.tools/lean-mcp/bin/python tools/lean_session.py` 使用同一个服务的标准客户端。
  该客户端仅转发请求、记录版本和结果，不代替 Lean 检查证明。

开始执行前先查本批私有环境交接，确认当前角色的固定 wrapper、实际工具/依赖、
源码/缓存/证据目录及重任务锁。证明隔离环境显示的虚拟路径与宿主物理路径分别记录；
虚拟旧路径存在不表示工具失效，宿主迁移也不授权重装或升级工具。私有账号、地址、
物理根和凭据不写入仓库。已有固定入口可用时先复用；若预检失败，记录未启动及具体
原因，不重新安装整套环境，也不把排队算作证明执行耗时。资源排程、保留与回收规则见
[CI 运行环境](ci.md)。

## 每个证明的工作顺序

### 翻译障碍的识别与处理

公共处理统一归 [V0 #632](https://github.com/VeriInfra-Lab/sandproof/issues/632) 的 [T0–T8 验收点](formal/00-foundations.md#3-t0t9-的有限验收清单)，原 #515/#510 不再维护平行计划。先复用 [依赖保证](formal/dependencies.md#如何阅读和使用本页)，再补本调用的输入、对象、结果与失败连接；公共合同已有时不另造同类模型。T9 排除。


本轮默认使用固定原 Charon/Aeneas，抽取真实同步业务核心；生产仍调用真实依赖，验证时以接口模型表示它们的允许行为。Tokio 及依赖登记中逐符号列出的少量任务、锁、资源移动与取消适配可作为可信边界，通过源码审查、精确版本与受影响合同测试核对；不以先完成通用 Future/poll/Pin/Drop 翻译或独立解释器为前置任务。T9 排除不取消本阶段必经的 Guest 撤销、重授权和断线责任；完整 Guest 证明后置。

每个接口分别写出安全保证、功能结果和额外进展条件，以及未知提交、部分效果、panic/JoinError、调用方取消和真实工作退出的区别。不能用总返回成功的桩，不能把 Busy 统一解释成“回调未执行”，不能以 Drop 或等待结束代替子进程/网络/宿主资源的真实退出证据。互斥、许可捕获和任务机械接线可依赖获批适配合同；授权、快照/请求绑定、动作及提交顺序、未知处理、释放决定和内部启用/无环等待仍由业务证明与组合提供。

每批先对声明的真实入口及其依赖运行固定工具链的抽取预检，记录源码、目标、配置、工具版本和失败阶段。先区分业务行为错误、翻译器不支持的结构、缺失库模型与尚未完成的证明；抽取失败本身不说明业务规约被违反。相关任务在验证总览的新 V0–V9 下关联实际处理 issue，复用已有确定提交和证据，同一共享障碍由一处负责；依赖未合入时明确登记堆叠关系，不重复实现修复。

抽取前将上一份中间产物保存在隔离证据目录，确认本次工具实际重新生成预期文件后才交给翻译器。输出路径须与驱动的真实工作目录和冻结配置一致；不能读旧文件取得一致性，也不能删除中间表示字段来掩盖跨工作区差异。

对翻译器结构限制，优先采用职责清楚、保持业务行为的小范围代码重构，再证明实际新实现符合原规约；尚未授权生产修改时先在冻结的隔离副本验证候选。审查检查顺序、首个拒绝、短路和提前返回、状态与调用顺序、异常及借用对象。接口桩只替代已登记的边界调用，不复制业务算法或删除效果；接口签名仍不可抽取时，改用具体值/句柄和显式结果的小接口。不得以验证专用替代算法、改弱规约或遗漏实际入口解决障碍。对照测试提供回归证据，不作为一般性等价证明；抽取成功也不等于实现已证明。

重构后重跑开发指南要求的基础及受影响合同检查，重新抽取实际入口，更新表示关系、对应证明和适用版本；完整验收仍保留原入口和失败判据。不受影响的局部证明可以继续交付，未闭合依赖显式保留，分别报告局部通过与整套结果。

同类限制反复造成大量机械改写，或重构明显损害可读性、性能、维护成本时，单独评估上游修复或工具补丁。工具变更需明确支持范围、拒绝行为、版本、回归及受影响证明闭包，并审查[转换正确性责任](formal-verification-design.md#4-rust-与模型的连接)。新增转换规则的模型定理不能自动背书实际补丁；未经对应论证的部分仍属于明确的工具信任条件，不在普通证明批次中静默替换工具。

### 局部证明开发

1. 先读取当前位置的目标和相关条件；不要凭旧编译日志猜测当前状态。
2. 使用 `lean_multi_attempt` 在隔离的试验文档中尝试候选步骤。
   正式文件只写入经过试验的方案；探索代码不得作为已完成证明汇报。
   候选步骤使用单行；复杂多行证明改用 `lean_run_code` 检查完整的小引理。
   当前工具的多行替换会跨越相邻源码行，不适合直接在分支头部插入多行方案。
3. 一个处理函数先通过，再扩展到其它处理函数。
4. 拒绝检查按程序的顺序处理：当前分支拒绝后，不展开后续查询的组合。
5. 公共引理分别处理查询、字段转换、计数器、容量、判断条件和结果对应。
   不用跨多个处理函数的大型自动化宏掩盖尚未解决的局部目标。
6. 文件修改后重新读取目标与错误诊断。无错误、无未完成证明才能进入验收。

## 版本与试验记录

标准客户端将请求、耗时、工具版本、文件及项目源码指纹、依赖清单指纹、
结果写入本地忽略目录 `artifacts/lean-session.jsonl`。
调用期间源码变化则返回 `stale: true`，不能用该结果确认新文件。
可传入 `expected_sha256`，拒绝针对已经变化的文件继续旧试验。
复用失败记录前必须确认目标、条件及环境未变；不把失败策略永久禁用。

同一文件版本只运行一轮构建，不让旧构建结果指导新源码。
修改被导入的模块后，先单独构建该依赖；交互检查当前文件不能替代导入产物更新。

## 检查层次

- 局部步骤：读取目标、隔离试验、增量诊断。
- 单个完整证明：确认没有错误，并检查实际证明依赖。
- 一批完成后的验收：运行 `scripts/verify-controller.sh`，保留 Rust 测试、
  静态检查、自动提取一致性、全部证明模块检查及证明依赖审计。

当前自动抽取根按公共基础、共享状态和 Linux 首链分别登记，并未覆盖统一控制器或全部新增 crate。旧整控制器生成物及其专属对应证明按 owner 决定退役，不纳入当前验收；各保留模块仍须完成其实际重抽取一致性与审计。新增模块的第一批需接通实际抽取/外部模型/微步骤对应及审计入口，清单记录源码提交、目标/features/cfg、工具与模型摘要、生成根、目标定理和依赖闭包；不能仅跑旧根便报告V1–V9通过。详细接线随对应证明批次交付，本次计划拆分不修改CI门槛。

默认构建成功不代表所有探索中的模块已通过，也不代表所有控制器输入已覆盖。
不修改检查脚本来排除失败模块，不以占位证明、自定义假设或调试开关绕过检查。

### 普通测试机与证明机的分工及证据交接

普通 CI 继续使用现有 ning 上的隔离 runner。普通 Rust/Python 测试、格式、
Clippy、SDK、组件回归和错误实现的原生断言也都在 ning 执行。
证明机（如 msra）仅运行证明所需的编译/MIR 捕获、固定 Charon/Aeneas 抽取、Lean 构建、
形式反例、真实文件诊断和依赖审计；不在证明机安装或复制另一套 CI 环境。

一次完整证明批次先在 ning 的确定提交上运行：

```sh
# 使用现有的固定 Rust、Python、离线 Cargo 和真实 Redis 环境。
export CARGO_NET_OFFLINE=true
export SANDPROOF_REDIS_SERVER=/path/to/fixed/redis-server
export SANDPROOF_SQLITE_STATEMENTS_SOURCE_ARCHIVE=/private/acceptance/sqlite-original.tar
export SANDPROOF_CHILD_OBSERVATION_SOURCE_ARCHIVE=/private/acceptance/child-original.tar
export SANDPROOF_WRITER_SOURCE_ARCHIVE=/private/acceptance/writer-original.tar.gz
export SANDPROOF_LIBRARY_SOURCE_ARCHIVE=/private/acceptance/library-original.tar
bash scripts/python-entry.sh tools/proof_native_suite.py run \
  --output /private/acceptance/native-evidence
```

这个入口包含完整 Linux `check-function.sh`，并运行原证明入口中的独立抽取
crate 测试/Clippy、任务持额、撤销、持额消息、Notify、JoinSet、标准 Mutex、Condvar、Tokio RwLock、原 Child 观察、有状态回调、JSON、TLS、relay、SQLite、Redis、BTreeSet 插入、Metadata 目录判断和 Tokio Mutex 候选回归。
保留原测试数量、拒绝断言、正确/错误版和新编译二进制检查。它不运行 Lean
或翻译器。原生错误版仍须确实编译并触发原断言；构建失败不能写入成功记录。
变体使用同一 Cargo target 时，还须检查实际业务库与测试二进制都绑定当前源副本；
新测试二进制不能证明其链接库已更新。Tokio RwLock 入口逐变体重建本自有包，并在结束时
移除错误版包缓存，保留其它依赖。原 Child 入口同样绑定实际同 crate 的业务测试程序，
检查 package/manifest/src/fresh，并只清理 sandbox-runtime 自有包的变体缓存。源码时间较旧不能作为复用前一变体库的依据。
SDK、Harbor、分布式合同继续由现有 CI 原入口检查，不能用这份证明批次记录替代。
涉及整文件 CoW 的 ning 普通测试须把 `TMPDIR` 配在已具备 XFS 条件的安全父目录；
入口保留该文件系统并新建 0700 私有子目录，逐级核对属主、模式和非符号链接，非法显式配置直接拒绝。
稳定的父目录身份参与原生缓存判断，随机子目录名不参与；这项 XFS 要求不适用于 msra 的 Lean 编译。

### 一批去重与跨批复用

`tools/proof_batch.py` 保留全部原模块，以及未被根文件导入的每一个保留 Lean
文件、总审计和全部登记真实文件的服务诊断。相同输入的 foundations 生成和嵌套
foundations 检查只执行一次。原脚本的生成物比较、错误版、反例、AST/Drop 检查
和依赖审计仍在模块任务内部执行，不以一次默认构建代替它们。

复用按内容检查，不只比较 Git 提交或某个 `.lean` 文件。记录包含真实 Rust
源码与 Cargo 依赖、配置、模块冻结清单及其父清单、全部本地 Lean 导入、库模型
和合同、生成物、验收脚本/检查器/负例，以及实际工具二进制、库源码和运行选项。
公共 Rust 闭包和验收工具暂取保守范围，变化可能使多个模块重跑；不会为了提高
命中率猜测它们无关。其他模块的 Lean 文件未进入该模块闭包时，不影响其命中。
编译资源同时包括 crate 内的非 Rust 文件、部署/参考/共享测试材料和继承配置，
不能漏掉 `include_str!` 等输入。当前项目没有自有 `build.rs`；以后新增时，须先
登记其生成输入，入口会拒绝未登记的自有构建脚本，不猜测其外部读取。

原生组件还逐字节收录 `verification/` 根级 JSON 合同/环境配置：检查工具所在源码和候选源码分别登记，新增、删除、改动或非普通文件均不能沿用旧输入。四份 SQLite/Child/Writer/目录判断原源码归档按实际内容摘要收录；两机绝对路径可以不同，内容须相同，缺失、修改或改成符号链接即拒绝。归档内容每次读取，不使用固定工具的元数据摘要捷径。原生整批结束及证明机准入再次核对这些输入，形式模块键同时绑定其封口记录；旧版缺少这些字段的封口不能升级标签后沿用。未来检查器读取新的外部文件或不同配置格式时，先登记它的内容输入，不把本条理解成自动追踪任意文件读取。纯证明文件/根级冻结清单仍由形式闭包检查；未进入该组件规则或合同闭包的 docs/ 覆盖报告变化，不单独使原生组件失效。experiments/ 内的说明和检查规则仍在原生规则闭包中；完整功能入口始终按全部跟踪文件重新准入。

仅复用先前完整成功、输入仍一致、日志和原始抽取/反例证据仍存在且摘要相符的
模块记录。失败、中断、缺失、损坏和任何输入不符都不能命中；受影响模块重新
执行。模块列表和本批源代码入场始终检查，新版本不能直接沿用 GitHub 的绿色
状态。`latest-batch.json` 分别记录本批 `RUN` 和历史 `REUSE`；后者不称“本轮重证”。
Status schema、原 Store 共享查询和 SQLite 条件 UPDATE 各有独立封口原生 case 与正式模块；新增 case 缺少、未封口或与当前输入不符时，正式入口必须拒绝。Status 与 TLS 的同名生成辅助声明以及 SQLite 的完整生成根保留独立审计环境；Status 值合同可共同导入。有界 Writer 的完整生成根也具有同名 ContractError 辅助声明，公共总根仅导入其纯 Model；实际对应和36项审计仍由全文件构建、独立模块及实际文件服务完整检查，不与 Foundations 生成命名空间合并导入。正例与错误版实际内核审计均进入总清单，不以公共根未导入实现对应为由省略。

有界 Writer 的私有工作目录与源码/target 分离，正式模块仍固定重抽取两版、检查同性质反例和全部实际文件。批次对只读目录凭据先准入，再收录其新增目录的原始 Rust/LLBC/Lean、服务日志与归档摘要；原始证据缺失或变化会使复用失效。

BTreeSet 插入、Metadata 目录判断和 Tokio Mutex 各有独立原生 case、形式模块及冻结清单；完整入口保留全部正确与错误版审计。目录判断的两份生成环境分开，公共根仅导入 Model，实际对应及全部16份物理文件由组件检查；Tokio Mutex 沿用条件模型与原生错误版，不称 async Rust 抽取。三模块转发经真实服务记录核对的原始审计消息，不自行生成成功消息。目录判断还逐字节核对原归档与八份已审查 Std 原文，并在任务结束时再次核对；新增必需原始输入而旧收据没有收录时必须重跑，不能只检查旧收据已经列出的文件。

原生记录只收录本次真正使用且全部外层断言成功的步骤。未封口批次的裸进程
退出记录不跨批复用；独立组件完成记录可以复用。原生 `uses` 同样区分执行和复用，
重跑前保留旧裸记录。模块耗时包含复用准入的成本，不把缓存核对写成零耗时。

固定工具和库的内容摘要另有本地缓存，避免每批重复读取整个工具安装目录。
它检查文件身份、大小、mtime 和 ctime；刚写入、时间可能落在同一文件系统
时钟刻度内、时钟倒退或摘要损坏时重新读取内容。该优化限于本轮固定 Linux
本地文件系统，依赖其正常修改记录；源码、生成物和证明证据不使用这个捷径。
有界 Writer 的受限嵌套运行还绑定原 bwrap 二进制、外层 wrapper 和宿主目录凭据的实际内容摘要；
缺少配置不能复用旧成功。凭据由宿主固定三个独立数据盘目录身份，在原命名空间中只读挂载并逐次核对；
它是操作者执行记录，不是不可信上传方的证明。配置/凭据始终读取内容，不使用工具元数据捷径。
迁移机器只改变明确登记的私有物理根及执行环境，不改固定工具版本、虚拟抽取路径或生成物。
新机可用有界 Writer v2 目录凭据登记当前操作者拥有的私有工作根；保留设备/inode、
目录互不嵌套、固定 bwrap 和只读挂载检查，不用符号链接伪装旧机路径。每次迁移重新
生成凭据、记录工具/库和 wrapper 的实际摘要；旧机器失败或未完成的验收不能沿用。
`--recompute` 同时重新读取固定工具内容。不能把未知文件系统上的相同时间戳
解释成内容相同，也不能将操作者不可信的摘要记录作为证明依据。
