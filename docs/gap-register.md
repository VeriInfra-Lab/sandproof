# 缺口登记表

> 历史缺口记录。当前 V1 功能、负责人、依赖和验收由[项目蓝图](project-blueprint.md)及 [GitHub 总计划 #1](https://github.com/ningZhang-cs/sandbox-lifecycle-refinement/issues/1)管理。本表不作为当前开发优先级或新增运行服务证明状态的依据。

> 2026-09 方向更正：当前主线是建设边界内 fully verified controller，不再将本地 harness 结果表述为已确认系统 bug。本表中 C2 以及“只有三个关键缺口”的旧排序已被 [verified controller 建设路线](verified-controller-plan.md) 取代。部分失败补偿、失败回执因果绑定、结果未知处理和 kill 取代旧 operation 已接入主模型；accounting 仍是独立子模型，未与 lifecycle `World` 组合。

> 2026-09-22：纯 Rust 控制核心已实现，现有公开输入在明确机器容量条件下的
> Rust—Lean 对应及有限执行安全证明已完成。最终完成性、长期容量边界及生产接入
> 仍未完成；当前可核对的定理和前提见 [证明覆盖记录](proof-coverage.md)。

本文汇总所有已识别的缺口，按"对结论的影响"分类，供优先级决策。区分两类：

- **边界（B）**：我们主动声明不做/不能证明的东西——不是洞，是范围。
- **未完成（O）**：范围内但还没做完的事。

| C4 相对完备 | G-7（复核未完成） | **未定稿**，定稿后为经验结论 |
| C5 verified controller | G-2（最终完成性）、G-9/G-20（长期容量与服务接入）、G-1（adapter） | **尚不存在完整部署系统**；纯 Rust 核心的现有公开输入已完成对应证明 |

## 3. 当前不能再压缩成“只有三个缺口”

旧的“三个关键缺口”排序混合了轨迹校验研究与 verified controller 建设，现已不再适用。当前至少要分开看：

1. 轨迹校验仍受可观察性、映射和历史校准限制；
2. 形式模型仍要闭合等待、执行、选择及最终完成性的整体证明；
3. 已证明的 Rust 纯核心仍需长期容量保障和真实服务接入；
4. adapter 内部正确性始终是明确边界，不能由 controller 证明替代。

## 5. 建议的优先顺序（避免发散）

**第一梯队（收口已有结论，成本低）**
1. G-7 语料复核 → 定稿 C4。
2. G-8 历史校准 → 让"尺子"自证。
3. G-12 witness 扩展 → α 证据面变宽。

**第二梯队（补一个高价值能力）**
4. G-4 节点 VM/slot introspection → 把 2 条 partial 变 observable，C3 直接扩两块。

**第三梯队（大工程，明确靠后）**
5. G-2 为 create/pause/resume/kill 分别闭合进度合同。
6. G-9/G-20 实现 refinement（C5 的唯一路径）。
7. G-5 tight acceptance。

**只写进边界、不需做**
G-1 adapter、G-10 多节点等、G-11 云复现。

## 6. 一句话

模型层已经从纯关系规范推进到可执行且带证明的控制核心，但这仍不等于生产系统。下一步应分别闭合逐工作流进度合同和生产实现 refinement；对 E2B 的候选行为继续只作为验证语料，不再当作已经确认的系统 bug。
