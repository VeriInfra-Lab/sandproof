## 2 预算不能混用

| 对象 | 规则与证明 |
|---|---|
| Start/Connect命令持续输出 | **无累计字节上限**；证明单消息/在途驻留、顺序、并发及写入停滞/撤销，不恢复已取消的累计输出配额 |
| 命令输入/文件/一元RPC | 分别使用 TransferLimits 的输入、上传、下载、rpc_request、rpc_response额度；线上编码与解码载荷分别说明 |
| 转发缓冲 | tunnel每方向固定64 KiB读缓冲不等于所有HTTP frame都≤64 KiB；实际库 frame/队列/多级缓冲需另列上界 |
| 时间 | 请求/文件生产空闲、写入停滞、执行/Connect等待、沙箱寿命不同；安静但仍在运行的命令不因没有stdout自动失败 |
| 并发/控制保留 | 同时受全局及每VM限额，控制请求预留不被普通流耗尽；正文/连接/子进程各覆盖实际生存期 |

期限不能推出内存上界；例如上游一次交付的巨大frame可在期限前耗尽内存。模型必须把自有缓冲、库队列、内核缓冲/辅助输出分别对应其合同和额度；“用了stream”不是资源定理。

## 3 模型与拟定定理

下方 B7/E7 定义每方向有限实现状态；全字节历史为证明用历史变量。转发将任意分块投影到相同有效载荷，不按题目/网站建立协议分支。

| 定理 | 精确义务 |
|---|---|
| `grant_register_revoke_order` | 同次当前资格与在途登记正确协调；中心/节点各自终止后不授新许可，存量撤销/排空另有事件 |
| `route_and_credentials_exact` | 全程目标是原实例/原envd会话；仅宿主向原中继覆写来宾凭据，不泄露公开key或替换目标 |
| `relay_prefix_preserved` | 所有允许短读/短写/分块/取消交错满足Written⪯Read⪯Source及各方向顺序，无重复/伪造 |
| `relay_complete_equal` | 只有原正文完整、待写队列空、无网关错误、需要的结束证据成立才报告相应完成；完整时逐字节相等 |
| `relay_failure_visible` | 截断/超限/撤销/读写错不能补造EOF/成功结束帧；请求方向结束不截断迟到响应，响应错误正确终止对侧 |
| `lease_release_after_exit` | 响应头/取消/等待超时不提前退还正文、socket或辅助执行许可；未知效果保留责任 |
| `gateway_residency_bounded` | 自有计数键、订阅、关联、待写缓冲及任务数/字节由并发/保留预算导出，与实际分配/回收逐项对应 |
| `async_gateway_refines` | 在逐符号登记的任务/撤销信号/I/O驱动合同下，真实同步转发核心、回调及释放决定对应上述事件；不假设一个正确Completed标记 |

主要 S2/S3/S7/S8/S9/S14、F2、DS6/DS8；具体源端命令/文件功能依赖 A_function。HTTP200、正文完整、Connect成功结束帧、shell退出状态分别解释：非零退出码也可以是正常命令结果，提前断线不能当正常结束。

透明中继无需为证明新增 Connect解析器；先证明原帧/错误忠实转发，再凭冻结SDK/envd结束合同建立端到端观察。若实际代码解析/改写帧或输入，就逐字段证明这一真实逻辑。文件上传失败可以留下来宾部分内容，不承诺原子回滚；下载并发写下也不默认快照。

## 4 首批、扩展与依赖

第一链路只认领原资格、终止/撤销、实际中继排空和释放前提，保证销毁真实闭合；完整任意字节流性质仍为后续必做项，不因首条链路通过而丢掉。

后续按三批：（1）纯分类/预算/计数及一次短写循环；（2）双向完整/失败/半关闭与已登记 I/O 驱动接口的事件连接；（3）两端授权撤销＋正文/连接/child额度＋功能端点合同。正常轨迹含零字节、跨UTF-8边界分块、长空闲命令和完整响应；禁止轨迹含第80/100字节断开报成功、迟到响应截断、头已回就释额。同一性质尽量复用 [传输测试](../../sandbox-data-transport/src/tests.rs)、[流测试](../../sandbox-data-transport/src/tests/streaming.rs) 与 [宿主SDK组合](../../sandbox-host-service/src/data_gateway/sdk_tests.rs)。

### 可信适配与业务证明的分界

本轮用固定原 Charon/Aeneas 验证真实同步核心，Tokio 及[依赖登记](dependencies.md)的 B1–B4 薄适配以审查、精确版本和合同测试核对。B3 可以保证原连接的读写结果、短写字节数、撤销信号、任务退出及错误被如实传递，B2 可以保证登记的锁互斥和共享对象身份；不要求先自动精化每次 poll/await/select/Drop，也不假设整个 relay 正确。

仍需证明实际授权与原实例绑定、撤销后的业务拒绝、每次读写对计数/缓冲的更新、短写重试和半关闭顺序、何时允许报告完成以及释放登记。适配不得将取消等待、发送撤销、HTTP 头、EOF、panic 或 JoinError 合并成“已排空且无效果”；部分上传/命令效果和未知退出继续保留。实际 child/socket/body 的结束观察必须明确覆盖哪个对象、哪种退出，业务才可据此解除引用。订阅端最终收到撤销、读写返回或受管进程最终退出是独立进展条件，不从安全互斥或 permit Drop 推出。

输入合同只提供原始结束/错误证据；`CompleteFrame`、`NoGatewayFault`、待写为空、原身份不变及所需业务结束的组合判断仍由实际业务核心证明。若当前循环包含这类判断，应拆成可抽取的小步骤；不得把 `wholeComplete`/`Completed` 的正确性整个纳入适配假设。

依赖 V0、V2/V7 原中心资格、V3 认证身份、V5 原本地资格/终止、V6 子进程事实；A6/A7/A9/A12。V9 连接分区下两端生效阶段，不承诺中心销毁提交瞬间所有字节消失；各自已生效的撤销不授新许可与最终排空分别证明。开工/完成沿用 [V0](00-foundations.md#5-开工与完成条件)。

## 精确条款

以下条款为本模块的规范定义；跨模块条款通过前提提供方连接，不将下游自有义务假定为已证。

### B7 数据通道状态

`G` 对每次请求记录：认证租户、绑定实例、代次、虚拟机与令牌身份、目标路由、许可、注册的连接与辅助进程、撤销状态、两个方向的输入和输出字节序列、协议解析状态、按操作种类适用的字节预算、在途缓冲与单消息预算、空闲与总期限、结束状态。

结束状态至少区分：`Open / Completed / Failed(reason) / Cancelled / OutcomeUnknown`。另外记录请求类型的业务结果，例如命令进程编号、退出码、文件写入确认。一次后台命令“已启动”不等于“已执行完成”。

### C8 终止不是一个瞬时事件

以下时间点按每个负责授权/执行的层分别解释：中心终止提交禁止中心新资格，节点持久落实禁止本地新资格；两者不要求同一时刻。D5 的跨机条件见 [V7](07-public-api.md#d5-两端授权全局查询和跨机时间)。定义三个不同时间点：

```text
t_intent：终止意图和关闭新访问授权提交。
t_fence ：宿主执行围栏生效，旧启动工作被阻止或已纳入停止集合。
t_drain ：已登记的数据通道与辅助执行全部排空。
```

需证明：`t_intent` 之后不授予新许可；`t_fence` 之后旧工作不能再产生新的运行；`t_drain` 之后旧连接不再转发新的字节。已经进入网络或客户端缓冲区的字节仍可能稍后被读取，不能承诺“用户点击销毁后世界上立即没有任何字节到达”。

### D1 获得许可不等于一直有许可

对用户 `u`、请求 `r` 和时刻 `t`：

```text
CanGrant(u,r,Σ,t) := Authenticated(u)
  ∧ Own(u,r.sandbox)
  ∧ phase = Running ∧ ¬terminal ∧ t < deadline
  ∧ effective = Running(与 r 完整一致的绑定)
  ∧ 请求能力属于该授权 ∧ 数据通道预算允许
```

网关授予许可和登记在途连接必须与撤销协调。若先检查许可、后无限延迟登记，销毁可能以为已经排空，再出现旧连接。这是并发顺序的证明义务，不是再加一次普通查询就能证明。

保密性质只包含明确的观察：管理响应、错误类别、列表字段、网关有效载荷和公开计数。不承诺执行时间、共享容量变化或硬件旁路不泄漏信息。

## E 数据完整性的精确定义

### E1 先定义观察位置

对一次传输 `x` 和某个方向，定义：

- `Source(x)`：按协议解释后的源端有效载荷，不含传输编码的长度头。
- `Read(x,t)`：网关截至 `t` 已成功读取的有效载荷字节序列。
- `Written(x,t)`：网关截至 `t` 已成功交给目标连接的字节序列。
- `Observed(x,t)`：目标协议接收方已交付给调用者的字节序列。

`Written` 不等于用户已经读到：套接字写入成功可能只是进入缓冲区。需要端到端交付结论时，定理必须量化接收方观察或依赖相应接收协议合同。

这些完整字节序列是证明用历史；真实网关不需要把它们全部缓存在内存。实现状态只保存有界缓冲、计数、解析进度和连接身份，由表示关系连接到历史。否则为证明“内存有界”而先在实现中收集整个输出，会与目标矛盾。

记 `a ⪯ b` 表示 `a` 是 `b` 的前缀。对不修改有效载荷的方向，所有中间状态要求：

```text
Written(x,t) ⪯ Read(x,t) ⪯ Source(x)
Observed(x,t) ⪯ Written(x,t)
```

对流式源，`Source(x)` 表示该次执行中实际由源产生的序列；它不包含源端本来“打算产生”但从未产生的数据。这些前缀关系证明不伪造、不重排、不重复，但**不能单独证明没有截断**。

### E2 完整成功必须是相等而非前缀

定义 `CompleteFrame(x)` 为协议声明的正文完整结束；`NoGatewayFault(x)` 表示未超限、未取消、未超时、未发生读写失败；`BoundTo(x,b)` 表示全过程使用原实例绑定。

需要建立的网关完成定理为：

```text
GatewayCompleted(x)
  ⇒ CompleteFrame(x) ∧ NoGatewayFault(x) ∧ BoundTo(x,b)
     ∧ Written(x,end) = Read(x,end) = Source(x)

ClientObservedCompleted(x) ∧ 接收端协议合同
  ⇒ Observed(x,end) = Source(x)
```

等长不够，还要逐字节相等；内容相等也不够，还要实例身份正确。把甲的完整文件发给乙，不是正确传输。

若上传和下载采用协议解码，则比较解码后的载荷；HTTP 分块重新分组可以改变线上的表示，但不能改变有效载荷、必要尾部字段或业务结束事件。UTF-8 字符可能跨块，应先证明字节正确，再证明增量解码；不能逐块独立解码后丢弃残缺字符。

### E3 HTTP 结束和业务结束不同

| 响应类型 | 完整性的判据 |
|---|---|
| 声明长度为 `n` 的正文 | 按协议接收恰好 `n` 个正文八位字节；提前断开不是完整 |
| 分块正文 | 每块完整，出现合法结束块，并完成尾部和最终分隔；断流不允许补造结束块 |
| 仅靠连接关闭结束 | 单靠连接关闭，无法区分正常结束与中途故障；不能据此证明源端意图的数据全部产生 |
| Connect 流式调用 | 帧头、长度和载荷完整，最终结束帧合法，业务错误按结束帧解释；HTTP 200 本身不表示调用成功 |

这些差异来自协议本身，不是增加重试就能消除。[HTTP/1.1 消息长度与不完整消息](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)、[Connect 流式协议](https://connectrpc.com/docs/protocol/#streaming-rpcs)

Connect 帧为一个标志字节、四字节大端长度及相应载荷；响应必须有最终结束帧。网关若只透明转发，可证明帧字节和传输错误不被改写；固定客户端对结束帧的解释仍属于端到端合同，不能假称网关自己已经验证了退出事件。

因此，无长度、无可信业务结束标记的上游流，最多证明“网关没有丢弃已经收到的数据”。若希望也承诺源端完整性，需要长度、可信完成标记或更强的源端合同；本设计不借此擅自修改现有兼容接口。

### E4 超限和超时必须保留失败

设允许有效载荷上限为 `B`。对正常成功，要求 `|Source| ≤ B`；对超限传输，允许转发一个有界前缀，但必须结束为错误、取消或未知，不能结束为成功。

特别禁止：

- 把原本 100 字节的长度改写成上限 80，再返回 80 字节“完整成功”。
- 到上限后伪造正常流结束，补上空结束块或成功结束帧。
- 已经发出 HTTP 200 后，把后续错误静默吞掉；此时必须由正文或协议错误让客户端观察到失败。
- 为释放并发名额提前结束计费，但连接、缓冲或辅助进程仍然存活。

预算必须注明计量对象：线上的编码字节、解码后字节、单帧大小、累计载荷、同时在途缓冲分别是什么。若不支持压缩则明确拒绝；不能只限制压缩前或压缩后其中一层，却声称两层内存都被限制。

### E5 文件正确性

对覆盖写入请求，令请求字节为 `B`，目标实例和路径为 `(b,p)`，`t_commit` 为 envd 合同中的写入完成点。功能定理应写成：

```text
A_function ∧ 完整上传 ∧ 对 (b,p) 的成功写入确认
∧ 相应期间没有其他写者修改该目标
  ⇒ FileContent(b,p,t_commit) = B ∧ FileLength(b,p,t_commit) = |B|
```

长度条件排除“写入了正确前缀，但旧文件尾巴还在”。空文件同样是合法的 `B = []`。若存在其他写者，只能陈述本次操作在其约定完成点的语义，不能保证稍后的文件内容仍相同。

这不是断电持久性证明，也不是写失败自动回滚证明。上传断开后文件可能已有前缀；结果未知时不自动重新写入。下载也不默认是并发写入下的原子快照：其源序列按 envd 的读取合同定义。

来宾路径不得被当作宿主路径使用。对宿主文件的安全命题是：“客户提交的文件请求只能进入获批实例的文件服务，不能改变宿主文件操作目标”；这与来宾内部是否允许访问 `/etc` 是两件事。

### E6 命令正确性

一次前台命令完成结果定义为：

```text
CommandResult = (原命令身份，标准输出字节，标准错误字节，退出状态)
```

在 `A_function` 下，结果对应原命令，两个输出流各自顺序保持、没有丢字节，而且结束前已交付该协议承诺的输出。除非协议本身记录全局顺序，不额外承诺标准输出和标准错误之间的精确交错。

退出码非零是命令正常结束的一种结果，不必然是网关故障。后台命令返回进程编号只证明启动确认；执行完毕需另一个完成事件。超时、终止或断线可以发生在命令已产生副作用之后，不能据错误自动重发命令，也不能把“等待结束”当作“进程已被确认杀死”。

### E6.1 命令句柄、终止范围和 envd 重启

本条细化 E6、S1/S4/S9、F2 与恢复合同；不把整个 envd 或 SDK 实现加入自有证明范围。

- 固定 SDK/envd 合同必须分别说明：命令主进程退出/被终止、进程组或后代进程停止、整个 VM 被停止。三者不能互相代替；不默认单命令超时/kill 会杀死全部后代，也不因此新增更强的进程组终止功能。
- Start/Connect 的命令身份和句柄绑定原实例及 envd 的有效执行会话；来宾 PID 只是该合同内的句柄，不是永久身份。Connect 返回哪些历史/新增输出、何时算结束须固定。重连或等待期限不得被当成重置原执行期限，也不得自动重新执行有副作用命令。
- envd 重启可能丢失命令登记而 VM/来宾进程仍在。此时按固定协议报告不可重连/未知，不仅凭相同 PID 接管旧命令；空进程列表不能证明来宾全部进程停止。控制器保留原 VM 身份/绑定/占用，宿主停止与精确清理不以 envd 正常响应为前置。
- 自有入口/路由/转发/撤销决定和失败解释必须证明；薄异步机械接线仅按已登记 B1–B4 合同可信。原命令的真实输出、端点完成事件及承诺的回调排空依赖明确的功能端点合同并做兼容测试。不能把端点故障伪装为正常完成，也不能声称已证明 SDK 客户端全部回调或来宾业务结果。

最小正常轨迹包含原命令开始、重连及合法完成；禁止轨迹包含“等待超时就报告已杀死全部后代”和“envd 登记丢失后仅凭 PID 自动重执行/接管”。使用受控端点故障先检查自有处理；真实端点测试只核对已冻结合同，不复现所有上游缺陷。[E2B #1031 的子进程案例](https://github.com/e2b-dev/E2B/issues/1031#issuecomment-5581469733)、[runtime #3650 的 envd 失效报告](https://github.com/e2b-dev/runtime/issues/3650) 是不同版本的边界线索，不代表当前我方环境已复现。

### E7 数据转发也有可执行的小状态机

每个方向定义实际状态：

```text
StreamState = (原绑定，许可阶段，源结束状态，目标写入状态，
               已读计数 nr，已写计数 nw，有界待写缓冲 q，协议进度，期限)
```

在非错误中间状态，需要 `0 ≤ nw ≤ nr`、`|q| ≤ M`，并且逻辑上 `Read = Written ++ q`。只有带累计预算的操作才另要求 `nr ≤ B`：文件、一元回复和宿主辅助输出各有 `B`；用户命令 Start/Connect 输出没有累计 `B`。`M` 是在途缓冲上限，不由执行期限替代；多级队列的 `q` 是其有序组合，`M` 须覆盖各级及明确的库/内核缓冲前提。证明侧计数可用自然数，不能要求实现保存全历史或使用会溢出的无界累计机器计数。

| 输入事件 | 接受条件 | 更新 |
|---|---|---|
| `ReadChunk(bytes)` | 原许可允许继续、源未结束；需要的机器计数可表示；缓冲预算及本操作适用的累计预算足够 | 在 `q` 末尾追加原字节，增加 `nr`；不能跳过已有待写字节 |
| `WriteAccepted(n)` | 底层确认接受 `q` 的前 `n` 字节，且 `0 ≤ n ≤ |q|` | 从 `q` 移除恰好这段，`nw` 增加 `n`；短写后继续处理剩余部分 |
| `SourceEnd(evidence)` | 该方法和传输编码的完整结束判据成立 | 标记源完整结束；`q` 非空时仍需排空，不能立即完成 |
| `BudgetExceeded / ReadError / WriteError / Deadline / Revoke` | 事件真实发生，原请求身份匹配 | 记录相应失败或取消；不补造源结束；部分副作用仍保留其未知性 |
| `Finish` | 源完整结束、`q` 为空、无错误、需要的业务结束证据成立 | 产生相应层次的完成事件，最后释放在途登记 |

流完成与整个连接、辅助进程排空分开记账；双向流一侧正常结束只关闭该方向，不提前截断另一侧响应。若解析库或套接字库还有内部缓冲，资源证明必须将它们的固定合同上界计入 `M` 或另一项预算，不能因为不在自定义结构体里就忽略。

从以上事件证明前缀关系和完成相等，再把真实同步步骤对应到这些事件，薄异步驱动如实交付原读写/退出结果由已登记适配合同提供，得到“在这些合同下 Rust 网关不会把截断当成功”的路径。未接通的业务步骤仍保留待证；直接假设网关存在正确的 `Completed` 标记，会把待证明内容放进前提。

### I3 一条性质应有正例和反例

100字节源在任意合法分块下完整通过应成功；第80字节断开应失败；预算80时不得改写长度变成功；零字节源应完整成功；上传完成但写入回执丢失应为未知；内容正确但实例身份不符必须拒绝。优先复用已有样例，它们检验规约，不代替任意字节序列/交错的证明，也不代替部署合同的实机核对。
