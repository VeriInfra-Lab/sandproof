# V9 系统组合：责任守恒、隔离、容量与最终完成性

## 3 拟定系统定理

| 定理 | 结论与限制 |
|---|---|
| `global_init_realizable` | 实际初始化配置/数据库/登记对应合法非空Init；排除功能在允许输入下不可达 |
| `global_invariant_step` | 所有模块、通信、独立崩溃、恢复、退休步骤保持共同约束，覆盖DS1–DS8 |
| `adjacent_preconditions` | 每条真实调用上游保证提供下游前提；未知/取消/部分效果和共享写范围均连接 |
| `system_implementation_refines` | 所有指定实现R_i＋相容性/组装证明→任意有限执行前缀符合系统规约；内部空步不丢观察 |
| `global_capacity_and_retention` | 下方F4/F4.1/F6/F7完整逻辑计费、收尾预留、峰值/驻留对应、安全退休；不承诺无限接单 |
| `tenant_observation_noninterference` | 下方G1两执行关系，经同公开资源/允许公开信息/匹配调度产生相同租户观察；不含时间/硬件旁路 |
| `accepted_operation_eventually_final` | 明确外部最终可用与调度前提下，内部工作启用/出队/预算/有限重试/确认顺序已证→L1/DL1 |
| `terminal_eventually_quiescent` | 停止/清理/通信/存储最终可提供必要结果时，无环引用/排空/退休推进→L2/DL2 |
| `local_fault_domain_progress` | 局部错误不由自有扫描、锁、任务或订阅永久阻断可独立处理实例；共享故障按声明范围停止 |

不是把最终正确性列作模块前提后再得出正确性；条件组合定理先显式保留尚未实例化的自有前提，最后必须以对应版本定理替换。状态安全与双执行保密、条件进展分别证明，不能互相代替。

## 4 首条闭环与并行组织

首批声明子集：创建→原节点启动/就绪→回执丢失→中心独立重启→原身份恢复→销毁→停止/精确清理。覆盖子集**全部允许分支与交错**，不是只证明一条示例轨迹。最小V7鉴权/结果、最小V8撤销/排空属于第一批；完整查询/任意数据/保密/长期容量仍保留后续。

V9在V0接口阶段就开始维护Σ、共同不变量和依赖图；不等所有局部定理完成才检查能否组合。三条并行线为中心V1/V2、本地V3/V4/V5/V6、公开与数据V7/V8；第一批按各线最小合同交付，后续按需要扩展，不要求某条线一次全部完成。

扩展后分别验收 P8 的三份产物：容量/退休闭合、双执行保密闭合、条件最终完成性闭合。历史四项未解义务仍按[覆盖记录](../proof-coverage.md#最终完成性已完成与剩余)的精确陈述认领：`ReservationGuardsPersistUnderNoRankDrop`、`WorkflowProtocolClosure.select`、`WorkflowServiceProgress.residual`、所有已接受操作（含被销毁取代的操作）的终局稳定及符合条件的非当前资源最终回收。新系统还须补齐跨实例推进，不能以新模块名称消除旧缺口。

进展证明选阶段/剩余必要工作/有限尝试的良基组合度量，并证明等待依赖无环；消息可丢失的模型只有另加“原操作最终可被投递/确认”等前提才有最终完成性。公平只对已启用工作成立，不能提供启用、预算或外部成功，也不能承诺期限内成功或永久分区下完成。

## 精确条款

以下条款为本模块的规范定义；跨模块条款通过前提提供方连接，不将下游自有义务假定为已证。

### B1 不能只建模纯核心

定义全系统状态，N 是任意满足部署预算的有限登记节点集合，不写死一/二个节点：

```text
Σ = (配置 Cfg，中心控制 Cc，中心持久/缓存 Jc，
     {Ni = (Ki, Ji, Hi, Gi)} i∈N，中心通道 Gc，在途消息 M，环境 E)
```

Cc 保存全局身份、固定节点、意图/版本、预留、待发送责任与已确认事实；Jc 保存 Redis 权威提交及派生视图。Ki/Ji/Hi/Gi 分别为节点核心、本地持久与易失协调、真实资源和通道。B3–B7 的既有 K/J/H/G 按单节点解释，不把中心与节点阶段合成同一个枚举。

M 包括发送、投递、重投、丢失和待确认消息及完整身份/版本，不假设跨请求 FIFO 或 exactly-once；无效消息在解析/身份边界拒绝。E 包括各进程/存储及各机时钟/声明误差，不假设所有机器时钟相同。中心未知但节点已经运行是允许状态，不能要求各层副本始终相等。

证明另外使用历史 `T` 记录已经发生的事件。`T` 是推理用的历史，不要求真实数据库永久保存无限日志。

三个状态必须分开：`K` 认为虚拟机怎样，`H` 中虚拟机实际怎样，宿主适配器最近观察到了什么。进程可能已经启动而 `K` 尚未收到回执；也可能 `K` 曾发布运行而进程随后退出。把它们定义成同一个变量，会直接排除最需要验证的故障。

### B8 初始化、可达状态与归纳

纯本地核心空初态仍对应 initial_world；完成原配置、维护、位置、租约及持久初始化前不能接受用户请求。

FreshReady_node(Ni) 要求合法配置/受管根与库租约、允许空部署、预算/位置持久建立、Decode(Ji)=Ki、无未登记物理资源及空在途通道。RecoveredReady_node 要求原持久格式与完整配置匹配，从完整检查点和连续尾恢复，保留原资源/未知责任，不继承未重建许可，按规定启用观察/恢复，不要求所有 VM 停止；损坏或不匹配的原库不能当新部署。

FreshReady_center(Cc,Jc) 要求显式一次性部署初始化、受保护节点登记、合法格式/预算/Redis配置、有效单写者及权威块/派生视图对应。RecoveredReady_center 从原耐久提交恢复绑定、意图、额度和 outbox；原库为空/损坏不能自动新建，节点结果未知继续未知。

中心、节点和 Redis 分别 Crash/Restart；一个重启不清空全部系统。上述条件是自有初始化/恢复程序的后置条件，不是任意给原库加的假设。系统从全新部署或其合法历史恢复，未就绪服务拒绝新工作。

WellFormed 包含局部表示/身份/索引/窗口，以及跨模块绑定/责任/版本关系；不要求中心、节点逻辑和真实资源相等。I_global 为 G3 所需共同不变量。

```text
Init(Σ) ⇒ WellFormed(Σ) ∧ Safe(Σ) ∧ I_global(Σ)
Reachable(Σ) := 从合法初态经允许步骤得到的有限执行前缀
WellFormed(Σ) ∧ Safe(Σ) ∧ I_global(Σ) ∧ Step(Σ,a,Σ')
  ⇒ WellFormed(Σ') ∧ Safe(Σ') ∧ I_global(Σ')
```

Step 包括中心/节点决定、存储、消息、宿主、流、时钟和故障，不能只证明正常调用。先后关系用辅助历史 T，保密另比较两条历史，最终完成性另分析无限执行条件。

### F4 资源不是一个磁盘剩余量数字

用资源向量表示预算：

```text
R = (实例数，处理器额度，宿主内存额度，磁盘未来增长，inode 数，
     宿主位置，控制记录，保留结果，网络连接，辅助进程，传输缓冲)
```

对每类资源 `r`，要求：

```text
Charged(r) + ReservedForUnfinishedWork(r) + ReservedForCleanup(r) ≤ Limit(r)
```

尚未确认清理的资源仍收费。逻辑磁盘的稀疏空洞只减少当下占块，不减少未来写满的责任；不能只按当前已用块数准入。数据库还需计入日志、检查点替换、索引和单事务峰值，而不只是主文件。

来宾内存大小也不等于整个宿主开销；进程、虚拟化线程和日志等需要独立限额或明确的外部上界。Firecracker 官方要求关注日志资源与宿主线程等部署因素。[生产宿主要求](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/prod-host-setup.md)

上式首先是逻辑预算定理。要推出真实峰值受限，还需逐项证明实际占用不超过模型计费，并声明非受管进程不会抢占预留空间的部署条件。资源检查本身不能创造磁盘，也不能保证任意宿主负载下不出现内存不足。

### F4.1 驻留结构和连接的完整计费

本条细化 F4/F6、S8/S14 及 G3 的容量责任，不恢复用户命令累计输出上限。

- 逐项纳入受管常驻结构：零计数键、已结束订阅者、请求/响应关联表、连接池、取消监听、排队/重试任务及库内在途队列。记录的值为零或业务结果已结束，不代表对应键/对象不占空间。
- 对每类结构给出“活跃对象 + 在途对象 + 显式保留窗口/结果 + 固定开销”导出的条数及字节上界，绑定实际分配和回收入口。可能无限增长的 unknown 责任不得丢弃，必须占用有限预算并限制新准入。
- 各类连接/许可按其合同覆盖所负责的完整正文、流、后台执行及实际退出/排空；收到 HTTP 响应头、发送取消或超时不能直接当成释放。自身退出路径须解除订阅和引用；有未确认效果时按合同保留责任。
- 零计数驱逐、池回收和后台任务退休必须与并发引用/计费原子配合，不能拆掉正在使用的计数器或遗失未决关联。模型计费到实际驻留的连接是自有证明义务；分配器、运行库、内核、envd 的剩余开销分别声明版本/配置和外部上界，并由工程测试核对。
- 持续命令输出只约束顺序、单消息/在途缓冲和并发，不约束累计字节；客户端 SDK 累积输出的内存不属于宿主内存定理。有限键数也不能单独推出整个进程内存上界。

最小正常轨迹在固定活跃/在途/保留预算下反复创建、连接、断线、销毁和退休，结束对象与订阅按合同回收。禁止轨迹是活跃计数不变但已结束键/订阅随总请求数无限增加，或只收响应头就退还仍在传输的许可。复用既有长期容量与慢流样例，不扩展为所有库的穷举压力测试。[runtime #3448](https://github.com/e2b-dev/runtime/issues/3448)、[E2B #1666](https://github.com/e2b-dev/E2B/issues/1666) 提供驻留键与许可生命周期的审查线索。

### F6 长期运行的真实承诺

历史退休保存足够的结果和高水位，使旧请求不能复活。结果保留期结束后，允许返回“结果已过期”等合同规定结果，而不是无限保存每次操作。

有界编号与有界记录下可以证明“耗尽时安全拒绝，仍保留清理能力”；不能证明“永远接受无限个新实例”。最终完成性也不能靠假设资源永不耗尽掩盖自身账本泄漏。

### F7 两层持久化、故障和责任守恒

中心 DecodeCenter(完整 Redis 权威提交)=Cc，节点维持 F3 的检查点/连续尾表示。两者不共享原子事务。中心 CAS 单条更新、编解码、耐久确认和缓存修订需对应 A11；Lua 不被插入不等于多命令出错自动回滚。发生持久化错误后，内存读到原记录不足以确认耐久；按[中心持久化合同](../module-contracts.md#中心持久化与恢复)恢复健康并确认包含原责任的耐久提交再派发。

新增故障点：中心提交回复丢失、节点已接受而回执丢失、节点事实已保存而中心未保存、中心已保存而确认丢失、两层退休中断。恢复使用原绑定/参数；失联不迁移/释额，Missing 不自动证明从未执行。

令 ReservationC(b,r) 为中心为绑定 b 保留的责任，ObligationN(b,r) 为节点该绑定可能仍有的占用及未完成/收尾义务。按统一计量证明 ObligationN(b,r) ≤ ReservationC(b,r)，并证明中心总和不超平台/租户/节点预算；两层账表示同一责任，不相加当双份物理资源。实际峰值另连接逻辑预算，未知/补偿不能丢预留。

节点事实退休由中心耐久确认及结果/窗口合同支撑，或保留足够有界退休信息，不能发出后即忘。两端保持高水位、过期窗口和终止记忆，旧请求拒绝；额度由原绑定充分清理证据释放，心跳到期不是证据。Redis/AOF、SQLite/WAL、日志、在途通信和收尾均计预算。

## G 目标性质和成立条件

令 `Reachable(Σ)` 表示从合法初始状态经过允许转换到达。`Always` 表示历史中每一点成立，`Eventually` 表示未来某一点成立。

下表既有本地字段/谓词按对应节点解释，公开入口/中心的对应责任按 D5 与 G3 连接。尤其 S3 的本地终止/围栏不能从中心终止提交直接推出；中心先禁止自身新许可，节点落实后的本地撤销及最终排空分别证明。

| 编号 | 正式性质 | 主要责任 |
|---|---|---|
| S1 身份完整 | `Reachable ⇒` 每个资源记录、索引、计划、尝试与所属实例的类型及身份一致；无冲突绑定 | 规则核心、持久服务 |
| S2 授权正确 | `Grant(u,r,b) ⇒ CanGrant(u,r,Σ,t) ∧ BoundTo(r,b)` | 请求入口、规则核心、网关 |
| S3 终止单调 | `Terminal(s)` 一旦提交，同一身份以后不能再次获得运行授权；旧工作不能越过生效围栏启动 | 规则核心、宿主 |
| S4 证据真实 | 成功工作、运行发布、停止、清理及释放各自蕴含该类事实的精确证据；未知不蕴含不存在 | 宿主、持久服务 |
| S5 结果不可改写 | `Final(k,r)` 与以后同键终局结果 `r'` 同时成立时，`r=r'`；迟到回执不能改变另一尝试 | 规则核心 |
| S6 持久责任 | `Accepted(op) ⇒` 未完成责任、原身份或合法退休结果持续可恢复 | 持久服务 |
| S7 隔离修改 | 每步只修改规则声明的对象；旧身份操作不能改变同位置的新绑定资源 | 所有模块 |
| S8 准入与界限 | 接受需要全部检查通过；编号不回绕；所有受管在途资源与清理责任不超预算 | 规则核心、持久服务、网关 |
| S9 流完整性 | 成功传输满足原绑定、合法结束、逐字节相等；截断、超限和错误不变成成功 | 网关及端点合同 |
| S10 时间正确 | 期限按对应接口计算；到期后不授予许可；旧到期观察不覆盖已提交续期 | 持久服务、请求入口 |
| S11 策略落实 | 实际宿主资源与规则对应获批描述；真实出口满足所选策略判定 | 宿主 |
| S12 查询与错误 | get/list 由可见状态正确派生；拒绝类别和顺序符合合同；无越权字段和私密日志泄漏 | 请求入口、持久服务 |
| S13 恢复一致 | 恢复状态来自某个合法持久提交，未知外部效果保留为未知；不补造历史成功 | 持久服务、宿主 |
| S14 安全退休 | 记录移除和位置复用保留防重放及原资源清理责任；失去原证据时不扩大删除范围 | 维护核心、宿主、网关 |
| F1 接受完备 | 对满足全部前提且可表示的输入，处理函数接受并返回规定后继，而非任意拒绝 | 各模块 |
| F2 正常功能 | 在功能端点合同及无故障条件下，创建、查询、续期、命令、文件和销毁产生规定结果 | 组合定理 |
| L1 有条件推进 | 已接受操作在规定公平与环境条件下最终成功或进入明确终局失败，不因自身循环而永久阻塞 | 组合定理 |
| L2 有条件清理 | 已终止且外部停止清理最终可完成时，原受管资源最终释放 | 持久服务、宿主、网关 |

### G1 保密是两条执行之间的关系

“每次鉴权都检查了”不等于已经证明无泄漏。定义 `Σ1 ≈u Σ2`：用户 `u` 自己可见的状态和允许公开的信息相同，其他租户私有状态可以不同。

在相同用户输入、相同公开资源条件及匹配外部调度下，要求：

```text
Σ1 ≈u Σ2 ⇒ Observations_u(T1) = Observations_u(T2)
```

必须明确哪些信息是公开的，例如共享容量不足可能是可观察结果；否则一边剩余容量足够、一边不足，响应不同就会使过强定理不成立。租户错误信息、列表总数、模板存在性和日志输出均需在规定观察集合中审计；时序和硬件旁路不包含在这个结论里。

### G2 最终完成性的条件不能代替证明

正常创建成功目标为：

```text
AcceptedCreate(op)
∧ 该操作不被取消且未到期
∧ 所需外部动作在允许期限内成功
∧ 已启用内部工作得到公平执行
  ⇒ Eventually RunningResult(op)
```

失败清理目标为：

```text
TerminalIntent(s)
∧ 外部停止、清理和持久写入最终可用
∧ 内部清理步骤得到公平执行
  ⇒ Eventually Quiescent(original_binding(s))
```

公平只表示持续可执行的步骤不会被永远忽略，不表示外部调用一定成功，更不表示一定在截止前完成。还必须证明：后续步骤真的被启用、前置条件在等待中不会被自己破坏、队列不会漏工作、重试预算不会形成循环、清理不会互相等待。

证明可用阶段顺序与剩余工作量的组合下降关系；加入工作可能暂时增加队列长度，因此不能简单声称“队列长度每步下降”。已有覆盖记录中的内部推进义务必须逐一解决，不能改名为“假设公平”后删除。

### G2.1 局部故障域与跨实例推进

本条细化 L1/L2 与 P8 的跨实例推进，不新增固定耗时 SLA 或要求本批完成 #284 的宿主并行重构。

- 冻结请求/通道局部、实例局部、真正共享依赖故障的分类及传播范围。单个坏请求、失效订阅或局部恢复错误不能通过自有错误传播/队列/引用/锁造成其他可独立处理实例无限阻塞；共享 Redis/SQLite 权威损坏则可安全停止相关全局推进。
- 中心决定锁不得跨远程 I/O 持有；本地串行实现仍须在约定期限和公平调度下释放等待/锁并继续处理，而非假定扫描器、锁和清理本身已经正确。永久不返回的外部调用若属于未满足的环境前提，必须明示其影响范围，不能承诺该条件下无限制推进。
- 进展前提只要求相关外部停止/观察/通信/存储最终提供所需结果和声明调度；内部工作启用、预算保持、队列取出、引用释放及无环等待必须实际证明。未知实例保留占用，不为让另一实例推进而误释额。
- 慢流/取消订阅在自己的网关中按预算解除引用并处理其他合格消费者。envd/SDK 的共享流广播和池行为作为细化外部合同及测试条件，不能用它们的局部修复声称整个外部程序已证明，也不能将自有阻塞改名为外部条件。

最小正常轨迹：A 的局部恢复/通道失败 → 按原身份保留或收尾 → 条件满足的 B 继续处理并完成清理。禁止轨迹：A 的错误导致整个恢复扫描永久退出，或一个已失效消费者通过自有结构永久卡住其他消费者。工程复用已有恢复/慢流测试，仅补确实缺失的故障分类样例。[E2B #1587 的弃用流讨论](https://github.com/e2b-dev/E2B/issues/1587#issuecomment-5058786818)、[#1641 的共享客户端池问题](https://github.com/e2b-dev/E2B/issues/1641) 是故障域依据，不是我方 SDK 全量证明任务。

### G3 分布式系统性质

保留 S1–S14、F1/F2、L1/L2，连接其局部版本与以下系统性质；不是只证明两个测试节点。

| 编号 | 系统结论 |
|---|---|
| DS1 唯一绑定 | 每个全局沙箱固定节点/代际与唯一原本地实例；无重试双跑/失联改绑 |
| DS2 全局责任 | 节点原资源及收尾义务由中心预留覆盖；平台/租户/节点预算不超界，未知不解账 |
| DS3 持久派发 | 高级派发有先行中心耐久意图，本地副作用有本地责任；未知提交不造新实例 |
| DS4 重放终止 | 同键同参数复用原结果；异参数/旧代际/过期窗口拒绝；迟到请求不复活终止绑定 |
| DS5 结果证据 | 对外成功有持久结果与真实证据；接受/就绪/停止/清理不同，旧观察不覆盖新事实 |
| DS6 两端隔离 | 身份、固定路由、本地资格与修改范围正确；同用户跨节点/同节点多租户不越权 |
| DS7 恢复退休 | 独立重启不丢另一层责任；确认/退休/窗口合同使旧请求不再次执行 |
| DS8 时间数据 | 原起点、续期和各终止阶段正确；两端中继维持原实例、完整性和有界驻留 |

I_global 是这些结论所需的归纳状态/历史约束，不只是终态检查表；保密仍按 G1 双执行关系，不能用单轨迹安全代替。

DL1/DL2 将 L1/L2 扩展到两端：单有效中心、必要存储/节点最终可执行、通信最终可提供原操作结果、停止/清理可用和声明调度条件下，接受工作最终有合法稳定结果及必要收尾。仍须证明工作被启用/不丢失、预算支持收敛和等待依赖无环；永久分区不保证完成。

### H1 模块之间的证明接口

按保证及其前提划分。每个合同注明输入/输出、修改范围、成功证据、拒绝/未知、崩溃责任、版本和预算；纯比较用函数合同，生命周期用状态转换，通信/流用事件历史，不给每函数另建状态机。

| 模块 | 下游保证 | 不可假设掉的自有逻辑 |
|---|---|---|
| 公开入口 | 完整输入、认证租户、结果/错误/可见投影 | 解析、身份、单位/默认、错误映射 |
| 中心控制 | 唯一固定节点、合法预留、原意图/版本及窗口终止 | 调度、全局检查、有界数值、退休 |
| 中心持久协调 | 原子接受、耐久后派发、原结果与恢复 | CAS/Lua/编码、未知、缓存/outbox、确认/退休顺序 |
| 协议/节点入口 | 编解码保真、认证绑定、原本地映射与拒绝 | 证书映射、版本/窗口、参数比较、持久接收/终止 |
| 本地控制/持久化 | 既有 World 转换、本机责任/寿命/预算/恢复 | 全失败分支、SQLite连接、工作/回执、时钟和退休 |
| 宿主执行 | 原资源、获批配置、真实观察、停止/清理 | 围栏/身份/调用顺序、部分失败及位置复用 |
| 两端网关 | 原实例、忠实转发、显式失败、有界驻留/排空 | 授权登记/撤销、路由、异步转发/半关闭/回收 |

上游输出满足下游前提须由邻接定理或 I_global 提供；双向依赖用初始化和每种步骤共同归纳，不能循环假设“整个系统正确”。实例独立不等于共享额度/登记无交互。

库/引擎/密码算法/系统调用提供最小外部合同；自有封装、组装、锁/事务/回调仍证明对应，不将整个 API/节点当可信函数。模板是 owner 明确排除项，核心使用其合同仍为显式条件。

### H3 系统组合的证明接口

1. 纵向精化：各实际模块对应独立合同/模型，覆盖初态、成功、拒绝、未知及恢复；对应业务字段、派生缓存及辅助历史。纯函数一步对应，编排以保持可观察事件的多步对应。
2. 横向组合：上游输出满足下游前提，共同 I_global 保持，共享状态/资源修改范围正确；不能只并列几个局部安全定理。
3. 通信连接：实际端点实现消息身份/版本和重投语义，允许重复/延迟/乱序/丢失；唤醒不替代持久 outbox。
4. 恢复连接：中心、节点、Redis独立中断，保持各自耐久状态及可能发生的物理/网络效果，不一起清空。
5. 系统结论：对任意预算内有限登记节点集合，初始化、所有微步骤与实现精化组合，推出实际可观察行为符合系统规约。允许内部不改变抽象状态的步骤，但无限内部空转由进展证明排除。

```text
外部合同 A ∧ 合法部署 D ∧ 各模块实现精化 R_i
∧ 接口相容/通信连接 ∧ I_global 初始化及保持
  ⇒ 实际组合执行符合声明系统规约及安全/功能性质

上述条件 ∧ 明确通信/存储/调度/收敛条件 ∧ 已证内部推进
  ⇒ 声明的最终完成性
```

安全按任意有限前缀归纳，G1保密另做双执行组合；不由两题 CI 或单机双服务实测推出全体多机执行已证明。每定理列节点/预算参数、输入、故障、外部前提及未覆盖项。
